### A1.3 추천

**추천: 안3.** 이유 3가지.
1. `[승인 #12·#13]`을 건드리지 않는다. 부제는 그대로 두고 **기술 정의 문장만** 교체하므로 승인 변경 결정이 필요 없다(#12·#13은 "기술 정의에서 언급"을 이미 허용).
2. 사용자 요구의 실체(운전 맥락·관계 탐색·근거 추적·결과 관리·매뉴얼 개선)가 전부 기술 정의에 들어간다. 즉 안1의 내용을 버리지 않는다.
3. 안1의 과장 지점 3곳을 제거한다: "상황을 판단" → "확인 순서와 행동 후보 제시" / "생산라인 전체" → "가상 생산라인" / "시스템" → "에이전트". "매뉴얼 개선" → "매뉴얼 개정 후보".

### A1.4 "포터블 MES" 3자 충돌 정리 — **결정 필요**

| 당사자 | 주장 | 상태 |
| --- | --- | --- |
| 기존 팀 결정 | codex 원 부제 유지. "포터블 MES"는 **부제가 아니라 기술 정의에서만** 언급 | `[승인 #12·#13]` |
| 전문가1 D-31 | "포터블 MES 부제 강등". 원문은 #13 재심 요청 | `[미결]` 승인 대기 |
| 사용자(2026-09-17) | 발표·문서에서 "현장 지식 계층을 보완하는 **포터블 MES 에이전트**"로 표현 | `[신규 제안]` 미승인 |

- 충돌의 실제 크기: D-31의 "강등"은 **이미 #12·#13으로 집행된 상태**다(부제에 없음). 따라서 D-31과 #12·#13은 실질 충돌이 아니고 중복이다. 남는 쟁점은 D-31 원문의 강한 해석 — "기술 정의에서도 빼자" — 인데, 이 해석을 채택하면 사용자 요구와 **정면 충돌**한다.
- 사용자 표현의 위험: "포터블 MES 에이전트"는 제품 범주를 MES로 선언하는 형태다. "현장 지식 계층을 보완하는"이 앞에 붙어도 슬라이드 제목·구두 발표에서 뒷부분만 남는다. 실무자 청중은 MES 대체품으로 듣는다. 이는 D-31이 경고한 지점이다.
- `[신규 제안]` 절충 문안(문서·발표 공통 규칙):
  - 프로젝트명·부제·슬라이드 제목에는 "MES"를 쓰지 않는다.
  - "포지셔닝" 문단 안에서만 다음 형태로 쓴다: **"ShiftLink는 MES·PLC·SCADA를 대체하지 않는다. 생산실적 집계가 아니라 현장 지식 계층(기록·판단 근거·유사 사건·인계·결과 추적·매뉴얼 개정 후보)을 보완하는 포터블 보조 에이전트다."** — "MES"는 반드시 "대체하지 않는다" 문장과 같은 문단에 둔다.
  - "포터블 MES 에이전트"라는 **단독 명사구는 쓰지 않는다**(A9 대조표에 포함).

## A2. 문제 정의 고도화

### A2.1 기존 문제 정의 인용 `[기존]` (src_b 2절)

> "현장 장비 관리에서는 작업자마다 사용하는 용어와 기록 수준이 달라, 동일한 증상과 조치에 관한 경험을 일관되게 축적하고 활용하기 어렵다는 것을 문제 가설로 설정한다. … 숙련자의 판단 근거, 작업 요령, 적용 조건이 충분히 기록되지 않으면 신규 작업자는 기존 기록과 매뉴얼만으로 업무 맥락을 이해하기 어렵다. 또한 작업 과정에서 얻은 경험이 매뉴얼 개선으로 연결되지 않아, 유사한 상황에서도 개인의 기억과 구두 설명에 의존할 수 있다."
> "본 MVP에는 외부 숙련자 자문과 실제 전문가가 작성·검수한 평가셋이 없다. … 실제 암묵지의 외재화, 신입 판단 능력 향상, 현장 생산성 개선은 측정·입증하지 않았다."

`[승인 #14]`는 "기존 문제 정의 보존 후 보강 문장 추가"다. 따라서 위 문단은 **삭제·재작성 대상이 아니다.** 아래는 보강(추가)안이다.

### A2.2 "개별 장비 관점 → 생산시스템 관점" 전환이 문제 정의에 요구하는 변화

기존 문제 정의는 손실 원인을 **기록의 불일치**와 **지식 전달의 단절** 두 축으로 본다. 생산시스템 관점을 넣으면 세 번째 축이 추가된다: **관측 지점과 원인 지점의 불일치**. 연속 라인에서는 증상이 나타나는 설비와 원인이 있는 설비가 자주 다르다. 기록이 아무리 일관돼도 "어느 설비의 기록을 찾아봐야 하는지"를 틀리면 지식은 있어도 도달하지 않는다.

`[신규 제안]` 보강 문단(2절 말미 추가안):
> "또한 연속 생산라인에서는 이상 증상이 관측된 설비와 원인이 있는 설비가 다를 수 있다. 상류 공정의 상태, 하류 정체, 공통 유틸리티 공급, 인터록 동작, 라인 속도·운전 모드·생산 품목이 함께 작용하기 때문이다. 개별 장비 단위로만 기록·검색하면 기록이 일관되어도 원인 지점의 지식에 도달하지 못한다. 본 프로젝트는 기록의 불일치·지식 전달 단절에 더해, **관측 지점과 원인 지점의 불일치로 인한 지식 접근 실패**를 문제 범위에 포함한다. 다만 이 확장은 가상 라인 L1 위에서 구조·절차를 검증하는 것이며, 실제 현장의 오진단 빈도나 손실액을 측정·주장하지 않는다."

### A3.1 계층 의미 정의 `[신규 제안]`

| 계층 | 의미 정의 | 판정 기준(무엇이 한 개인가) | 이번 MVP에서의 취급 |

핵심 구분 `[신규 제안]`: **설비군(종류)과 개별 장비(대수)를 분리한다.** 기존 K-01 `equipment` enum(HPU/GR/RT/CV/COMMON)은 **설비군**으로 읽고, 개별 장비는 `equipment_unit_id`(RT-01, GR-02 …)로 새로 둔다. 이렇게 하면 승인 #1의 "HPU·GR·RT·CV 4설비" 범위를 **종류 기준으로 그대로 보존**하면서 대수를 늘릴 수 있다.

### A3.2 승인 #1과 D-32의 관계 정리 — **결정 필요**

- `[승인 #1]`: "가상 냉연 코일 처리 라인 L1, 공용 설비 HPU·GR·RT·CV". 문면은 **설비 4종**이고 "대수"나 "구간"은 언급이 없다.
- 전문가1 D-32 `[미결]`: "L1을 보조설비 구간으로 표기하고 공정 본체(압연·산세 등)를 제외 명시".
- 사용자 요구: 공정/구간 3~5개, 장비 6~10대.
- 사실관계: HPU(유압 유닛)·GR(구동 모터·감속기)·RT(롤러 테이블)·CV(컨베이어)는 **모두 소재를 가공하지 않는 보조·이송·유틸리티 설비**다. 이 4종만으로는 냉연 라인의 공정 본체(산세·압연 스탠드·소둔·조질압연)를 구성할 수 없다. 따라서 **D-32의 진단은 도메인적으로 맞다.** 공정/구간을 "산세→압연→권취"처럼 만들면 존재하지 않는 설비를 가정하게 되고, 이는 승인 #1 위반이면서 동시에 합성 데이터의 도메인 오류가 된다(A10 RK-01).
- `[기존 수정안]` 최소 변경 결론: **공정(process)을 만들지 말고 구간(zone)을 만든다.** 구간은 "기능 전환"이 아니라 "기동·정지 그룹 + 소재 위치"로 정의하면 이송 설비만으로 성립한다. 그리고 공정 본체는 **라인 경계 밖의 외부 인터페이스**로만 둔다(상류 소재 공급원, 하류 반출 수요처). 이것이 D-32 채택과 동일한 효과다.
- → **결정 질문 Q2, Q3**(A13).

### A3.4 관계 유형 정의 · 냉연 코일 이송 계통 예시 · 진단에서의 사용법 `[신규 제안]`

관계는 방향이 있는 3항(from, type, to) + 속성(조건·지연·강도)으로 둔다.

| 관계 유형 | 도메인 의미 정의 | L1 구체 예시 | 진단에서 쓰이는 방식 |
| --- | --- | --- | --- |
| `material_flow_upstream/downstream` (상류/하류) | 소재가 지나가는 순서. from이 먼저 소재를 다룬다 | RT-01 → RT-02 → CV-01 → EX-DN | 증상 관측 지점의 **상류**를 원인 후보로, **하류**를 정체 후보로 동시에 올린다. 시간 순서상 상류 이상은 하류 증상보다 **앞서** 나타나야 한다(시간 순서 검증) |
| `material_handoff` (물류 전달) | 소재가 설비 간에 **넘겨지는 접점**. 상류/하류와 달리 "인수 조건"이 있다 | RT-02 ↔ CV-01 전달 접점(코일 착지 위치·간격) | 전달 접점의 증상(충격음·위치 편차·간격 불균일)은 **양쪽 모두**를 후보로 만든다. 단일 설비로 좁히지 못하게 하는 장치 |
| `drive` (구동) | from이 to에 회전·직선 동력을 준다 | GR-01 → RT-01, GR-01 → RT-02, GR-02 → CV-01 | to에서 관측된 속도 변동·진동·이음은 from의 베어링·커플링·감속기를 반드시 후보에 포함. 같은 구동원을 공유하는 to가 여러 개면 **동시 증상** 예상 |
| `utility_supply` (유압·전력·공압·냉각 공급) | from이 to에 에너지·매체를 공급한다. 하위 유형 `hydraulic`/`power`/`pneumatic`/`cooling` | HPU-01 →(hydraulic) RT-01 클램프, HPU-01 →(hydraulic) CV-01 스토퍼, UT-PWR →(power) GR-01·GR-02·HPU-01, UT-AIR →(pneumatic) CV-01 브레이크, UT-CW →(cooling) HPU-01 오일쿨러 | **여러 to에서 동시에** 다른 증상이 나오면 공통 공급원을 최우선 후보로 올린다. "동시성 + 공통 공급원"이 공통 원인 후보 판정 규칙 |
| `interlock` (인터록) | from의 상태가 to의 운전을 **강제로 제약**한다. 설계된 정상 동작이다 | CV-01 만재 →(interlock) RT-02·RT-01 정지 / HPU-01 압력 저하 →(interlock) RT 이송 정지 | 관측된 "정지·간헐 정지"가 **고장이 아니라 설계 동작**일 수 있음을 먼저 배제하게 한다. 사건 2의 핵심 |
| `influence` (영향, 인과 미확정) | 상관은 관측되지만 인과 경로가 확정되지 않은 연결. **가설 표시 전용** | RT-02 롤 편심 ↔ GR-01 진동(가설) / GR-02 부하 변동 ↔ CV-01 벨트 트래킹(가설) | 원인 후보로 **제시하되 확정에 쓰지 않는다.** `influence`만으로 지지되는 원인은 "원인 미확정 + 추가 확인 질문"으로 강제한다 |

`[신규 제안]` 관계 사용 규칙(판단 원칙과 연결):
1. 조회 범위는 관측 지점에서 관계 **1홉(hop)**까지를 기본으로 하고, `utility_supply`와 `interlock`만 2홉까지 확장한다. 이유: 이송 계통은 1홉만 보면 유틸리티 공통 원인을 놓치고, 3홉 이상은 6대 규모에서 라인 전체와 같아져 범위 식별 정확도 지표가 무의미해진다. `[제안값]`
2. `influence` 관계로만 도달한 장비는 "확인 대상"에 넣고 "원인 후보"에는 낮은 순위로만 넣는다. 인과와 동시 발생을 구분하라는 사용자 판단 원칙의 구현 지점이다.
3. 동일 시각에 2대 이상에서 증상이 있으면, 공통 `drive` 또는 공통 `utility_supply` 조상을 먼저 조회한다.
4. 관측 증상이 "정지·속도 저하"이면 `interlock` 관계를 **먼저** 조회해 설계 동작 여부를 배제한 뒤 고장 후보를 올린다.

## A5. 암묵지 T1~T5 고도화

**중요 전제**: `[미결 #16 / U-6]` T1~T5의 **원 정의문과 포함·제외 기준은 미확인**이다(전문가1 원문 미대조). 아래 내용은 **원 정의 확인 전 잠정안**이며, 0주차에 원 정의가 확인되면 재작성 대상이다.

### A5.1 기존 정의(용어사전 기준) `[기존]`
T1 감각 기반 이상 징후 판단(소리·진동·냄새) / T2 조건부 요령 / T3 트러블슈팅 순서 / T4 인수인계 맥락 / T5 안전 금기.

### A5.2 T유형 × scope 연결 `[신규 제안, 잠정안]`

`scope`를 K-01에 새로 둘 것을 제안한다: `line` / `zone` / `equipment_class` / `equipment_unit` / `component`. 기존 `equipment`(설비군) 필드는 그대로 두고 `scope`와 `equipment_unit_id`를 추가한다(하위 호환).

| T | 주 발생 scope | 왜 그 scope인가 | 생산시스템 관점에서 추가되는 것 |
| --- | --- | --- | --- |
| T1 감각 이상징후 | `component`·`equipment_unit` (주), `line`(부) | 소리·진동·냄새·열은 물리적 발생원에 붙는다 | `line` scope T1이 새로 필요하다: "라인 전체 사이클 리듬이 미세하게 늘어진다", "전달 접점 충격음의 간격이 불규칙하다" — 단일 장비에 귀속되지 않는 감각 지표 |
| T2 조건부 요령 | `equipment_unit` + **운전 컨텍스트 조건** | 요령은 조건이 본질이다 | `conditions[]`의 signal 축에 `line_mode`·`line_speed`·`product_spec`·`shift`·`restart_after_stop`를 추가해야 T2가 성립한다. 기존 conditions는 설비 계측값만 상정 |
| T3 트러블슈팅 순서 | **`zone`·`line`** (기존안 추정은 `equipment_unit`) | 순서의 핵심이 "어디부터 보는가"이고, 그것이 관계 탐색 순서다 | T3 steps에 "① 인터록·설계 동작 배제 ② 공통 유틸리티 확인 ③ 상류 확인 ④ 당해 장비 내부"를 넣으면 T3이 곧 관계 모델의 사용법이 된다. 구조화는 D-28 `[미결]` |

| T5 안전 금기 | `equipment_unit`·`component` + **`line` 운전 상태** | 금기의 성립 조건이 "라인이 어떤 상태일 때"다 | LOTO·운전정지는 라인·구간 단위 에너지 격리 문제다. T5 카드에 `line_state`(운전/정지/재가동 중/에너지 격리) 조건을 넣어야 정지·재가동 상황의 금기를 표현할 수 있다 |

### A5.3 새 유형이 필요한가 — D-29 T6_setup_restart 검토

- `[미결]` 전문가1 D-29: `T6_setup_restart` 신설 + `tried_and_failed[]`. `[미결 U-7]`: D-27·D-29는 1주차 스키마 확정 전에 결정되지 않으면 MVP 미채택.
- 도메인 판단: **정지·재가동은 별도 유형이 필요할 만큼 성질이 다르다.** 연속 라인에서 사고·불량의 상당 부분은 정상 운전 중이 아니라 정지 후 재가동·셋업 전환 시점에 발생한다. 소재가 라인에 남아 있는 상태, 유압 계통 재가압, 인터록 리셋 순서, 잔압·잔류 에너지가 모두 이 시점에 걸린다. 사용자 요구에도 "정지·재가동 상태"가 데이터 범위(3항)에 명시돼 있다.
- 그러나 **T6 신설의 비용이 크다.** T축은 문서 6곳에 동시에 걸려 있다: ① K-01 `tacit_type` enum ② 규모 목표 "T별 최소 20, T5 최소 25" `[승인 #5]` ③ 커버리지 매트릭스 "T1~T5 × 설비 4종, 빈칸 0" ④ judge 4항목 기준 ⑤ 봉인 평가셋 층화 구성(질의36+인계24, 안전 서브셋12) ⑥ 정답지 형식. T6을 넣으면 최소 20장을 추가 생성·검수해야 하고 봉인셋 구성이 바뀐다. 2주차 말 봉인 일정에서 위험이 크다.
- `[신규 제안]` **절충안: T6을 만들지 않고 `procedure_phase` 필드를 추가한다.** 값 `normal` / `stop` / `restart` / `setup_change`. T3·T5 카드에 `procedure_phase=restart`를 붙이면 재가동 금기·재가동 순서를 표현할 수 있고, T별 최소 건수·커버리지 매트릭스·봉인셋 구성은 건드리지 않는다. 대신 커버리지 매트릭스에 열 하나(`procedure_phase`)를 추가하고 `restart` 최소 건수를 `[제안값] 8건`으로 둔다.
- 병행 제안: `tried_and_failed[]`(D-29 후반)는 T6과 분리해 **사건(Event) 측 필드**로 두는 것이 낫다. "확인했으나 이상 없던 장비"(사용자 요구 4항)와 같은 성질이고, 카드가 아니라 사건의 사실이다. → `checked_no_finding[]`으로 Event에 둔다.
- → **결정 질문 Q4**(A13).

### A5.4 T유형 판정 경계 잠정 규칙 `[신규 제안, 잠정안]`
동일 지식이 2개 유형에 걸릴 때의 우선순위: **T5 > T3 > T2 > T1 > T4**. 근거: 안전 금기는 누락 비용이 가장 크고(T5 선두 노출 규칙과 정합), 순서는 요령을 포함하며, 요령은 감각 판단을 조건화하고, 인계 맥락은 위 넷의 전달 형태이기 때문이다. 이 우선순위는 원 정의 확인 전 잠정이며, 원 정의가 다른 경계를 쓰면 폐기한다.

## A6. 대표 사건 3건 — 도메인 서사

**모든 수치는 `[가상 값]`이다.** 실제 설비 정상범위·임계치가 아니다. 설비 사전 `plant/L1.yaml`에 "가상" 명기 `[기존]`. 사건 ID는 제안값이며 실제 원장 번호는 2주차에 부여된다.

### EV-A01 — 상류 구동 이상이 하류 전달 증상으로 나타난 사건 (사용자 필수 시나리오 1)

- **사건 당시 라인 상태**: 운전 모드 `자동 연속`, 라인 속도 `42 m/min`[가상 값](해당 품목 표준 45 m/min[가상 값]), 생산 품목 `코일 폭 1050mm · 두께 0.8mm`[가상 값], 교대조 `C조 야간(22:00~06:00)`, 직전 4시간 무정지.
- **관련 장비와 관계**: 관측 지점 CV-01. 관계 경로 — GR-01 `drive`→ RT-01·RT-02 / RT-02 `material_handoff`↔ CV-01 / GR-02 `drive`→ CV-01 / HPU-01 `hydraulic_supply`→ RT-01 클램프.
- **관측값(3개 이상)**:
  1. CV-01 사이드 가이드 접촉음 발생 빈도 `약 3~4회/코일`[가상 값] (평소 0회)
  2. CV-01 코일 착지 위치 편차 `+18 mm`[가상 값] (허용 ±10 mm[가상 값])
  3. RT-02 롤 회전속도 변동폭 `±2.4 %`[가상 값] (정상 ±0.8 % 이내[가상 값])
  4. GR-01 감속기 케이스 표면온도 `68 ℃`[가상 값] (정상 55~62 ℃[가상 값]), 진동 실효값 `4.1 mm/s`[가상 값] (정상 ≤2.5 mm/s[가상 값])
  5. HPU-01 공급압 `14.2 MPa`[가상 값] (정상 13.5~15.0 MPa[가상 값]) — 정상
- **확인했으나 이상 없던 장비**: HPU-01(압력·유온 정상), GR-02(온도 57 ℃·진동 1.9 mm/s[가상 값]), CV-01 벨트 장력(정상), UT-PWR(전압 변동 없음).
- **베테랑의 판단 과정(V-01 박 반장, 28년, 감각 우선)**:
  1. "소리가 CV에서 나지만 CV 혼자 낼 소리가 아니다." — 접촉음이 **코일마다 일정 횟수**로 반복되는 것은 벨트 자체 손상보다 **들어오는 소재의 자세**가 매번 틀어진다는 뜻으로 읽는다.
  2. 전달 접점(`material_handoff`) 증상은 양쪽을 본다 → RT-02를 먼저 본다.
  3. RT-02 롤 자체 손상이면 특정 롤에서만 소리가 날 텐데 그렇지 않다 → **RT-02를 돌리는 쪽**을 본다.
  4. GR-01은 RT-01·RT-02를 **같이** 구동한다. 회전 변동이 두 RT에 함께 나타나는지 확인한다(공통 구동원 규칙).
  5. 온도와 진동을 손으로 확인한다. "68 ℃면 손을 오래 못 댄다. 진동이 평소보다 굵다."
  6. 유압을 의심에서 내린다: 클램프 압력이 정상 범위이고 압력 저하였다면 접촉음보다 **슬립음**이 먼저 난다.

### EV-A03 — 공통 유틸리티 이상이 여러 장비에 동시 영향 (사용자 필수 시나리오 3)

- **결과와 관찰 기간**: 즉시 결과 — 유온 `74 → 58 ℃`[가상 값], 압력 맥동 `±1.8 → ±0.5 MPa`[가상 값], RT-01 압하 시간 `1.2 초`, CV-01 응답 지연 해소. 관찰 기간 `1주`[가상 값]. 결과 상태 = `관찰 중` → 1주 후 `해소`.
- **재발 여부**: 없음. 단 동일 원인(냉각수 스트레이너 막힘)이 **과거 1건** 존재 → 누적 2건, 안전 관련이므로 개정 후보 임계(안전 2건) 충족.
- **교대 인계 문구 예시**: "HPU-01 유온 74 ℃ 경보 초과로 RT-01 압하 지연·CV-01 스토퍼 응답 지연 **동시 발생**. 개별 설비 고장 아님. 원인은 냉각수 스트레이너 막힘(냉각수 온도차 2 ℃). 정비가 청소 완료, 유온 58 ℃ 회복. 라인 속도 40 m/min 유지 중, 유온 55 ℃ 이하 안정 확인 후 45 복귀. **유온 65 ℃ 초과 시 유압 배관·필터 분리 금지**(T5). 관찰 1주, 매 교대 유온·냉각수 온도차 기록 인계. 근거: EV-A03, K-aaaa(T3 동시 증상 시 공통 공급원 우선), K-bbbb(T5 고온 유압 금기)."
- **반복 시 매뉴얼 개정 후보**: 조직 보조 매뉴얼 「HPU 일상점검」 절 — 점검 항목에 "**냉각수 입·출구 온도차**(기준 6~9 ℃[가상 값])" 추가, "온도차 4 ℃ 미만이면 유온 정상이라도 스트레이너 점검" 조건 추가. 적용 범위: Z9 유틸리티 계통, 영향 장비 HPU-01·RT-01·CV-01. 검증 필요사항: 기준 온도차 값은 가상 값이므로 실 설비 적용 시 재설정 필요.
- **승인·발행 후 답변 변화**: 발행 전 — "RT 압하가 느리다" 질의에 RT 카드만 상위, 후보 ①(압력 상향)이 상위. 발행 후 — 응답이 "동시 증상 여부 확인 → 공통 유압 공급원 HPU-01 확인 → 유온·냉각수 온도차 확인" 순서로 바뀌고, ①에는 "유온 65 ℃ 초과 시 제외" 가 붙으며, 보조 매뉴얼 일상점검 절(버전·승인자 표시)이 인용된다.

### A6.4 3건이 함께 검증하는 것
EV-A01은 **상류 원인 ↔ 하류 증상**과 임시 복구·재발 추적을, EV-A02는 **인터록 = 설계 동작 배제**와 불필요 정비 억제를, EV-A03은 **동시 증상 → 공통 공급원**과 안전 보류를 각각 검증한다. 세 사건 모두 "①(대증 조치)을 수행하지 않음"이 포함되는데, 이것이 관계 모델이 실제로 오진단을 막았음을 보이는 증거 지점이다. 단 이는 **합성 사건에서의 설계된 결과**이며 현장 오진단 감소의 증거가 아니다.

## A7. 성공·실패·재발·정보부족·안전보류·상충 사례 설계 원칙

### A7.1 유형별 필요성·그럴듯함 조건·검증 대상

| 유형 | 왜 데이터에 반드시 있어야 하는가 | 도메인적으로 "그럴듯하게" 만드는 조건 | 평가에서 무엇을 검증하는가 |
| --- | --- | --- | --- |
| 정상(무이상) | 정상 상태를 모르면 "이상"의 기준이 없다. 또한 모든 질의에 이상을 찾아내는 과적합을 막는다 | 관측값이 전부 정상 범위 안이고, 그런데도 작업자가 질문한 이유(감각·불안·교대 인수)가 있어야 한다 | 근거 없는 이상 판정을 하지 않는가, "해당 지식 없음"·"정상 범위" 응답률 |

### A7.2 결과 미확인·관찰 중을 성공으로 집계하지 않는 이유

- **도메인적 의미**: 설비 이상 조치의 유효성은 조치 직후에 판정되지 않는다. 유압 계통·베어링·벨트 트래킹은 열적·기계적 정상화에 시간이 걸리고, 증상은 특정 운전 조건(속도 복귀, 품목 전환, 외기온, 연속 운전 시간)에서만 다시 나타난다. EV-A01이 그 예다: 조치 직후 개선처럼 보였으나 속도 복귀 시 재현됐다.
- **집계 규칙 `[신규 제안]`**: 결과 상태 enum = `improved_observing`(개선·관찰 중) / `resolved`(관찰 기간 종료·재발 없음) / `no_change` / `worsened` / `unknown`(결과 미확인) / `temporary_fix`(증상 억제, 원인 미제거). **성공 집계 = `resolved`만.** `improved_observing`·`unknown`·`temporary_fix`는 성공 분모에도 분자에도 넣지 않고 별도 계상한다.
- **과장 방지 효과**: "조치 성공률"을 발표할 때 관찰 중을 포함하면 수치가 부풀려진다. 이 프로젝트는 합성 데이터이므로 성공률 자체가 설계값이고, 따라서 **성공률 수치를 성과로 발표하지 않는다**(A9). 발표 가치는 "성공·미확인·임시복구를 구분해 집계하는 규칙이 코드로 구현되고 테스트됐다"는 사실에 있다.
- 구현 책임: 통계 계산은 코드(사용자 판단 원칙). LLM은 이 수치를 계산하거나 요약에서 재진술하지 않는다.

### A7.3 임시 복구(temporary fix)가 현장에서 발생하는 방식과 재발 추적의 필요성

- 발생 경로 4가지(도메인):
  1. **정지 불가**: 야간·납기·연속 라인이라 정지가 필요한 근본 조치를 할 수 없다 → 속도 하향·감시 주기 단축으로 버틴다(EV-A01).
  2. **정비 인력·부품 대기**: 예비품이 없어 설정 변경·응급 조정으로 대체한다.
  3. **원인 미확정**: 어느 장비인지 모르니 증상이 사라지는 조작을 찾아 그 상태로 둔다.
  4. **효과가 있어 보여서 굳음**: 임시 조치가 반복되면 "원래 그렇게 한다"로 기록 없이 표준화된다. 이것이 매뉴얼과 현장의 괴리(LG-8)의 주 발생 경로다.
- 왜 추적이 필요한가: 임시 복구는 **증상을 지우면서 원인 신호까지 지운다.** 추적하지 않으면 (a) 다음 교대가 정상 상태로 오인하고, (b) 재발이 새 사건으로 계상되어 같은 원인이 여러 번 "신규 발생"으로 기록되고, (c) 개정 후보 반복 횟수 집계가 틀린다.
- `[신규 제안]` 필수 필드: `temporary_fix`(bool), `original_cause_removed`(bool), `revert_condition`(임시 상태가 풀리는 조건: "속도 42 복귀 시"), `observation_end_at`, `recurrence[]`(재발 시각·조건).
- 인계 규칙: `temporary_fix=true` 항목은 관찰 기간이 끝나도 **자동 종료하지 않는다**(`[기존]` F-05의 자동 종료 금지 원칙과 동일). `original_cause_removed=true`가 기록될 때만 종료 가능.

### A7.4 베테랑 간 상충이 실제로 왜 생기는가 — 기존 `conflict_group` 정책과의 연결

`[기존]` 정책(src_b 4.7.3): 상충 카드는 병합하지 않고 `conflict_group` ID로 묶는다. 비안전 상충은 복수 의견으로 제시하고 어느 쪽을 인용해도 정답 처리. 안전 상충은 보수적 쪽만 채택하고 다른 쪽은 `status=rejected_safety`.

`[신규 제안]` 상충의 도메인 출처를 3가지로 명시하고, 각 카드에 `conflict_reason`을 기록한다. 이유: 출처를 모르면 상충이 "합성 데이터의 품질 결함"으로 보이고, 검수자가 한쪽을 지우려 한다. 출처가 기록되면 상충이 **보존해야 할 정보**가 된다.

| 출처 코드 | 무엇인가 | L1 예시 | 페르소나 대응 |
| --- | --- | --- | --- |
| `generation_gap` (경험 세대 차) | 과거 설비·과거 운전 방식에서 형성된 요령이 현재 조건에서는 조건이 달라짐 | "유온은 손으로 만져서 판단한다"(V-01, 28년) vs "온도계 값과 냉각수 온도차를 본다"(V-02, 19년) | V-01 감각 우선 ↔ V-02 계측 우선 |
| `modification_history` (설비 개조 이력) | 같은 설비가 개조·부품 대체를 거쳐 정상 범위·응답이 달라짐 | "클램프는 1.1초면 내려온다"(개조 전 기준) vs "1.3초까지 정상"(실린더 교체 후) | 경력 구간 차이로 표현 |
| `assigned_zone` (담당 구간 차이) | 담당 구간에서 관측되는 증상만으로 원인을 귀속시키는 경향 | Z2 담당은 "CV 벨트 조정", Z1 담당은 "GR 구동 확인"을 먼저 제시 | V-01(HPU·GR) ↔ V-02(RT·CV) |

`[신규 제안]` 처리 규칙 보강:
1. 비안전 상충 제시 시 `conflict_reason`과 `persona_id`를 함께 노출한다(전문가1 D-34 `[미결]`와 같은 방향). 단 **가상 페르소나임을 같은 줄에 표시**해 실제 전문가 출처로 오인되지 않게 한다.
2. `assigned_zone` 상충은 관계 모델로 **해소 가능한** 상충이다. 두 의견을 나열하는 대신 "두 후보가 각각 어느 관계 경로를 근거로 하는지"를 표시하고 확인 순서를 제시한다. 이것이 생산시스템 관점이 상충 처리에 주는 실질적 개선이다.
3. `modification_history` 상충은 **정상 범위 값 자체가 다른** 경우이므로 조건 필드(`conditions`)에 설비 개조 상태를 넣지 않으면 영구 상충으로 남는다. MVP에서는 개조 이력 모델링을 하지 않으므로, 이 유형은 **사건 3건 이내로 제한**하고 데이터 카드에 한계로 명시한다 `[제안값]`.
4. 안전 상충은 기존 정책 그대로(보수적 쪽만 채택). 변경 제안 없음.

## A8. 매뉴얼 개정 판단 기준·승인 정책 (도메인 관점)

### A8.0 범위 경고 — 이것은 신규 범위 확대다

`[기존]` MVP 제외 목록에 "실제 MES·CMMS의 확정 상태 자동 변경"이 있고, 기존안에는 **매뉴얼 개정 기능이 전혀 없다.** 문서 개정·승인·발행·복구는 7묶음 데이터 중 가장 무거운 신규 요구(src_c 6·7항)이며, 상태 머신·권한·해시·버전·검색 필터 연동을 모두 요구한다. 4주·4인·학생 프로젝트에서 전부 구현하는 것은 **과욕이며 위험**이다(A10 RK-02). 아래는 "도메인적으로 옳은 완전형"과 "4주 안에 가능한 최소형"을 구분해 쓴다.

### A8.1 개정 후보를 올리는 기준 (도메인 관점, 완전형)

| 판단 축 | 기준 | 근거 |
| --- | --- | --- |
| 반복 횟수 | 동일 조건 사건 **3건 이상** `[제안값]` | 2건은 우연, 3건이면 조건 재현성이 있다고 보는 현장 관행 수준. 실측 근거 없음 |
| 기간 | 최근 **90일** 이내 발생 `[제안값]` | 오래된 조건은 설비·운전 기준이 바뀌었을 수 있다 |
| 동일 조건 | 설비군 + 증상 코드 + `procedure_phase` + 품목·속도 조건군이 일치 | 조건이 다르면 개정이 아니라 새 조건 분기 추가다 |
| 재발 동반 | 3건 중 **1건 이상 재발 또는 임시 복구** | 재발·임시복구가 없으면 기존 절차로 해결된 것이므로 개정 불필요 |
| 안전 관련 | `safety_flag=True`이면 **2건**에서 후보 상정, 1건이라도 법령·지침 위반 가능성이면 즉시 후보 `[제안값]` | 안전은 반복을 기다리지 않는다 |
| 절차 결손 | 기존 절차에 **해당 단계가 없음**이 확인될 때(단계 누락) | 잘못된 단계 수정보다 누락 추가가 개정의 다수다 |
| 제외 | 원인이 라인 밖(EX-DN 반출 지연 등)이고 라인 절차로 통제 불가하면 개정 후보가 아니라 **운전 기준 조정 건의** | 매뉴얼로 해결할 수 없는 것을 매뉴얼에 넣으면 사문화된다 |

### A8.2 누가 승인하는가 `[신규 제안]`

| 개정 유형 | 초안 | 검토 | 승인 | 비고 |
| --- | --- | --- | --- | --- |
| 일반 절차 단계 추가·순서 변경 | LLM 초안 + 저년차·베테랑 | 반장 | 반장 | 기존 4.12 "반장·관리자 작업 승인" 확장 |
| 운전 기준(속도·조건) 변경 | LLM 초안 | 반장 | 반장 + 설비 엔지니어 | 품질·생산 영향 |
| 안전 관련(T5·safety_flag) | LLM 초안 | 안전담당 | **안전담당 필수 + 반장** | `[기존 4.12]` "정비·안전 담당 고위험 절차 승인" |
| 제조사 원문 관련 | — | — | **승인 불가** | A8.3 |

**MVP 한계 명시 `[기존 4.12]`**: 역할별 인증은 MVP에서 구현하지 않고 UI 라벨로만 구분한다. 따라서 위 승인 체계는 **데이터 모델과 상태 전이 규칙**으로만 구현되며, "권한이 없는 사람이 승인할 수 없다"는 것은 **보장되지 않는다.** 이 한계를 발표·문서에 그대로 적는다.

### A8.3 제조사 원문 불가침 — 2계층 문서 구조 `[신규 제안]`

| 문서 계층 | 코드 | 성질 | 편집 | 검색 |
| --- | --- | --- | --- | --- |
| 제조사 원문 | `vendor_doc` | 외부 저작물. 내용·해시 고정, 읽기 전용 | **불가**(수정·삭제·병합 금지) | 인용 가능. 원문 문장은 복제하지 않고 절 참조(문서명·절 번호·버전)만 `[기존 4.7.2 원문 미복제 원칙]` |
| 조직 보조 매뉴얼 | `org_manual` | 우리 조직이 원문 위에 덧붙인 보조 절차 | 개정 가능(상태 머신) | 승인·발행된 버전만 |

- 개정은 **항상 `org_manual`에만 기록**된다. `org_manual` 절은 자신이 보완하는 `vendor_doc` 절을 `supplements` 참조로 가리킨다.
- 원문과 보조 매뉴얼이 충돌하면 병합하지 않고 **"원문 절 + 조직 보완 절 + 충돌 표시"**로 함께 제시한다(카드 `conflict_group` 정책과 같은 철학).
- 저작권·라이선스 측면에서도 이 구조가 필수다: 시드는 원문 미복제 원칙이므로, 이번 MVP의 `vendor_doc`은 **가상 제조사 매뉴얼(합성)**이며 실제 Bosch Rexroth·Parker·SKF 문서를 적재하지 않는다. 이 사실을 데이터 카드에 명기한다.

### A8.4 승인 전 내용이 검색에 반영되면 안 되는 이유

1. **작업 지시로 오인된다.** 초안은 검증 전이며 L0에 해당한다. 검색에 뜨면 작업자는 승인 여부를 구분하지 않는다.
2. **순환 참조가 생긴다.** LLM이 만든 개정안 초안이 검색되어 다음 답변의 근거가 되면, AI 출력이 근거로 승격된다. 사용자 판단 원칙 "AI가 작성한 답변이나 개정안을 새로운 현장 성공 사례로 재집계하지 않는다"의 위반이며, 기존 `[기존 4.7.1]` 입력 격리 규칙(생성물을 입력으로 되먹이지 않음)과 같은 종류의 오염이다.
3. **책임 추적이 끊긴다.** 승인자·승인일·근거 사건 ID 없이 절차가 인용되면 사후 추적이 불가능하다.
- 구현 규칙 `[신규 제안]`: 검색 필터에 `doc_status='published'`를 **코드로 강제**한다(LLM 프롬프트 지시가 아니라 쿼리 조건). 평가 지표 "승인 전 개정 내용 검색 반영 0건"이 이 규칙의 검증이다.

### A8.5 복구(rollback) 버전이 필요한 현장 상황

1. 개정 후 **새로운 문제가 생겼다**: 추가한 단계가 다른 조건에서 오히려 정지를 유발.
2. 개정 근거 사건의 **원인 판정이 뒤집혔다**: 나중에 실제 원인이 다른 장비로 확인됨(EV-A02형 오판).
3. 설비·운전 조건이 **바뀌어 근거가 무효**가 됐다(부품 교체, 품목 단산).
4. **승인 절차 결함**: 안전 관련인데 안전담당 승인 없이 발행된 것이 사후 발견.
- 복구 규칙 `[신규 제안]`: 복구는 삭제가 아니라 **이전 버전 내용을 새 버전으로 재발행**한다(`rollback_of`, `base_version`, 복구 이유 필수). 이력은 지우지 않는다(`[기존]` 폐기 레코드 보존 원칙과 동일 철학). 복구된 버전도 승인 절차를 거친다.

### A8.6 4주·4인에서 가능한 최소형 `[신규 제안]`

**최소형 사양(MVP-M)**
- 대상: `org_manual` **4~7건** (사용자 제안값), 각 1~3개 절. `vendor_doc`은 합성 3~4건, 읽기 전용·해시 고정.
- 개정 후보: **3~5건** (사용자 제안값). 그중 최소 1건은 안전 관련, 최소 1건은 복구(rollback) 시연용.
- 상태: `draft` → `under_review` → `approved` → `published` / `rejected` / `superseded` / `rolled_back` (7상태). 전이는 코드가 수행.
- 필수 필드: `base_version`, `before`, `after`, `reason`, `evidence_event_ids[]`, `evidence_card_ids[]`, `applies_to`(라인/구간/설비군/장비), `affected_units[]`, `verification_needed`, `approver`, `approve_reason`, `content_sha256`, `published_at`, `rollback_of`.
- 검색 연동: `doc_status='published'` 강제 + 발행 전/후 동일 질의 답변 비교 1건(데모 증거).
- 반복 사건 집계: **코드가 계산**(동일 조건 3건 규칙). LLM은 개정안 문안 초안만.
- 개정 후보 생성은 **버튼 수동 트리거**(자동 감지 배치 없음).

**최소형에서 포기하는 것(명시)**
1. 자동 diff 렌더링 UI — 변경 전/후 텍스트를 2칸 표시만.
2. 절(section) 단위 부분 병합·충돌 해소 — 절 전체 교체만.
3. 다중 승인자 워크플로·전자 서명 — 승인자 1명 + 안전 건은 2명을 **기록만** 하고 강제하지 않음(역할 인증 미구현).
4. 개정 후보 자동 탐지 배치·알림.
5. `vendor_doc` 실제 제조사 문서 적재 — 합성 가상 매뉴얼로 대체.
6. 개정이 지식 카드(K-01)에 미치는 영향 자동 전파(카드 재검토 플래그) — 수동 목록만.
7. 매뉴얼 전문 검색(FTS5 전체 문서) — 절 단위 메타데이터 검색만.
8. 개정 이력의 시각화·타임라인.

**일정 배치 제안 `[제안값]`**: 1주차 스키마·상태 전이 정의(유현준), 2주차 데이터 4~7건 + 후보 3~5건 작성(전혜민) 및 상태 전이·해시·검색 필터 구현(유현준), 3주차 "승인 전 검색 반영 0건"·"미승인 발행 차단"·복구 1건 회귀 시험(전원), 4주차 데모에 "발행 후 답변 변화" 1스텝 추가. **2주차는 이미 사건 120·카드 250·산출물 600 생성과 봉인이 겹쳐 있어 충돌한다** → A11·Q5·Q7.

## A9. 안전 문구·과장 방지 문구 (그대로 문서에 넣을 수 있는 문안)

### A9.1 응답 화면 상시 표기 문안 `[신규 제안]`

```
[근거 등급: L1 — 합성·시뮬레이션 검증]  이 내용은 가상 라인 L1의 합성 데이터에서 생성·검증된 지식 후보입니다.
실제 작업지시가 아니며, 숙련자·관리자의 확인 없이 설비 조작·파라미터 변경·정비에 사용하지 마십시오.
ShiftLink는 고장 원인을 확정하지 않고, 안전·품질·정비의 최종 판정을 대신하지 않으며, 공식 MES/CMMS 상태를 변경하지 않습니다.
```
- 안전 관련 응답에 추가되는 줄:
```
[안전 금기 — 우선 확인]  아래 항목은 검색 순위와 무관하게 먼저 표시됩니다. 근거: {safety_basis}
근거가 확인되지 않은 안전 관련 조치는 제시하지 않고 보류합니다. 반장·정비·안전 담당을 호출하십시오.
```
- 근거 부족 시:
```
[원인 미확정]  현재 입력된 관측값과 관계 정보로는 원인을 확정할 수 없습니다. 아래 확인 질문에 답해 주십시오.
확인되지 않은 원인을 추정으로 제시하지 않습니다.
```

## A11. MVP / 후속 범위

### A11.1 4주 안에 반드시 되어야 하는 것 (MUST)

1. `[기존]` 기존 승인 골격 유지: 설비 사전·페르소나 3명·사건·카드·산출물·품질 게이트·2주차 말 봉인·3주차 채점·4주차 동결·데모.
2. `[신규 제안]` **관계 테이블 + 관계 기반 조회 범위**: A3.3 배치(구간 2 + 계통 1, 개별 장비 6대) + A3.4 관계 6유형 10~15건. 없으면 사용자의 관점 전환이 전혀 구현되지 않는다.
3. `[신규 제안]` **Event 다중 장비 연결**: `primary_unit`, `cause_candidate_units[]`, `affected_units[]`, `checked_no_finding[]`. 기존 `equipment`(단일)은 설비군 필드로 남긴다.
4. `[신규 제안]` **운전 컨텍스트 스냅샷**: `line_mode`, `line_speed`, `product_spec`, `shift`, `procedure_phase`, `interlock_triggered`, `alarms[]`.
5. `[신규 제안]` **결과·재발 기록과 성공 집계 규칙**: 결과 상태 6종, `temporary_fix`, `observation_end_at`, `recurrence[]`. 성공 = `resolved`만.
6. `[신규 제안]` **대표 사건 3건**(EV-A01~A03)이 W1~W12까지 끊김 없이 동작하고 데모에 포함.
7. `[기존]` T5 선두 노출 유지 + `[신규 제안]` 관계 확장 장비의 T5도 별도 조회에 포함.
8. `[신규 제안]` 과장 방지 문안(A9.1·A9.2) 화면·문서 적용.
9. `[기존]` 봉인·해시·데이터 카드·알려진 한계(RK-01을 1순위 한계로 기재).

### A11.2 되면 좋은 것 (SHOULD, 시간 여유 시)

1. `[신규 제안]` 매뉴얼 개정 **최소형**(A8.6): `org_manual` 4~7건, 개정 후보 3~5건, 상태 전이, 승인 전 검색 미반영, 복구 1건, "발행 후 답변 변화" 데모 1스텝.
2. `[신규 제안]` `procedure_phase=restart` 카드 8건 내외(정지·재가동 지식).
3. `[미결]` D-30 S4(숙련자 등록 초안)·S5(지식 결손 조회), D-37(작업 전 브리핑) — 승인되면 데모 스텝으로.
4. `[신규 제안]` S6(반장 개정 승인) 여정 시연.
5. `[신규 제안]` 상충 `conflict_reason` 3분류 표시.

### A11.3 다음 단계로 미룰 것 (DEFER)

1. 공정 본체(산세·압연·소둔) 설비 추가 — 승인 #1 확대이며 도메인 검증 부담이 급증.
2. 설비 개조 이력 모델링(`modification_history` 상충의 근본 해소).
3. 개정 후보 자동 탐지 배치·알림, diff UI, 절 단위 병합.
4. 개정이 카드에 미치는 영향 자동 전파.
5. S7(엔지니어 분석 대시보드), S9(복구 전용 여정) 전용 화면.
6. 역할별 인증·권한 강제 — `[기존 4.12]` MVP 미구현 유지.
7. 실제 제조사 문서 적재, 실제 현장 데이터 시드 교체.
8. 관계 3홉 이상 탐색, 그래프 DB.

### A11.4 MVP 제외 목록 — 기존 보존 + 추가

`[기존 3.1 보존]`: PLC·안전장치·설비 직접 제어 / 검증되지 않은 자동 파라미터 변경 / 안전·품질·수리의 최종 판정 대행 / 실제 MES·CMMS의 확정 상태 자동 변경 / 예지보전, 음성·OCR·3D, 다중 단말 실시간 동기화 / 상용 현장 성능이나 다운타임 절감 효과의 단정.

`[신규 제안]` 추가 제외 항목:
