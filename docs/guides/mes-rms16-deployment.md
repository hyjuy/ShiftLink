# RMS16 candidate rollout and rollback

This guide describes the approved conditional rollout. It does not state that deployment has happened. See the final qualification/deployment report for actual status.

The separate deploy/analytics/normal-profile-rms16.json changes only seven RMS confirmation windows from eight to sixteen valid consecutive running measurements. Keep the original profile and r6 source. This suppresses short quantized plateaus; it adds up to eight seconds to in-range freeze confirmation (seven to fifteen seconds from first frozen frame). A healthy sixteen-frame plateau can still be ambiguous. No Timestral runtime or neural retraining is added.

All tests execute on Raspberry Pi. Require sealed fresh holdout, paired r6 comparison, zero missed process/persistent-freeze episodes, zero false/duplicate notices, real 1Hz worker/reader/alarm DOM checks, source delivery checks and valid current services before activation. Pi loopback timing must be labeled separately from actual Jetson→Pi timing. Preserve all consumed data and failed checks.

The optional MES progressive mode requires the three mode files plus the cursor-bound storage.py. The latter prevents replay from decoding all accumulated snapshots; full history, run/sequence/time boundaries and existing alarm data stay intact. The expected operating source hashes must match the captured originals. Back up files, original effective unit and a consistent SQLite backup before replacing code. Do not clear alarms or existing confirmed advisories to satisfy a deployment gate. If either exists, keep the deployment pending.

Pi target is a separate rms16-active-advisory-20261024-r7 release and /var/lib/shiftlink-analytics-rms16-v1 state. The rms16.service.in template keeps the shared /var/lib/shiftlink-analytics/STOP switch. Existing r6 release/profile/state and the actual PDA files are retained. No PDA restart is needed when its bytes are unchanged.

Before changing the worker unit, validate its rendered unit with systemd-analyze verify. Stop only the analysis worker, save the final old checkpoint and existing unit, validate the old binding using the old source, assert that the only profile differences are the seven RMS windows, and copy the checkpoint to the separate state directory with the new fingerprint. Validate the copied checkpoint with the candidate source before starting it. Preserve cursor, confirmed event IDs, stopped notices and episode state. Existing confirmed notices are retained until observed recovery, including those confirmed under the old eight-frame rule; deployment never silently deletes them. A migration rehearsal must pass first.

Install the new worker unit and daemon-reload/start it. Confirm ready status, correct profile hash/path, no restarts or model_error, same PDA PID/files, and unchanged source/alarm identities. If readiness fails, restore the saved unit, daemon-reload and restart the original worker with its untouched old state. Do not remove STOP to force startup.

For Jetson, use an opt-in systemd drop-in that adds --progressive-faults to the original ExecStart and preserves all other environment drop-ins, port, database and services. A MES restart creates a new simulation run; previous run history stays in SQLite. Only activate with no existing alarm/advisory and restore the previous running/stopped mode through its normal control API. Do not describe this restart as preserving the same in-memory simulation run. Save a rollback copy of the prior unit/drop-ins and exact modified source files. Rollback restores those files and removes only the new progressive-mode drop-in, then reloads/restarts the MES; it never restores a whole old database over newer records.

After applying, check the real Pi PDA /api/state, same-equipment merged alarm row, unchanged acknowledgement/haptic behavior, one-second source frames, replay cursor continuity, latency distribution and service resources. A later naturally generated fault may be observed; do not manually clear or repair it merely to improve metrics. The progressive-mode repair API is documented in mes-progressive-faults.md.

Actual activation completed on 2026-10-25 after all gates passed. See [verified deployment and exact backups](../testing/mes-rms16-deployment-20261025.md); the r6 release/profile/journal and all actual PDA files remain intact.
