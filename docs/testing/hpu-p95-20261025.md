# HPU p95 구간 분석과 decode·임시 뷰 수명 개선

기준 커밋 `39a96aa27fec096195d1905be374527c7834ae23`과 최종 구현 `8d2d18c`를 비교한다.
모델 학습·운영 배포·서비스 재시작·모델 다운로드·운영 DB/KB/인덱스 변경은 하지 않았다.
HPU 관계 검색은 기본 off이며 기존 질의에 새 훅을 연결하지 않는다.
이전 [이력 검색 개선](hpu-retrieval-recheck-20261025.md)의 질문·라벨·모델·인덱스를 유지한다.

## 측정 경계

대표 16질문×2회와 기존 탐색 4질문×2회를 별도로 집계한다.
각 버전에서 관계 off 기준 경로와 관계 실험 경로를 교차 순서로 실행한다.
기존 집계의 `baseline_total`은 **비교 하니스의 독립 뷰 복사 + 파이프라인 실행**이며,
실제 MES API의 종단 지연과 동일하지 않다. `baseline`은 복사 비용을 제외한 실행이다.
실험 total에는 기존대로 관계 준비·복사·실행·최종 게시 재검증 비용을 포함한다.
이전 수치를 더 유리한 다른 정의로 대체하지 않고 total과 run을 함께 보고한다.

`tests/hpu_retrieval_live.py:profile_requests`는 같은 HTTP 요청과 응답 바이트를 유지하며
Ollama의 load/prompt_eval/eval 시간·토큰 수와 클라이언트 wall 시간을 수집한다.
`RecordingPipeline.evidence`는 임베딩을 포함한 검색 시간을 별도로 기록한다.
판정 호출은 병렬이므로 개별 wall 시간의 합을 직렬 임계 경로 시간으로 해석하지 않는다.
계측은 opt-in 하니스에만 있으며 운영 응답 형식·원문을 바꾸지 않는다.

자료는 실제 ck176·embeddinggemma·SFT judge를 호출한 **합성 검수 일지 한 장**이다.
운영 실측 일지 분포나 PDA 종단 성능을 대표하지 않는다.

## 확인한 원인

- 현재 질문의 답변 생성이 가장 크다. 수정 전 `foam-noise` 0회 기준 total 10.157초,
  검색 0.813초, 답변 생성 7.035초였다. 생성 내부 입력 처리 2.020초,
  autoregressive decode 4.941초(137토큰)이며 모델 로딩은 약 8ms였다.
- 다른 `current-restart`는 검색 0.610초, 생성 5.180초이며 decode만 4.158초(109토큰)였다.
  빠른 재호출의 입력 처리 40ms와 처음 바뀐 근거의 입력 처리 0.9~2초 차이도 있다.
  매뉴얼/관찰/답변을 삭제하지 않으면 이 생성 비용이 남는다.
- judge는 후보마다 JSON 7토큰을 끝까지 생성했으나 실제 사용 정보는 그 이전의 점수 확률이다.
  여러 후보를 판정하는 비용이 생성 앞에 추가된다.
- 가장 긴 수정 전 `foam-noise` 1회는 total 14.225초 중 독립 뷰 복사가 5.465초였다.
  실제 파이프라인 실행은 8.760초다. 실험의 `trial.evidence` 클로저가 `trial`을 다시 참조하여
  복사된 rows/cards/vectors가 순환 GC 전까지 남는 문제를 재현했다.
  이 한 번의 5.465초 정체를 전부 GC 시간이라고 단정하지는 않는다.
  일반 서비스는 이 실험의 `_view` 복사/클로저를 사용하지 않으므로 서비스 병목과 구분한다.

## 적용한 최소 수정

1. `evidence_score.py:judge_dist`: 확인한 `exaone-sft-judge` 이름/alias에만 첫 요청의
   `num_predict`를 20에서 6으로 줄인다. 입력 메시지·JSON schema·모델·temperature·context·
   logprobs·임계값은 유지한다. 점수가 없으면 20으로 다시 확인하며 끝내 없으면 기존처럼 None/보류다.
   점수가 포함된 내부 JSON이 닫히지 않아도 외부 Ollama JSON과 logprobs는 정상이며,
   내부 부분 JSON을 답변으로 파싱하거나 점수를 추정하지 않는다. 다른 모델은 기존 20을 유지한다.
2. `hpu_retrieval_experiment.py:run_experiment`: `finally`에서 임시 evidence override를
   제거하거나 이전 override로 복구한다. 성공·오류·invalidated 종료에서 인덱스 사본을 GC에 맡겨 붙잡지 않는다.
   독립 복사·게시 재검증·후보 예산·원문 보호는 유지한다.
3. 추가로 각 경로의 독립 복사·실행·해제를 하나의 수명 범위로 묶어 baseline/trial 사본이
   동시에 살아 있지 않게 한다. 딥 카피를 공유하거나 생략하지 않는다.
   초기화·결과 변환·해제 등 나머지 시간을 `baseline_overhead`/`trial_overhead`로 노출하고
   total에 더한다. 파이프라인 실행 구간은 기존대로 별도다.
   이전 total이 준비+실행이었다면 최종 total은 이에 정리 overhead까지 포함하므로 더 보수적인 비용 집계다.

답변 모델의 토큰 상한을 잘라 필요한 절차가 빠지게 하거나, 판정을 생략하거나,
답변/판정 캐시로 반복 질문을 실제 추론 성공처럼 세지 않는다.

## 탐색했으나 적용하지 않은 방법

- JSON 점수 prefix를 강제로 넣고 1토큰만 생성하면 빨랐으나 기존 확률이 달라졌다.
  예를 들어 `pressure-zero`/`card_K-1203`의 P(>=2)가 약 0.9195→0.8829로 바뀌어
  단독 HI=0.9 경계를 넘었다. 이 탐색을 기존 판정 보존으로 간주하지 않고 배제했다.
- judge worker 2/4 비교는 같은 현재 질문 3종×2회에서 이득이 작거나 역전됐다.
  요청 동시 수를 늘리는 변경은 채택하지 않았다.
- judge 예산만 바꾼 중간본도 별도로 보존한다. 그 버전의 대표 total p95는
  **12.393초**, 수정 전 10.157초보다 나빴다. 모델/호스트/로컬 준비 지연 변동을
  제거한 성공으로 간주하지 않고 최종 수명 수정과 구분한다.
- 출력 없는 prefix prefill도 API에서 시험했으나 `num_predict=0` 요청에 실제 31토큰이 생성됐다.
  이 런타임에서 무출력 작업으로 확인되지 않아 동시 prefill 코드는 추가하지 않았다.

## 한계와 후속 범위

고정 질문·2회 반복만으로 p95의 작은 차이를 유의한 성능 개선이라고 판정할 수 없다.
별도 군의 p95들을 더해 전체 p95로 만들지도 않는다.
모델·통신·PC 부하·프롬프트 캐시·생성 길이는 실행 간 변동한다.
현재 답변 생성의 100개 이상 토큰과 근거 입력 처리가 남아 있어,
이 수정으로 일반 질의 전체가 수 초 이내에 끝난다는 보장은 없다.
실제 설비 질문·여러 검수 일지·동시 부하·Jetson 서버 자체/API/PDA 구간의 후속 측정이 필요하다.
