# 근무일지와 지식카드 후보 연결 하네스

2026-10-16 기준. 기존 PDA 근무일지의 `고장·정비`, `story`, `causes`, `result`, `candidate`와 기존 `/api/work-reports` 저장 경로를 사용한다. 고장 기록에 서버 질문 ID를 연결하면 당시 검색 결과와 관측 근거를 확인해 검토 대기 카드를 만든다. 별도 근무일지 양식이나 모델 학습은 추가하지 않는다.

[앞 단계인 사건 연결](work-report-incidents-20261016.md)을 기반으로 구현했다. 브랜치는 `feat/work-report-card-candidates-20261016`이다.

## 현재 동작

1. 기존 `POST /api/query`가 서버 질문 ID `query_id`, 검색 상태 `knowledge_status`, 질의 당시 설정·자산 정보를 반환하고 DB에 보존한다.
2. 기존 근무일지의 개별 고장 기록에 `query_id`를 넣어 저장한다. 기존 사건을 이어 쓰면 기록에 `incident_id`도 명시한다.
3. 고장 기록에 `candidate=true`가 있고, 연결한 질문이 `no_applicable_card`이며 질의 당시 설정·자산이 유효하면 카드 후보를 생성한다.
4. 일지·사건·질문 연결·카드 후보·처리 결과를 한 트랜잭션으로 저장한다. 재전송은 같은 결과를 반환한다.
5. 기존 `/api/card-drafts`에서 후보를 읽을 수 있다. 일지 상세·목록의 `candidates`, 사건 상세의 `queries`와 `candidates`로 원본을 추적할 수 있다.

현재 PDA는 새 질문 ID를 근무일지 기록에 자동으로 붙이지 않는다. 이번 단계는 서버 연결이며, 다음 화면 작업에서 이 연결을 제공한다. 질문 ID가 없는 기존 요청도 일지는 저장하고 `missing_query`를 반환한다.

## 기존 필드에 대한 처리

| 원본 항목 | 후보에서의 처리 |
| --- | --- |
| `story` 상황·조치 | 원문을 `know_how`에 보존하며, 실행 단계로 임의 분해하지 않음 |
| `causes` 원인·설비·확실성 | `reported_causes`에 추정·확인·배제 그대로 보존 |
| `result` 결과·후속·인계 | `worker_result_text`에 보존하며 해결 성공으로 자동 분류하지 않음 |
| `candidate` 후보 체크 | 검토 제안이며 승인·승격 또는 MES 검증을 뜻하지 않음 |
| 질의 당시 관측 | 서버에 저장된 근거로 이상 조건을 계산하며 일지가 보낸 센서값은 사용하지 않음 |

자유 입력 결과가 ‘정상’, ‘효과 없음’, ‘임시 조치’이거나 미기재여도 자동으로 검증된 성공을 만들지 않는다. 후보의 해결 상태는 `unconfirmed`, MES 검증 성공은 0건이며 `ready=false`다. 결과 미기재, 원문에서 재사용 절차 분리, 해결 여부 확인, 적용 시나리오 확인을 보완 항목으로 남긴다. 미정 단계는 검토 전 표시로만 넣는다.

카드 자체는 `draft/L0/dev`, 후보 행은 스키마 검증을 통과하면 `pending_review`다. 기본 KB 로더에 포함하지 않는다. 기존 조치 세션의 자동 후보 병합 대상에서도 원문 후보를 제외한다. 같은 원인인지 확인하지 않고 원문과 정리된 조치 단계를 섞지 않기 위해서다.

## API 사용

기존 질문 요청을 사용하고 응답의 실제 `query_id`를 받는다. 기존 사건에서 질문할 때만 선택적으로 `incident_id`를 추가한다. 이 ID들은 LLM의 `QueryRequest` 입력으로 보내지 않는다.

근무일지 전체 요청은 기존 형식을 유지하고 `work_report.records`의 해당 기록에 연결 ID만 추가한다.

```json
{
  "type": "고장·정비",
  "equipment": ["EQ-0004"],
  "story": "필터를 점검하고 청소했습니다",
  "causes": [{"equipment": ["EQ-0004"], "certainty": "추정", "note": "필터 오염 가능성"}],
  "result": "작업자 확인: 정상 운전",
  "pms": null,
  "candidate": true,
  "query_id": "Q-서버가반환한실제ID"
}
```

저장 응답의 `candidates`에는 `handover_id`, `record_index`, `incident_id`, `query_id`, `draft_id`, `reason`이 담긴다. 새로운 필수 조치 입력 객체는 요구하지 않는다.

| `reason` | 의미 |
| --- | --- |
| `pending_review` | 원문 후보 생성, 검토 필요 |
| `not_requested` | 후보 체크 안 함 |
| `missing_query` | 질문 연결 없음, 일지는 저장 |
| `query_not_knowledge_gap` | 답변 완료·보류·조건 미확인·상태 불명으로 지식 공백 후보 생성 제외 |
| `query_configuration_changed` | 질의 이후 설정 변경, 과거 값의 조건 해석을 다시 확인해야 함 |
| `invalid` | 카드 스키마 검증 실패, 후보 검토 보완 필요 |

존재하지 않는 질문·사건, 다른 대상 설비·교체된 자산, 다른 사건에 속한 질문 연결은 400으로 거절한다. 같은 일지 ID의 다른 본문은 기존 409 처리를 유지한다. 내부 카드 참조는 외부 인계 ID와 충돌하지 않는 별도 범위를 사용한다.

## 하네스 실행과 검증 근거

```powershell
python scripts/check_work_report_reuse.py --coverage
```

기존 `.test-deps`가 있으면 사용하며 의존성을 설치하지 않는다. `--coverage`를 생략하면 pytest로 같은 검사를 실행한다. 테스트 데이터는 임시 SQLite와 로컬 HTTP 서버에서만 사용한다.

- [고정 시나리오 입력과 기대 결과](../../tests/fixtures/work_report_reuse_cases.json): 12개 시나리오.
- [하네스 테스트](../../tests/test_work_report_reuse_harness.py): 기존 일지 필드, 질문 ID·검색 상태, 원문 보존, 검증 성공 오인 방지, 재시작, 동시 재전송, 오류 주입, ID 충돌, KB 미반영 확인.
- [반복 실행 스크립트](../../scripts/check_work_report_reuse.py): 하네스와 기존 근무일지·검색·저장·현장 초안·승격·판정기 장애·KB 로더 계약을 함께 검증.
- 결과: `artifacts/work-report-reuse-harness/latest.json`, 실행별 JUnit XML과 `coverage.json`. JSON에는 fixture SHA256, 시나리오, 개별 테스트 상태와 종료 코드가 남는다.

| 단계 | 실제 확인 |
| --- | --- |
| 최초 RED | 질문 ID·후보 연결 부재로 하네스 18개 실패, 체크포인트 `de02051` |
| 기존 양식 반영 RED | 새 조치 양식 없이 후보 제안하는 2개 검사 실패, 17개 통과, 체크포인트 `7702ae6` |
| ID 충돌 RED | 기존 인계 ID와 내부 참조가 겹치면 후보 생성이 누락되는 검사 실패, 체크포인트 `1fdaf32` |
| 최종 GREEN | 전체 하네스 및 연결된 회귀 검사 136개 통과, 67.89초 |
| 변경 코드 실행 확인 | 새 서버 실행문 107개 중 107개 실행. 전체 프로젝트·전체 분기 커버리지 수치가 아님 |

실행 시간은 테스트 묶음의 소요 시간이며 실제 질의 응답 지연이나 장비 성능 측정값이 아니다. 실제 근무일지·운영 DB·LLM·Jetson·PDA 장비를 사용한 검증은 아니다.

## 다음 단계

1. 기존 PDA에서 질문 ID를 해당 고장 기록에 자동 연결하고, 사건 선택과 후보 생성·보완 결과를 표시한다.
2. 검토 화면에서 원문과 근거를 읽고 해결 여부·적용 조건·재사용 조치 단계를 확정한다. 기존 시연용 승격 스크립트의 `--force`는 정식 검토를 대체하지 않는다.
3. 승인·배포 후 새 질문에서 카드가 검색되는 전체 흐름을 검증한다.
4. 사건·후보 연결의 중앙 DB 동기화를 연결한다. 현재 서버 생성 연결은 로컬 SQLite에 있으며 기존 일지 업로드 본문은 유지한다.

기존에 수정 중인 PDA HTML·JavaScript와 `output/`은 이번 작업에서 변경하거나 커밋하지 않는다. 실제 장비 배포와 공개 시각화 사이트 갱신도 포함하지 않는다.
