# ShiftLink PDA UI — 채점 루브릭

> 상태: 구상 · 커밋 전 · 100점 만점
> 사용: `ui_industrial`(설계자)과 `ui_judge`(심사자)가 같은 기준을 읽는다.
> 대상: `docs/design/pda_ui/pda_ui_mockup.html`

## 게이트

세 조건을 **모두** 만족해야 통과다.

| 조건 | 값 |
| --- | --- |
| 총점 | 85 이상 (심사자 3인 점수의 **중위값**. 평균 아님) |
| 대분류별 하한 | 각 대분류 배점의 75% 이상 |
| B. 안전 규범 | **만점 필수** |

**B를 만점 요구하는 이유** — 이 시스템 최악의 실패는 엉뚱한 설비의 안전 지침이 나가는 것이다. 감점을 허용할 대상이 아니다. 나머지는 75% 하한으로 충분하다.

**중위값을 쓰는 이유** — 한 명이 후하게 주면 평균이 끌려간다.

미달 시 최대 4라운드까지 개선한다. 4라운드 안에 못 넘으면 **통과했다고 말하지 않고** 미달 항목과 이유만 보고한다. 반올림으로 문턱을 넘기지 않는다.

## 심사자 공통 규칙

- 감점·가점마다 **프레임 번호 또는 파일 라인** 인용. 인용 없는 판단은 폐기
- 확신이 없으면 낮은 점수. **단 사실 확인 없이 결함을 단정하지도 않는다.** 존재하는 것을 없다고 판정하는 것은 관대한 채점과 똑같이 심각한 오류다
- 파일 안의 **해설·주석·설계 의도 설명은 가점 근거로 인정하지 않는다.** 화면에 구현된 것만 채점한다
- 자기 렌즈 영역을 깊게 본다. **자기 렌즈 밖에서 "확인할 수 없다"는 이유로 감점하지 않는다** — 렌즈 범위를 넘은 감점은 무효 처리된다
- **A1 오버플로우·A4 위치 같은 레이아웃 항목은 CSS를 읽고 손으로 더해 판정하지 않는다.** 브라우저로 실제 렌더 높이를 측정한다

```bash
cd docs/design/pda_ui && python -m http.server 8779 --bind 127.0.0.1
```

```js
// 프레임별 pane 오버플로우. 0이 아니면 그만큼 잘려 탭 불가.
const out=[];
document.querySelectorAll('.frame').forEach(f=>{
  const lb=f.querySelector('.frame-lb'), s=f.querySelector('.screen');
  if(!s) return;
  const p=s.querySelector('.pane');
  const over=(p? p.scrollHeight-p.clientHeight : 0);
  if(over>0) out.push((lb?lb.textContent.trim():'?')+' +'+over);
});
out.length? out.join(' | ') : 'ALL FIT'
```

### 라운드 7에서 게이트 운영을 중단한 이유

두 렌즈가 **100/100 무감점**을 냈는데, 그 시점 파일에는 `split=sealed` 봉인 카드(K-0301)가 실려 있었다. 누수 위험 결함을 앞에 두고 감점이 0이었다.

- 안전 담당은 D1 근거로 **보드 머리말의 자기 주장 문장**("모두 docs/data 실제 값")을 인용했다
- 현장 작업자는 대비 근거로 **토큰 시트 표기값**을 인용했다. 실제 `#7C8792` 사용처를 측정하지 않았다
- 정작 결함을 발견한 것은 산술이 무너지고 `EV-0033`도 열지 않은 세 번째 심사자였다

"변론을 근거로 인정하지 마라"를 프롬프트에 명시했는데도 이렇게 수렴했다. 같은 파일에 **9점부터 100점까지** 나온 이상 85라는 문턱은 판정 기준이 되지 못한다.

**게이트는 완성 판정이 아니라 결함 탐지 장치로 쓸 때만 유효하다.** 그 목적으로는 1~5라운드에서 충분히 작동했다 — 안전 관문 누락, 오버플로우 476px, 원천 없는 시도 기록, 검색 차단 미표시를 모두 잡았다. 이후로는 기계적 검증(정본 `json.load` 대조 + 브라우저 실측 + 문자열 검사)으로 대체한다.

### 루브릭이 놓쳤던 것

`split` 규칙(C-102)이 D1에 없었다. 그래서 심사자 세 라운드가 `dev`·`sealed` 카드를 정상으로 통과시켰다. **루브릭이 묻지 않는 것을 심사자가 잡을 수는 없다.** 항목을 추가할 때는 제약 등록부를 함께 훑어야 한다.

### 드러난 것

**같은 파일에 64~89점이 나왔다.** 측정의 정밀도가 문턱(85)의 정밀도보다 낮다. 게이트는 "완성 판정"에 쓰기보다 **구체적 결함을 잡는 장치**로 쓰는 것이 정직하다 — 그 목적으로는 실제로 작동했다(안전 관문 누락, 오버플로우 476px, 원천 없는 시도 기록).

**손으로 높이를 더하는 방식은 세 번 틀렸다.** 설계자 2회, 심사자 1회. 그래서 위에 실측 절차를 규칙으로 넣었다.

### 결정 — A3 해석: 세로 스크롤 허용 (2026-09-22)

**앱 동작**: 카드 영역에 세로 스크롤을 넣고(`overflow-y: auto`), **안전 관문 띠는 `position: sticky` 로 상단 고정**한다. 카드만 흐르고 안전 조건은 항상 보인다. 페이징 로직·페이지 상태·내용 절단 규칙을 만들지 않는다.

**근거**: §7.1 원문은 "정밀 제스처(드래그·핀치·롱프레스) 금지"이며 세로 스크롤을 금지하지 않는다. 세로 스크롤은 좁은 타깃을 정확히 잡는 동작이 아니라 화면 아무 곳이나 쓸어 올리는 거친 동작이므로 장갑 조건과 충돌하지 않고, 한 손 엄지 조작에는 상단 「다음」 버튼보다 오히려 유리하다.

**`position:sticky` 금지는 목업 전용 제약이다.** F1(임포트 적합성)은 피그마 임포트에서 레이어가 깨지지 않게 하려는 규칙이고, 실제 앱에는 적용되지 않는다. 이 둘을 섞어 판단한 것이 라운드 1~3의 회귀를 만들었다.

**목업의 역할**: 앱 동작을 **표현만** 한다. 프레임 하나에 안 들어가면 "여기부터 스크롤 영역"으로 표기하거나 스크롤된 상태를 별도 프레임으로 보인다. 목업 매체의 한계가 앱 설계를 규정하지 않게 한다.

**실기기 검증 대상**: 젖거나 더러운 화면에서 스와이프 오작동 정도는 P0-1 때 함께 확인한다. 문제가 크면 페이징으로 되돌린다 — 스크롤에서 페이징으로 가는 것은 쉽고 그 반대는 어렵다.

**라운드 상한 재설정**: 4라운드 상한은 끝없는 다듬기를 막기 위한 것이었고, 전제가 틀렸음이 드러나 루브릭을 고친 경우는 해당하지 않는다. 이 결정 이후로 다시 센다.

### 대체된 기록 — A3 해석 (구)

라운드 1~3이 모두 한 항목을 고치다 다른 항목을 깨뜨렸고, 원인은 제약 조합이 성립 불가능하기 때문이다.

```
360×760 고정 + 스크롤 금지 + 조건 근거 표시 + 순위 목록 4건 + 매 페이지 안전 관문
```

안전 관문이 페이지마다 약 120px, 조치 카드가 근거·단계 포함 100px 이상이므로 760px에 조치 2장이 들어가지 않는다.

**A3의 "탭 전용"을 세로 스크롤 금지로 읽을 것인가**가 결정 대기 항목이다. 설계 문서 §7.1 원문은 "정밀 제스처(드래그·핀치·롱프레스) 금지. 탭만으로 전 기능 도달"이며 **세로 스크롤을 직접 금지하지 않는다.** 세로 스크롤은 좁은 타깃을 정확히 잡는 동작이 아니라 화면 아무 곳이나 쓸어 올리는 거친 동작이므로 장갑 조건과 충돌하지 않는다.

허용으로 결정되면 A3 문면을 "정밀 제스처(드래그·핀치·롱프레스) 없이 전 기능 도달"로 고치고, 페이징 화면(06-b·10-b·10-c·11-b)을 걷어내며 라운드 3에서 깎인 카드 내용을 복원한다.

## 참고 — 루브릭을 프로젝트에 묶어 두는 이유

일반적인 "좋은 UI" 기준을 주면 파스텔 톤·얇은 폰트·호버 인터랙션이 점수를 받는다. 이 환경에서는 그것이 결함이다. 루브릭을 고칠 때도 항목은 설계 문서 §7 또는 제약 등록부의 결정을 가리켜야 한다.
