# PDA 대시보드 분석 — 지표 정의·데이터·시연 (2026-10-14)

PDA 화면에는 제목·숫자·근거 사건만 둔다. 계산 근거, 데이터 출처, 합성 데이터라는 사실은 이 문서와 발표 자료에서 설명한다.

## 1. 화면이 답하는 질문

| 화면 칸 | 질문 | 누르면 |
|---|---|---|
| 정지 손실 · 이번 주 | 이번 주 어느 설비 때문에 코일을 가장 많이 못 만들었나? (위: 생산 N개 · 손실 M개) | 그 설비의 사건 목록 |
| 반복 증상 · 4주 | 같은 문제가 왜 반복되나? | 그 증상의 사건 목록 |
| 조치 효과 · 4주 | 어떤 조치가 효과 있었고, 얼마 뒤 재발했나? | 그 조치를 한 사건 목록 |
| 지식 공백 · 누적 | 카드에 없던 노하우가 현장 기록으로 얼마나 모이고 있나? | — |

배치(1280×800, 10/15 다듬음): 위 상태 한 줄(라인 상태 + 확인 필요 설비·후속 대기 설비·제품 보류 코일 — 0이면 조용한 칩, 0이 아니면 그 칩만 빨강/앰버), 아래 3열 — 정지 손실·반복 증상(위) / 지식 공백(아래 두 열), 오른쪽 열 전체는 조치 효과. 칸 안의 행은 상자 대신 가는 구분선 목록, 재발한 조치는 왼쪽 빨간 표지 + 빨간 재발 수, 정지 손실은 범례 없이 설비 줄의 색 표지가 범례, 지식 공백은 상자 없는 숫자 흐름(→).

**대응 시간(탐색·조치 시간, 도입 전·후 비교)과 인계 미완료 항목은 대시보드에 두지 않는다**(10/15 팀 합의). 저장 이력의 `action_at`·`_meta.adopted_at`은 남아 있지만 계산에 쓰지 않는다.

**지식 공백은 합성 이력을 쓰지 않는다.** 이 MES DB에 쌓인 실제 기록만 센다(`analytics.knowledge_gap`):

| 칸 | 데이터 |
|---|---|
| 지식 없음 | `query_log`의 PDA 질의 중 `no_knowledge = true` (기존 카드 묶음 86장으로 답하지 못한 질문) |
| 카드 초안 | `card_drafts` 전부 — "해당 지식 없음"에서 시작한 조치 기록을 인계와 함께 저장하면 생김(K-7000~) |
| 검수 대기 | 그중 `pending_review`이고 아직 카드 묶음에 없는 것 |
| 승인 | 초안의 카드 ID가 `kb_cards.json`에 들어간 것(`scripts/field_card_promote.py promote`). 승격 도구는 초안 상태를 바꾸지 않으므로 카드 묶음으로 판정 |

그래서 시연 시작 때는 0이고, 시연 대본(지식 없음 → 조치 기록 → 저장 → 승인)을 따라가면 눈앞에서 늘어난다. 기간 필터는 두지 않는다(질의 시각은 실제 시계, 대시보드는 모의 MES 시각이라 섞이지 않게). 시연 전 Jetson 테스트 데이터를 비우는 준비 단계가 그대로 "누적 0에서 시작"이 된다.

사건 목록의 각 항목은 시각·설비·경보·결과(재발/관찰 중/재발 없음/조치 중)·정지 시간·후속 대기 설비 수·조치·원인·인계 ID·지식 카드를 보여 준다.

### 1.1 홈 화면 「현재 설비 상황」 카드 (10/15)

홈은 작업자가 이번 교대에 바로 쓸 정보만 둔다: **지금 이상**과 **다시 날 수 있는 것(지켜볼 설비)**. 효과 비교(카드 방법 대 카드 밖, 도입 전·후 탐색 시간)는 홈에 두지 않고 상세 대시보드와 발표 자료에서 보인다(10/15 검토: 홈에 효과 비교를 두면 작업자에게 인위적).

| 자리 | 내용 | 누르면 |
|---|---|---|
| 머리글 오른쪽 | 정상 N · 이상 감지 N(1 이상이면 빨강). 왼쪽 인계 카드의 "확인 0 / 전체 3"과 같은 꼴 | — |
| 이상 설비 | 이상이 있을 때만 한 줄씩(없으면 칸이 사라짐) | 그 설비 변경 확인 |
| 지켜볼 설비 | 최대 3줄, 설비·증상당 한 줄. ① '해결'로 닫았는데도 반복된 증상 — "4주 N회" + 「원인 미확인」(마지막 조치가 재발 기간을 넘겨 버텼으면 뺌) ② 최근 조치해 아직 재발 기간(7일) 안인 증상 — "N일 전 조치", 최근 것 먼저 | 그 증상의 지난 조치 목록(무엇을 했고 재발했는지). 「이전」은 홈으로 |

작업자에게 주는 것: 이번 교대에 다시 날 수 있는 설비를 미리 알고, 나면 지난번에 무엇을 했는지 한 번에 본다. 합성 이력 기준: CV-01 출측 코일 정체 4주 8회(원인 미확인) · GR-02 감속기 누유(1일 전 조치) · CAU-01 공압 공급 저하(2일 전 조치). PDP-01은 해결 후 재발이 있었지만 마지막 조치(K-1317)가 재발 기간을 넘겨 버텨서 빠진다. 이상이 하나 있어도 1280×800에서 세 줄이 스크롤 없이 들어간다(줄 높이 44px).

## 2. 데이터: 사건 하나

```
사건 = 경보(alarm_at) → 조치 시작(action_at) → 복구(recovered_at)
       + 설비 · 경보 코드 · 조치 · 원인 · 결과(해결/임시 조치/실패) · 인계 ID · 지식 카드 ID
```

| 출처 | 저장 이력 (`docs/data/analytics/line_history.json`) | 지금 실행 (시연 중) |
|---|---|---|
| 경보·복구 | 기록값 | MES 이벤트 `alarm_raised` → 같은 설비·같은 경보의 `alarm_cleared` |
| 조치 시작 | 기록값 | 그 설비 조치 기록 세션의 첫 조치 완료 시각(경보 뒤, 복구 전) |
| 조치·원인·결과 | 기록값 | 세션 첫 조치 + 세션과 함께 저장한 인계의 `resolution` |
| 지식 카드 | 기록값 | 조치 기록을 시작한 답에서 본 첫 카드(세션 `card_ids`) |
| 카드 방법 여부 | 카드 ID가 있으면 카드 방법 | 조치 기록에서 **카드 단계 칩**으로 완료한 조치가 하나라도 있음(조치마다 `card_step` = 카드·단계 ID) |
| 센서 변화 없이 닫음 | 없음(단계별 센서 결과가 없다) | 세션의 모든 조치 결과가 '센서값 변화 없음' |

카드 단계 칩: 답이 근거로 쓴 카드의 단계가 조치 기록 칩 줄 맨 앞에 나온다(칩 글자는 단계 첫 문장, 40자 넘으면 자름). 단계가 없는 카드는 "K-xxxx 방법대로" 칩 하나. 서버는 그 세션에서 본 카드의 단계만 받고, 위험 여부(잠금 응답)는 칩 글자가 아니라 단계 원문으로 판정한다. 카드를 봤어도 칩을 쓰지 않고 직접 입력만 했으면 카드 밖 방법이다.

조치 기록은 카드 답에서도 시작할 수 있다. 카드를 본 세션은 그 카드의 효과 기록으로만 남고, 새 카드 초안을 만들지 않는다(인계 저장 응답 `draft.reason = card_used`). 카드가 없는 답("해당 지식 없음")에서 시작한 세션만 카드 초안 경로로 간다.

두 출처를 같은 형식으로 합쳐 같은 함수(`shiftlink/mes/analytics.py`의 `summary`)로 계산한다. 저장 이력은 끝 시각(`_meta.end`)을 MES 실행 시작 시각에 맞춰 옮겨 쓰므로 언제 시연해도 "지난 4주"로 보인다.

**회사에 붙일 때 필요한 입력**: 설비 경보 기록(발생·해제), 조치 기록(시작 시각·조치·원인·결과), 설비 간 관계(구동·유압·공압·전원·인터록). 이 세 가지가 있으면 같은 계산이 돈다.

## 3. 지표 정의

| 지표 | 정의 | 제외·한계 |
|---|---|---|
| 정지 시간 | 경보 → 복구(복구 전이면 지금까지) | 증상 패턴 알림(`AL-SYMPTOM`)은 설비를 세우지 않아 제외 |
| 라인 정지 | 원인 설비가 라인 경로(RT-01→RT-02→RT-03→CV-01)이거나, 구동·유압·공압·전원·인터록 관계를 여러 단계 따라 경로 설비에 닿음 | 같은 시간으로 본다(전달 지연 무시) |
| 정지 손실(개) | 이번 주(지금부터 7일) 라인을 세운 정지 시간 × 표준 생산 속도(시간당 10.7개). 직렬 라인이라 대기 설비 수는 곱하지 않는다 | 근거·한계: `coil_loss_basis_20261015.md`. 감속 손실·겹치는 정지는 반영하지 않음 |
| 이번 주 생산 | 계획(주 168 h × 10.7 ≈ 1,800개) − 손실 | 계획 정지·소재 부족은 사건이 아니므로 들어가지 않음 |
| 재발 | 복구 뒤 **7일 안에** 같은 설비·같은 경보가 다시 발생 | 판정은 계산으로만(이력에 재발 여부를 저장하지 않음) |
| 관찰 중 | 복구 뒤 아직 7일이 지나지 않았고 재발도 없음 | "재발 없음"으로 세지 않는다 |
| 반복 증상 | 4주 안에 같은 설비·같은 경보 2회 이상. 원인 분포·임시 조치 건수를 함께 | — |
| 근본 원인 미확인 | 반복 증상 안에서 결과를 '해결'로 닫았는데 재발한 사건이 1건 이상. 적힌 원인을 고쳐도 끝나지 않았다는 뜻 | 원인 문구는 비교하지 않는다(표현이 달라도 같은 판정). 임시 조치 뒤 재발은 세지 않는다 |
| MTBF·MTTR (정지 손실 줄) | 설비 단위·4주, 그 설비 고장 전부(증상 구분 없음). MTTR(평균 수리 시간) = 정지 시간 합 ÷ 고장 수, MTBF(평균 고장 간격) = (4주 672시간 − 정지 시간 합) ÷ 고장 수 | 팀이 뺀 '대응 시간(도입 전·후 탐색·조치 비교)'과 다르다 — 도입 효과 비교가 아니라 설비별 표준 신뢰성 지표. 이번 주 정지 손실이 있는 설비 줄에 "MTBF N시간 · MTTR N분 · 정지 N분"으로 붙는다. 계획 대비 %는 줄에서 빼고 위 요약·도넛에만 둔다 |
| 조치 효과 | 반복 증상 안에서 **카드 방법 / 카드 밖 방법**으로 나눠 각각 재발 건수/건수, 그 아래 조치별 건수·재발·평균 재발 간격 | 같은 증상 안에서만 비교. 관찰(인과 아님) — 카드를 본 사건이 쉬운 사건에 몰렸을 수 있다 |
| 센서 변화 없이 닫음 | 카드 밖 방법 중 모든 조치가 센서를 움직이지 못했는데 기록을 닫은 건수 | 엉뚱한 시도와 합리적이지만 안 된 시도를 가르는 객관 신호. 점검 단계는 원래 센서를 바꾸지 않으므로 조치 하나가 아니라 세션 전체로 본다 |

## 5. 시연 장면

1. 대시보드를 열어 칸을 질문 순서대로 읽는다. 정지 손실 "생산 1,749개 · 손실 51개", 1위 HPU-01 17개 → 눌러서 사건 2건(재발 1, 관찰 중 1).
2. MES에서 GR-01 감속기 과열을 일으키고, PDA에서 질의 → 조치 기록(조치 시작·완료·마무리) → 인계와 함께 저장.
3. 대시보드로 돌아오면(10초 이내 갱신) 반복 증상 GR-01이 6회가 된다. 정지 손실에도 GR-01이 들어오지만 시연 사건은 몇 분짜리라 4위 아래(칸 안에서 스크롤)다.
4. 지식 공백 칸을 채우는 장면은 별도 대본: `docs/testing/knowledge-gap-demo.md`(유압유 과열 — 공백 발견 → 초안 → 근거 → 승인 → 같은 질문에 현장 카드로 답).
