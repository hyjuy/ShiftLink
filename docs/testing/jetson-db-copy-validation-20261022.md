## 배포 전 온라인 백업

로컬에서 압축 전송 해시와 복구 DB 해시를 대조했다. 복구 사본만 main의 이행·게시 시험에 사용했고 보존본은 읽기 전용으로 유지했다. 로컬 Python 3.13에서 21개 테이블 수와 17개 주요 테이블의 내용 해시를 비교했다. 기존 후보 4개와 카드 86개는 보존됐으며 새 게시 테이블의 초기 행은 0개였다. 이 DB에는 이미 `work_report_candidates.kind`가 있어 그 열이 없는 구형 스키마 이행은 시험하지 않았다.

검토 승인과 검색 가능 상태의 분리, 검수 후 임베딩 대기, 실패·재시도, 게시 저장, 객체 재생성 후 상태 복원, 재검토 후 제외, 늦은 결과의 게시 방지를 사본에서 확인했다. 객체 재생성은 장비 서비스 재시작 시험이 아니다. 검증용 후보와 검수는 사본에만 만들었으며 실제 사람 검수 승인을 대신하지 않는다.

실제 Jetson embeddinggemma:300m 호출로 768차원 벡터를 저장하고 검색도 확인했다. 이 단계는 **빈 기준 인덱스 + 게시 delta**를 사용했다. 운영 색인에서의 경쟁 검색이나 최종 judge·답변 품질을 검증한 것으로 기록하지 않는다.

별도 롤백 복구 사본은 백업과 바이트 동일했고 원래 21개 테이블과 게시 테이블이 없는 상태를 복원했다. 운영 DB를 덮어쓰지 않았다.

## 실제 배포 때 새 백업으로 재검증

온라인 백업 이후 운영 쓰기가 있었으므로 이전 사본을 배포 백업으로 재사용하지 않았다. MES와 업로더를 정지한 뒤 `/home/jetson/shiftlink/backups/20261022-140849-main-7582378/database-before.sqlite3`를 새로 만들었다. 크기는 2,487,664,640 bytes, SHA-256은 `8df21eb10b38aeaaf86ed4cd4493008e13add763a78d370a060bf30872241247`이다.

Jetson Python 3.10.12와 실제 배포 코드로 새 복구 사본에 대해 **18개 검사**를 통과했다. 복원 바이트 동일성, 이행 후 원문·후보 보존, 자동 게시 없음, 실제 임베딩 저장, 재검토 시 제외·ticket 무효화, 무결성·외래키, 보존 백업 불변을 확인했다.

이번에는 운영 색인 **3,950행 × 768차원**을 읽기 전용으로 사용했다. 사본 게시 청크 2행을 합친 3,952행 검색 뷰에서 실제 질의 임베딩의 검색 결과 8개 내 게시 카드가 조회됐다. 기준 인덱스 파일을 수정하지 않았다. 운영 게시 테이블은 생성됐지만 0행이고, 기존 후보는 대기 3건·승인 1건이었다.

게시 카드의 최종 judge·생성 답변, 운영 후보의 양성 게시, 운영 DB에 대한 실제 복원은 검증하지 않았다. 새 업무 기록과 업로드가 재개된 이후 과거 백업을 그대로 복원하면 기록이 유실될 수 있으므로 [롤백 절차](jetson-main-deployment-preparation-20261022.md)의 데이터 대조 단계가 필요하다.
