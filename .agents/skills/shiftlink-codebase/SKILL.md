# ShiftLink 기능 이해

## 시작점

저장소 루트는 이 파일의 상위 `.agents`가 있는 폴더다. 명령은 루트에서 실행한다.
먼저 `docs/design/project-structure.md`와 적용되는 `AGENTS.md`를 읽는다.
이어서 `docs/design/feature-map.md`에서 요청한 기능의 행만 찾아 실제 코드를 연다.
기능 지도는 탐색 인덱스이며 코드나 현재 실행 결과를 대신하지 않는다.

## 근거를 확보하는 방법

1. `git rev-parse HEAD`, `git status --short`로 분석 기준을 확인한다. 필요한 파일만
   `git ls-files -- <경로>`, `git diff -- <경로>`로 대조한다. 미커밋·미추적·무시 파일을
   원격에 공유된 구현으로 설명하지 않는다. GitHub 요청이면 사용자가 지정한 ref/commit을
   기준으로 읽고 로컬 HEAD와 섞지 않는다. 실제 원격 ref를 확인하지 않았다면 공유 여부는 미확인이다.
2. 구조 문서의 시작점에서 `rg`로 함수·라우트·호출자를 찾는다. 사용자 동작에서 출발해
   화면 → HTTP 처리 → 서비스 → 저장/검색 → 응답의 관련 경로만 읽는다.
   파일이나 함수 이름만 보고 기능을 확정하지 말고 본문·호출부·분기 조건을 확인한다.
3. 기본값, 환경 변수, CLI 옵션, 실패/보류 동작을 함께 확인한다. `hybrid`와 `s30h`,
   합성 관측과 연구 정답, 현재 관측과 질의 당시 evidence, 과거 조치 원문을 구분한다.
   심사·검수·임베딩·게시·검색 노출은 각각 확인한다.
4. 근거는 `저장소 상대 경로:심볼`로 남기고 응답에서는 현재 줄 번호를 확인해 링크한다.
   문서 주장, 코드 확인, 이번 실행 확인, 미확인을 구분한다. 테스트 파일의 존재는 통과 증거가 아니다.
   장비·모델·성능·배포 상태는 이번에 직접 확인하거나 시점이 명시된 기록으로만 설명한다.
5. 요청에 필요한 가장 작은 격리 검증을 선택한다. 새 테스트를 덧붙이거나 전체 pytest를
   기본 실행하지 않는다. 모델 fixture 통과를 실제 모델 품질로 확대하지 않는다.
   분석을 위해 운영 DB·KB·인덱스를 쓰거나 장비 서비스를 기동/재시작하지 않는다.

## ShiftLink에서 놓치기 쉬운 경계

- MES 진입점은 `shiftlink/mes/__main__.py`, 조립은 `server.py:MesService`다.
  정적 HTML/JS 화면이며 React/Vite 프로젝트로 가정하지 않는다.
- 질의의 모드 선택은 `query.py:build_query_pipeline`, 관측 선택은 `query_service`다.
  모델/인덱스 준비 여부와 환경 변수 설정을 코드 기본값에서 추정하지 않는다.
- 게시/검색 변경 전에는 `.github/instructions/knowledge-publication.instructions.md`와
  `docs/failures/knowledge-publication-integrity.md`를 읽고 해당 검증을 따른다.
  단순 기능 지도 작성만으로 제품 동작·이력 의미 검증 완료를 주장하지 않는다.
- PDA UI 변경은 `shiftlink/mes/web/AGENTS.md`를 따른다. 외관 요청을 센서·프록시·질의
  근거 변경으로 넓히지 않는다.
- 연구 스크립트는 실제 서버 호출 경로가 확인될 때만 서비스 기능으로 설명한다.
  `uploader.py:HOLD_RESOLUTION_UPLOAD` 등 보류 조건을 확인하고 전량 동기화로 요약하지 않는다.

## 다음 작업에 남길 내용

새로 확인한 사실이나 달라진 경로가 있으면 `docs/design/feature-map.md`의 해당 행/설명만 갱신한다.
기능별로 사용자 목적, 호출 흐름, 근거 심볼, 관련 검증, 확인 수준과 남은 의문을 보존한다.
기준일·HEAD·로컬 변경 여부와 실행한 명령/결과를 기록하되 비밀·개인정보·실행 DB 내용은 복사하지 않는다.
구조나 진입점이 바뀌면 `project-structure.md`도 갱신한다. 설명만 요청받았다면 변경을 만들기 위해
문서를 다시 쓰지 말고, 확인된 새 사실이 있을 때만 필요한 부분을 유지보수한다.

다음 작업에서는 지도를 재사용하되 관련 파일의 상태와 심볼을 다시 확인한다.
낡은 기록은 삭제해 숨기지 말고 현재 코드와의 차이 및 미확인 범위를 명시한다.

답변은 기능과 근거를 먼저 제시하고, 이번 확인 결과와 남은 불확실성을 짧게 덧붙인다.
