# 지식 카드 작성 가이드 초안

> 이 문서는 v0.9 당시의 기록이다. 현재 카드 작성·유형 판정에는 [스키마 v1.1 작성 가이드](../../seeds/카드_작성_가이드_초안.md)를 사용한다. 아래의 유형·필드 설명과 미결 사항은 현재 기준을 대체하지 않는다.

작성일: 2026-09-17 · 기준: K-01 / pipeline schema v0.9 · 상태: 검토용 초안

## 1. 목적과 기준

이 가이드는 베테랑의 경험과 사건 기록을 `KnowledgeCard` 형식으로 정리할 때 사용한다. 작성자는 **어떤 상황에서, 무엇을 확인하거나 해야 하며, 왜 그런지, 언제 적용하면 안 되는지**를 카드 한 장만 읽어도 알 수 있게 쓴다.

기준 파일은 [`shiftlink/agent/schemas.py`](../../shiftlink/agent/schemas.py)의 `KnowledgeCard`, `Condition`, `Provenance`다. [`tests/test_schemas.py`](../../tests/test_schemas.py)는 주요 검증 규칙을 보여준다.

- **스키마 규칙**: 현재 코드가 검사하는 필드·허용값·조합 규칙이다.
- **작성 권장**: 내용 품질을 위한 이 초안의 작성·검수 기준이다. 코드가 자동으로 검사한다는 뜻은 아니다.
- **미결 사항**: 고도화 문서의 제안이며 현재 카드에 새 필드로 추가하지 않는다.

유형 설명은 [`A_domain.md` A5](../design/A_domain.md)를 참고한다. T1~T5 원 정의와 포함·제외 기준은 미결이므로 아래 설명은 잠정적인 작성 기준이다. 검증 등급·검색 대상 정책은 [`04_확정_미결_목록.md`](../planning/04_확정_미결_목록.md)를 따른다.

## 2. 작성 순서

1. **근거를 먼저 확보한다.** 참고 시드, 출처 사건, 페르소나를 확인한다. 근거가 없는 경험·관측값·성공 결과를 만들어 넣지 않는다.
2. **한 카드의 핵심을 정한다.** 하나의 판단, 조건부 요령, 확인 순서, 인계 맥락 또는 안전 금기를 담는다. 서로 다른 조건에서 쓰는 별개 요령은 분리한다.
3. **유형·대상·사용 장면을 고른다.** `tacit_type`, `equipment`, `component`, `scenario`를 지정한다.
4. **본문을 쓴다.** 제목 → 증상 → 노하우 → 이유 순서로 작성한다. 관측 사실과 원인 추정을 구분한다.
5. **적용 범위를 명시한다.** `conditions`와 `exclusions`를 채우고 안전 관련 여부 및 근거를 확인한다.
6. **관리 정보를 채운다.** ID, 버전, 출처, 데이터 분할을 기록한다. 신규 초안은 `grade: "L0"`, `status: "draft"`로 시작한다.
7. **형식 검사와 내용 검수를 진행한다.** JSON 검증 통과만으로 채택하지 않는다. 검수 결과에 따라 담당자가 등급·상태를 변경한다.

## 3. 유형 선택

| 유형 | 잠정 의미 | 작성 초점 | 코드가 추가로 요구하는 것 |
| --- | --- | --- | --- |
| `T1` | 감각 기반 이상 징후 판단 | 어떤 소리·진동·냄새가 평소와 어떻게 다른지, 무엇을 추가 확인할지 | 비어 있지 않은 `symptom` |
| `T2` | 조건부 요령 | “어떤 조건이면 어떤 요령을 적용하는가”와 적용 제외 상황 | `conditions` 1개 이상 |
| `T3` | 트러블슈팅 순서 | 확인 순서와 각 단계의 분기·종료·보류 기준 | 비어 있지 않은 `symptom` |
| `T4` | 인수인계 맥락 | 현재 상태, 이미 확인한 것, 미해결 사항, 다음 조 확인 사항 | 유형별 추가 검증 없음 |
| `T5` | 안전 금기 | 금지 행동, 적용 상황, 보류·담당자 확인 기준 | `safety_flag: true` 및 비어 있지 않은 `safety_basis` |

작성 권장: 카드의 주된 목적에 따라 유형 하나를 선택한다. T1~T4에도 안전 내용이 있으면 `safety_flag`를 표시한다. T3 단계는 현재 `know_how` 문자열에 `1)`, `2)`, `3)` 순서로 쓴다. T4에는 개별 교대 기록 전체보다 다음에도 재사용할 수 있는 인계 요령을 담고, 원 사건은 출처로 연결한다.

`scenario`의 프로젝트상 사용 장면은 `S1` 신입, `S2` 저년차, `S3` 교대다. 카드 유형과 별도로 선택한다. 코드가 허용하는 값은 이 세 가지뿐이다.

## 4. 필드별 작성 방법

‘필수’는 입력 키가 반드시 필요하다는 뜻이다. 기본값이 있는 필드는 생략 가능하지만, 검토용 JSON에는 명시적으로 쓰는 것을 권장한다. 일반 문자열의 빈칸 여부까지 모두 검증되는 것은 아니므로 사람이 확인해야 한다.

### 4.1 식별·분류

| 필드 | 필수 / 기본값 | 작성 방법 |
| --- | --- | --- |
| `card_id` | 필수 | `K-` + 숫자 4자리. 예: `K-0001`. 기존 ID와 중복되지 않게 관리한다. 형식만 코드 검사 대상이다. |
| `version` | 필수 | 문자열. 코드에는 버전 형식 제한이 없다. 팀의 버전 표기 규칙을 따른다. 아래 예시의 `0.9`는 예시값이다. |
| `grade` | 생략 시 `L0` | 허용값 `L0`, `L1`, `L2`, `L3`. 프로젝트 정책상 신규 초안은 L0, MVP 최고 검증 등급은 L1이다. |
| `tacit_type` | 필수 | `T1`~`T5` 중 하나. |
| `equipment` | 필수 | `HPU` 유압 유닛, `GR` 구동 모터·감속기, `RT` 롤러 테이블, `CV` 컨베이어, `COMMON` 공통. 개별 장비 번호를 넣지 않는다. |
| `component` | 필수 | 해당 부품·대상을 일관된 명칭으로 작성한다. 가능하면 설비 사전 명칭을 사용한다. 현재는 자유 문자열이다. |
| `scenario` | 필수 | `S1`, `S2`, `S3` 중 하나. |

### 4.2 본문

| 필드 | 필수 / 기본값 | 작성 방법 |
| --- | --- | --- |
| `title` | 필수 | 대상과 판단·행동이 드러나는 짧은 제목. 예: “반복 이상음 기록 시 운전 상태 함께 남기기”. |
| `symptom` | 생략 시 `null` | 관측된 현상을 쓴다. 발생 시점·반복 여부·운전 상태를 구체화한다. T1·T3에서는 필수다. |
| `know_how` | 필수 | 작업자가 이해할 수 있는 확인·판단·전달 방법을 쓴다. 조건, 순서, 분기 또는 보류 기준을 포함한다. |
| `rationale` | 필수 | 이 방법을 쓰는 이유와 출처가 뒷받침하는 범위를 쓴다. 추정을 확정 원인으로 바꾸지 않는다. |

작성 권장 문장 틀:

> **증상:** [운전 상태/시점]에서 [관측 현상]이 [빈도/변화]로 나타난다.  
> **노하우:** [조건]이면 [확인/행동]한다. [다른 결과]이면 [다음 확인/보류]한다.  
> **이유:** [근거]에 따르면 [판단에 도움이 되는 이유]가 있다. [확인되지 않은 부분]은 추가 확인이 필요하다.

| 피할 표현 | 권장 방향 |
| --- | --- |
| “소리가 이상하면 잘 확인한다.” | 평소와 다른 소리의 특징, 발생 시점, 추가로 남길 기록을 명시한다. |
| “이 소리면 무조건 베어링 문제다.” | 관측된 이상음과 원인 후보를 분리하고, 원인 확인 전 단정하지 않는다. |
| “지난번에 해결됐으니 이번에도 똑같이 한다.” | 이전 사건과 현재 상황의 조건 차이 및 적용 제외 상황을 쓴다. |
| “점검 완료.” | 확인 항목, 확인 결과, 남은 불확실성, 다음 확인 사항을 적는다. |

### 4.3 적용 조건·안전·상충

| 필드 | 필수 / 기본값 | 작성 방법 |
| --- | --- | --- |
| `conditions` | 생략 시 `[]` | 카드 적용 조건의 목록. 각 항목은 아래 `Condition` 형식이다. T2는 1개 이상 필요하다. |
| `exclusions` | 생략 시 `[]` | 적용하면 안 되는 조건의 목록. 자료형은 `conditions`와 같다. |
| `safety_flag` | 생략 시 `false` | 안전 관련이면 `true`. T5는 반드시 `true`. |
| `safety_basis` | 생략 시 `null` | `safety_flag: true`이면 반드시 작성. 확인한 안전 문서의 이름·식별 정보·관련 절과 적용 이유를 적는다. |
| `conflict_group` | 생략 시 `null` | 상충하는 카드가 있으면 같은 그룹 문자열로 연결한다. 없으면 `null`. 그룹의 존재·참조는 코드가 검사하지 않는다. |

`Condition` 형식:

| 필드 | 자료형 / 필수 | 작성 방법 |
| --- | --- | --- |
| `signal` | 문자열 / 필수 | 비교할 계측 항목이나 상태 항목의 이름. 설비 사전·소비 코드와 일치시킨다. |
| `op` | 문자열 / 필수 | 비교 연산자. 현재 스키마는 허용 연산자 목록을 정하지 않는다. |
| `value` | 임의 자료형 / 키 필수 | 비교 기준값. 숫자·문자열·목록 등 실제 연산자와 맞는 값을 사용한다. |
| `unit` | 문자열 또는 `null` / 기본 `null` | 수치의 단위. 상태값처럼 단위가 없으면 `null`. |

현재 코드에는 단위 사전, 연산자 실행 의미, 여러 조건의 AND/OR 결합 규칙이 없다. 작성 권장: 조건 해석을 `know_how`에도 명시하고, 실제 필터에 쓰기 전에 소비 코드와 표기를 맞춘다. `>`와 `gt`, `>=`와 `gte` 등을 같은 의미라고 임의로 혼용하지 않는다. 빈 조건 목록은 “무조건 안전하게 적용 가능”을 뜻하지 않는다.

가상 수치는 본문 또는 동반 문서에서 `[가상 값]`으로 표시하고, `value` 자체는 수치형으로 유지한다. 안전 근거를 확인하지 못했다면 이를 숨기려고 `safety_flag`를 끄거나 가짜 문서 번호를 입력하지 않는다. 미확인 내용을 검수 메모에 남기고 채택을 보류한다. 이 가이드는 실제 설비 작업 절차나 안전 문서의 유효성을 확정하지 않는다.

### 4.4 출처·신뢰도·상태

| 필드 | 필수 / 기본값 | 작성 방법 |
| --- | --- | --- |
| `confidence` | 필수 | **0 이상 1 이하의 수치**. `high`, `medium`, `low`는 허용하지 않는다. 점수 산정 기준은 코드에 없으므로 팀 기준을 정하고, 높은 점수를 검증 완료의 증거로 취급하지 않는다. |
| `provenance` | 필수 | 아래 출처 필드 5개를 모두 작성한다. |
| `split` | 필수 | `kb`, `dev`, `sealed` 중 하나. 출처 사건의 데이터 분할과 일관되게 관리한다. |
| `status` | 생략 시 `draft` | `draft`, `accepted`, `rejected_rule`, `rejected_judge`, `rejected_human`, `rejected_safety` 중 하나. |

| `provenance` 내부 필드 | 자료형 | 작성 방법 |
| --- | --- | --- |
| `seed_ids` | 문자열 목록 | 참고한 시드 ID. 출처 레코드에서 가져온다. |
| `persona_id` | 문자열 | 출처 페르소나 ID. 실제 전문가 검증을 뜻하지 않는다. |
| `event_ids` | 문자열 목록 | 카드의 근거가 된 사건 ID. |
| `generator` | 문자열 | 생성 모델 또는 수동 작성 경로를 식별할 수 있는 이름. |
| `generated_at` | datetime | 생성 시각. JSON에서는 ISO 8601 문자열을 권장하며 시간대 오프셋도 기록한다. |

출처 필드의 키는 필수지만, ID 형식·참조 대상 존재·목록의 비어 있음은 현재 `Provenance`가 검사하지 않는다. 시간대도 코드상 강제되지 않는다. 작성·검수 과정에서 별도로 확인한다.

`accepted`인 카드는 반드시 `grade: "L1"`이어야 한다. 반대로 `L1`이라고 자동으로 `accepted`가 되지는 않는다. 상태 전이 이력이나 실제 검수 수행 여부는 스키마가 검사하지 않는다. 프로젝트 문서상 검색 대상은 **`accepted` AND `kb` AND `L1`**이며, 이는 검색 정책이지 모델 생성 시 자동 실행되는 필터가 아니다. 평가용 `dev`·`sealed` 출처를 검색용 `kb` 카드로 옮기지 않는다.

## 5. 복사해서 수정할 수 있는 JSON 예시

아래는 **작성 형식 설명용 가상 T1 초안**이다. ID와 출처는 자리표시용이며 실제 등록 전에 발급·존재 여부를 확인하고 교체해야 한다. 신뢰도 `0.5`는 예시값이며 권장 기본점수가 아니다. 실제 설비에 대한 진단·검증 결과를 나타내지 않는다.

```json
{
  "card_id": "K-0001",
  "version": "0.9",
  "grade": "L0",
  "tacit_type": "T1",
  "equipment": "GR",
  "component": "감속기",
  "scenario": "S1",
  "title": "반복 이상음 기록 시 운전 상태 함께 남기기",
  "symptom": "[가상 상황] 감속기 주변에서 평소와 다른 반복음이 관측되었다.",
  "know_how": "기존 관측 기록의 이상음 발생 시각과 당시 운전 상태를 함께 정리한다. 운전 상태 기록이 없으면 미확인으로 남기고 담당자에게 확인을 요청한다. 소리 기록만으로 고장 부품을 확정하지 않는다.",
  "rationale": "[작성 예시] 발생 시점과 운전 상태를 함께 기록하면 후속 검토에서 서로 다른 조건의 관측을 구분하는 데 도움이 된다. 이 예시는 실제 사건 검증 결과가 아니다.",
  "conditions": [],
  "exclusions": [],
  "safety_flag": false,
  "safety_basis": null,
  "conflict_group": null,
  "confidence": 0.5,
  "provenance": {
    "seed_ids": ["EXAMPLE-SEED-001"],
    "persona_id": "EXAMPLE-PERSONA-01",
    "event_ids": ["EV-0001"],
    "generator": "manual-guide-example",
    "generated_at": "2026-09-17T09:00:00+09:00"
  },
  "split": "kb",
  "status": "draft"
}
```

## 6. 제출 전 체크리스트

### 코드로 확인되는 항목

- [ ] 필수 키와 자료형이 맞고 ID가 `K-` + 숫자 4자리다.
- [ ] 유형·설비·시나리오·등급·분할·상태가 허용값이다.
- [ ] `confidence`가 0~1의 수치다.
- [ ] T1·T3에는 `symptom`이 있고 T2에는 `conditions`가 1개 이상 있다.
- [ ] T5는 `safety_flag: true`다.
- [ ] 모든 `safety_flag: true` 카드에 `safety_basis`가 있다.
- [ ] `status: "accepted"`이면 `grade: "L1"`이다.

### 작성자·검수자가 확인할 항목

- [ ] 필수 본문이 빈 문자열이나 공백뿐이지 않고, 한 카드의 목적이 분명하다.
- [ ] 관측 사실, 원인 추정, 확인 결과를 구분했다.
- [ ] 적용 조건·제외 조건·본문이 서로 모순되지 않는다.
- [ ] 조건의 신호명·연산자·자료형·단위가 소비 코드 및 설비 사전과 맞는다.
- [ ] 출처 ID가 실제로 존재하고 내용을 뒷받침하며, 카드 ID가 중복되지 않는다.
- [ ] 사건과 카드의 데이터 분할이 일관되고 평가 데이터가 검색용 지식에 섞이지 않는다.
- [ ] 가상 수치·합성 내용임을 표시했고, 검증되지 않은 성공이나 현장 검증을 주장하지 않는다.
- [ ] 안전 근거가 해당 상황에 적용되는지 검토했고, 필요한 검수를 거쳐 상태를 변경한다.
- [ ] 상충 카드가 있으면 그룹을 연결하고 차이가 생기는 조건을 설명했다.
- [ ] 정의되지 않은 필드를 추가하지 않았다.

## 7. 형식 검증 방법과 한계

프로젝트 의존성이 설치된 환경에서, 카드 한 장을 JSON 객체로 저장한 뒤 저장소 루트에서 다음을 실행한다. `path/to/card.json`은 실제 파일 경로로 바꾼다.

```bash
python - <<'PY'
from pathlib import Path
from shiftlink.agent.schemas import KnowledgeCard

card = KnowledgeCard.model_validate_json(
    Path("path/to/card.json").read_text(encoding="utf-8")
)
print(card.card_id, card.grade, card.status)
PY
```

이 검사는 형식과 일부 필드 조합만 확인한다. 참조 무결성, 분할 상속, 내용의 정확성, 물리적 타당성, 안전 근거의 적합성은 별도 검수 대상이다. 현재 모델에는 알 수 없는 필드를 거부하는 설정이 없어 추가 필드가 무시될 수 있다. “오류가 나지 않았다”만으로 입력 내용이 모두 보존된다고 판단하지 않는다.

## 8. 기존 샘플 이용 시 주의 및 다음 검토 사항

[`01_kb_cards_shared.json`](../data/knowledge_cards/01_kb_cards_shared.json)은 확장안이 포함된 샘플이다. 현재 v0.9용 입력으로 그대로 복사하면 `confidence: "high"`가 수치 제약에 맞지 않는다. `high`를 특정 숫자로 바꾸는 공식도 정의되어 있지 않으므로 임의 환산하지 않는다. `scope_level`, `equipment_ids`, `manual_refs`, `is_synthetic` 등은 현재 `KnowledgeCard` 필드가 아니다.

다음 항목은 작성 규칙 확정 또는 스키마 개정 때 검토한다. 현재 필수 입력으로 취급하지 않는다.

- T1~T5의 최종 정의와 유형별 포함·제외 기준.
- 신호명·단위·연산자 목록과 다중 조건의 결합 규칙.
- `confidence` 산정 기준, 카드 버전 표기 및 ID 발급 규칙.
- D-26: `safety_flag` 기반 노출·채점·전수 검수 확대.
- D-27: T4 전달축 분리(`content_type`, `handover_relevant`).
- D-28: `type_payload` 및 T3 `steps` 구조화.
- D-29: T6 및 `tried_and_failed` 도입 여부.

위 D-26~D-29는 현재 스키마에 승인 대기 주석으로만 존재한다. 승인 및 코드 반영 이후 가이드와 예시를 함께 갱신한다.
