### 3.1 스키마 변경 작업안

아래 이름은 구현 제안이다. 9/22 계약 검토 후 스키마 v1.0에 고정하며, 회의가 모든 필드명까지 승인한 것으로 표현하지 않는다.

| 대상 | 최소 구조 제안 | 검증 규칙 | 필요한 예제 |
|---|---|---|---|
| 안전 공통 | 기존 `safety_flag`, `safety_basis`, `conditions`, `exclusions` 활용 | T5이면 flag 필수. flag이면 근거 필수. 안전 조회는 일반 top-k와 독립, 중복 ID 제거 | T2/T3/T4이면서 safety flag인 카드, top-k 밖 안전 카드, 조건 불일치 안전 카드 |
| T4 인계 방법 | `type_payload.handover_method`: `required_context`, `recipient_role`, `timing`, `channel`, `acknowledgement` | “인계했다”만 있는 카드는 방법 지식으로 통과시키지 않음. 전달 대상·시점·내용·확인 방법의 누락 판정 | 좋은 인계 방법·정보 부족·수신 확인 누락 각 사례 |
| T3 단계 | `type_payload.steps[]`: `step_id`, `order`, `action`, `preconditions`, `expected_result`, `stop_conditions` | 단계 ID·순서 중복 금지, 필수 단계 누락·역전 차단. 안전·중지 조건은 길이 제한으로 잘라내지 않음 | 정상 순서, 역전, 단계 누락, 중지 조건 포함 |
| 재가동·실패 | `type_payload.restart_type`, `tried_and_failed[]`: `attempt_id`, `restart_type`, `action`, `observed_result`, `failure_reason`, `evidence_ids` | 유형별 실패 연결, 실패 이유 미상은 미상으로 보존. 한 유형의 실패를 다른 유형에 일반화하지 않음 | 서로 다른 유형 2개 이상, 유형 미상, 실패 근거 부족 |

- 재가동 유형 분류의 예시는 정상 정지 후 재가동·이상 정지 후 재가동·정비 후 재가동이다. 현장 표준으로 단정하지 않고 가상 설비 사전에서 명칭·허용값을 정한다.
- 카드의 재사용 가능한 지식과 사건별 시도 이력은 구분한다. 사건 이력을 카드에 연결하더라도 평가용 사건의 정답을 런타임으로 전달하지 않는다.
- T4 카드와 실제 교대 인계 레코드는 별개다. 카드에는 전달 방법, 인계 레코드에는 이번 교대의 요청·상태·수락·수정 이력을 둔다.
- v0.9 데이터를 읽는 변환 경로를 마련하되 없는 안전 근거·단계·인계 방법을 자동 창작하지 않는다. 필수 정보가 부족하면 검토 대기로 보존한다.
- D-26~29를 스키마만 바꾸고 끝내지 않는다. 생성 프롬프트 → P5 규칙 → 검색 → 응답 → 화면 → 정답지의 같은 규칙을 함께 변경한다.

### 3.2 N-3 업로드 운영안

1. 런타임은 로컬 원본·인계·감사 로그를 먼저 저장한다. 네트워크 오류로 사용자 요청을 실패시키지 않는다.
2. 전송 항목을 outbox에 추가하고 원본 payload는 수정하지 않는다. 전송 성공 상태·재시도 횟수는 별도 상태 기록으로 관리한다.
3. **계획 기본안은 PC가 하루 1회 배치를 실행하는 방식**이다. Jetson 런타임 외부 의존을 늘리지 않는다. Jetson에서 PC로 가져오는 경로와 실행 시각(안: 작업일 18:00, 비작업일 다음 실행 시 누적 처리)은 9/22 운영 계약에 기록한다. 매일 자동 실행이 필요한 운영 단계의 비작업일 스케줄도 구분한다.
4. 업로드 필드는 ID·버전·해시·상태·검수 코드·집계 지표의 허용 목록으로 제한한다. 인계 원문·모델 원문 응답·judge 코멘트·자격 증명은 전송하지 않는다.
5. 논리 레코드의 `record_id + version + kind` 등 유일키와 해시를 사용한다. 같은 키·같은 해시는 중복 무시, 같은 키·다른 해시는 충돌로 보류한다.
6. 성공 확인 전 outbox를 삭제하지 않는다. 네트워크 중단 후 재전송·부분 성공·중복 전송·재시작을 시험한다.
7. Aiven 7개 이력 테이블은 통합본 §4.11을 따른다. 실제 접속 정보·테스트 DB가 없으면 로컬 계약 시험과 실서버 미검증을 분리해 보고한다.

### 4.2 선정 절차와 마감

- **9/22, 최재영:** 후보마다 공식 모델 카드·공식 가격/콘솔·라이선스·실행 위치 확인. 확인 날짜와 URL, 정확한 ID를 비교표에 기록한다. N-7 생성 모델 후보와 온디바이스 B/C를 함께 놓고 계열 충돌을 표시한다.

- **9/28~30:** 같은 개발용 검수 샘플 30건을 후보별로 채점한다. T1~T5, 비T5 안전, 부정/철회, 단계 순서, 재가동 실패를 포함한다. 봉인셋은 후보 선정에 사용하지 않는다.
- **10/1:** 사람 판정과 judge의 채택/보류 일치율, 안전 오통과, 점수 근거, JSON 실패율, 시간·사용량·비용을 비교한다. 같은 가족 모델의 자기평가를 교차 judge로 집계하지 않는다.
- **10/2:** 계열 분리·실행 조건·비용 조건을 만족한 경우 `models.lock` 및 실행 설정에 최종 judge를 고정한다. 미충족이면 미선정으로 남기고 P5 미통과 카드를 `accepted/L1`로 올리지 않는다.
- 비용은 실제 입력/출력 토큰, 재시도, 캐시 적용, 환율 기준일 및 로컬 자원비를 분리해 기록한다. 후보표만으로 예산 상한을 계산하지 않는다.

### 4.3 N-5 임베딩 미결 상태에서 진행할 일

- 검색 API·설비/조건 필터·가시성 필터·안전 강제 노출·인용 검증은 임베딩 선정과 독립적으로 구현한다.
- 기존 스파이크 모델은 임시 실험 설정으로만 사용한다. 모델 ID·차원·정규화·버전으로 인덱스를 구분하고 서로 다른 임베딩의 벡터를 혼합하지 않는다.
- 최종 모델 변경 시 카드 ID와 평가 문항을 유지하고 인덱스만 다시 만든다.
- 10/2까지 N-5가 미결이면 기능 통합 결과는 보고할 수 있지만 “최종 임베딩 확정·최종 검색 품질 검증 완료”로 표시하지 않는다. 사용자 결정 시한을 임의로 확정하지 않는다.

### 7.2 데이터·평가 산출물

- 생성·스키마 통과: 사건 60건, 카드 120건, 산출물 5종 합계 100건을 1차 목표로 한다.
- 통합용 카드 20건 이상은 P5 전 게이트를 통과한 `accepted/L1`을 목표로 한다. 임시 검수나 사람 검수만으로 judge 게이트를 생략하지 않는다.
- 개발셋 30건 초안과 20건 E2E 결과를 연결한다. N-4 비교용 30건은 카드/산출물 검수 샘플이며 개발 질의·인계 30문항과 다른 단위다.
- 최종 봉인 평가셋 60건의 분할 계약·접근 통제·생성 계획을 준비한다. 이번 기간의 목표를 최종 봉인·본 평가 완료로 부풀리지 않는다.
- 안전 flag 전체 전수 검토, T4 전달 방법, T3 단계, 재가동 유형별 실패의 별도 커버리지 표를 만든다. 기존 T별 최소 20·T5 최소 25는 최종 채택 150 목표의 기준으로 유지한다.
- QC 보고서는 입력/생성/스키마 통과/규칙 탈락/중복/judge 보류/사람 검수/최종 채택을 구분한다. 검수 전 레코드를 런타임 KB에 넣지 않는다.
- 원천 시드와 합성 데이터를 분리하고 사건·템플릿 그룹을 기준으로 분할한다. 이전 합성 결과를 새 원천 근거로 되먹이지 않는다.

### 7.3 성능 판정

- 기준은 **15W**, 같은 입력·같은 컨텍스트/출력 상한·같은 KB·같은 캐시 정책이다. 장비 모드 조회 결과를 실행 로그와 함께 남긴다.
- 플랜 B의 p95 15초 이하·검색 2초 이하 목표를 유지하되 측정 결과와 구분한다. C도 동일 조건으로 별도 측정하며 자동 대체 성공으로 표시하지 않는다.
- 20건에서 성공률과 지연을 함께 보고한다. 실패를 지연 집계에서 조용히 제외하지 않고 실패 수·타임아웃·재시도 시간을 별도 표시한다.
- warm E2E는 요청 시작부터 검증/결과 반환까지 측정한다. cold 최초 로딩은 별도 보고하고 캐시 적중·미적중을 구분한다.
- p95 계산 방식(안: nearest-rank, 20건 정렬 시 19번째 값), 요청별 raw, peak RAM, 온도, load duration, 출력 토큰 수를 기록한다. 20건은 예비 측정이며 장시간 안정성 증명은 아니다.
- 목표 미달 시 원인을 검색·컨텍스트·생성·재시도·저장으로 나눠 보고한다. 안전 문구나 필수 해결 단계를 생략해 속도 목표를 맞추지 않는다.
- Recall@5 0.8, 근거 충실도 0.9 등 통합본의 미확정 정량 목표는 참고 목표로 유지한다. 이번 회의가 해당 수치까지 확정한 것으로 처리하지 않는다.

현재 CLI 호출은 다음과 같지만 **지금은 계획 출력만 수행한다**. 기간 중 실제 실행 구현 후 명령·출력·재개 지점·산출물 수량을 가이드에 갱신한다.

```text
python -m shiftlink.data all --seed 42 --version v1.0
python -m shiftlink.data all --from P3 --seed 42 --version v1.0
```

새 LLM 호출의 결과가 seed만으로 바이트 단위 재현된다고 주장하지 않는다. 저장 raw 재생의 결정적 후처리 해시와 새 생성 실행의 품질 결과를 구분한다.
