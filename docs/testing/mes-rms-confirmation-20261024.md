# 정상 RMS 정체·센서 고착 구분 보정 — 2026-10-24~25

모델·미사용 평가·Pi 실시간 검증은 통과했다. 이 검증 기록 작성 시점에는 운영 적용 전이며, 실제 적용 여부·백업·복구 경로는 후속 배포 기록으로 구분한다.

## 수정 범위와 원인

기존 `normal-profile.json`과 r6 모델·원본 결과를 보존하고 `normal-profile-rms16.json`을 별도로 만들었다. 일곱 `vib_rms` 채널의 확인 기간만 8→16 유효 연속 프레임으로 바꿨다. 전처리·EWMA·부하별 정상 기준·임계값·회복 상태기·PDA 파일은 그대로다. Timestral이나 새 신경망 학습은 사용하지 않았다. 기존 16프레임 버퍼를 재사용한다. 새 파일의 normal_flat_rule/training_sha256는 원본 정상 학습의 출처이며, 이번 16프레임 고정 보정은 이 문서와 파일 이름으로 구분한다.

보존된 이전 평가의 CV-01(EQ-0009, cooling_loss-03, seq649) 1.369와 RT-03(EQ-0008, normal-06, seq515) 1.348은 모두 정상 범위·good 품질이었다. 정상 생성기의 소수 셋째 자리 반올림으로 8프레임 동안 같아져 고착으로 오인했다. 해당 설비의 정상 반사실 재생도 전체 649/515프레임이 같아 파급 반응이 아님을 확인했다. 정상 범위 고착을 무조건 무시하는 방식은 쓰지 않았다. 두 소비된 사례를 회귀 자료로만 사용했고, Pi에서 원본의 두 오통지를 먼저 재현한 뒤 수정 후보에서 제거했다.

## 새 미사용 평가의 공정 비교

후보·생성기·설정·프로토콜 해시를 고정한 뒤, 모든 평가 입력을 생성·봉인하고 같은 자료를 원본 r6와 후보에 재생했다. 별도 개발셋은 공정 고장4·고착14·정상4실행이며 18/18 탐지, 오통지·중복0이었다. 미사용 평가는 네 공정 고장 종류별6건(24), 일곱 RMS 채널의 정상 범위 안/밖 지속 고착(14), 정상16실행×900프레임이다. 총 38,935프레임, 정상 4시간 상당 합성 재생이다. 개발·이전 평가·새 평가 사이 seed/nonce/run_id 중복은 각각0이며 모든 입력 SHA256를 확인했다. 정답 장부는 센서 입력과 분리했다.

| 항목 | 원본 r6 | RMS16 후보 |
|---|---:|---:|
| 공정 고장 탐지 | 24/24 | 24/24 |
| 지속 센서 고착 탐지 | 14/14 | 14/14 |
| 전체 탐지 | 38/38 | 38/38 |
| 정상·비매칭 오통지 | 0 | 0 |
| 중복 통지 | 0 | 0 |
| 고장 시작 기준 탐지 p95 | 25초 | 25초 |
| 정상 범위 안 고착 p95 | 7초 | 15초 |
| 정상 범위 밖 고착 p95 | 5초 | 5초 |
| Pi 계산 p95 | 30.88ms | 27.03ms |

이번 새 자료에서는 원본도 오통지0이었다. 따라서 새 자료에서 오통지율 우위가 입증됐다고 설명하지 않는다. 확인된 개선은 기존 두 오통지 회귀의 제거이며, 새 평가에서 탐지·오통지·중복·공정 고장 지연이 유지된 것이다. 정상 범위 고착 확인은 7→15초로 8초 늦어지는 명시적 절충이다. 16프레임 이상의 건강한 정체나 실제 현장 분포에 대한 완전한 구분을 보장하지 않는다.

첫 통지는 공개 reader의 고유 event_id이며 같은 설비의 고장 창에 매칭한다. 다른 설비·고장 창 밖 통지는 오통지, 같은 창의 추가 ID는 중복이다. 반복 표시 자체는 중복 통지가 아니다. 3프레임 가상 조회 지연 p95 26초는 실제 끝단 간 측정과 다르다. 통과 기준과 RED/GREEN 이력은 [고정 기준·TDD](mes-rms-confirmation-20261024.tdd.md)를 따른다.

## Pi 실시간 1Hz·화면 확인

미리 정한 네 공정 고장 첫 사례와 정상 범위 고착 한 사례를 1초씩 실제로 공급했다. 소스·실제 worker·체크포인트 fsync·설치된 PDA reader·실제 알람창 JavaScript/Chromium은 전부 Pi에서 실행했다. HTTP는 임시 loopback SSH forwarding으로 Pi→Jetson→Pi를 왕복했으며 운영 포트·DB·사용자 알람에는 쓰지 않았다. 실제 3초 조회와 두 requestAnimationFrame 뒤의 표시를 측정했다.

- 269프레임 송신/처리 일치, 누락0, 최대 처리 지연2프레임.
- 표시 끝단 간 p95/최대 26.64초, 사례5건. 표본이 작고 실제 운영 DB·키오스크/물리 화면 경로의 p95는 아니다.
- HTTP/replay/처리/저장 poll p95의 사례별 최대 0.188초.
- 같은 설비1행, 기존 확인 상태 유지, AI 추가 진동 호출0, 같은 event_id 유지, 30프레임 이후 표시 유지.
- 물리 진동 모터의 움직임은 계측하지 않았다. 실제 사용자 확인 버튼이나 기존 경보를 조작하지 않았다.

초기 v3/v4 시험은 임시 Chromium의 데스크톱 키 저장소 대기 때문에 화면을 시작하지 못했다. Chrome NetLog의 키 로드 시작/미완료와 별도 HTTP 대조로 원인을 확인했고, 계정 정보 없는 임시 프로필에만 `--password-store=basic`을 적용한 v5에서 전체 프로토콜을 통과했다. 원본 실패 로그와 helper를 보존했다. 운영 브라우저·키 저장소 설정은 바꾸지 않았다.

## 누적 이력 전달 경로 보정

실제 기존 poll은 5.390초였고 `MesStorage.replay`는 요청 cursor 앞의 전체 이력을 역직렬화한 뒤 걸러내고 있었다. `snapshots`에 선택적 after_sequence를 추가해 기존 (run_id,sequence) 인덱스의 SQL 범위 조건으로 내렸다. 기존 전체 이력 호출·as_of·실행 경계·정답 비공개·경보 데이터는 유지한다.

같은 2,000프레임×69채널에서 끝의2프레임 요청을 5회씩 비교한 Pi 중앙값은 원본2.385361초→수정0.002231초다. 보존된 행2,000개와 반환 프레임은 같았다. 이 수치를 운영 네트워크나 화면 지연으로 설명하지 않는다. 1,000프레임 회귀에서 원본은 빈 요청도1,000개를 해석했고 수정은 필요한2개/0개만 해석한다. 저장·incremental·실제 progressive HTTP 회귀20개와 해당 두 메서드 실행 줄 관측8/8(100%, 전체 파일/분기 커버리지 아님)을 확인했다.

## 회귀·보존·적용 조건

후보로 교체한 표시/회복/재시작/reader/RMS 회귀24개와 저장/HTTP 회귀20개를 Pi에서 통과했다. 같은 공개 합성 fixture 경로로 새 RMS 검사5개도 별도 통과했다. 원본 journal을 바꾸지 않고 fingerprint를 명시 변환하는 전환 리허설에서 cursor·확정 event_id·정지 이력이 보존됐고 중복0이었다. 새 unit은 Pi systemd-analyze 검증을 통과했다.

이전 `mes-progressive-eval-20261024-v2`와 원본 r6/profile/결과 ZIP을 보존했다. 이번 개발/평가/실패·성공 측정은 별도 `rms-confirmation-20261024` 아래에 둔다. 원본 모델 모듈과 실제 PDA 파일은 변경하지 않는다. 적용·STOP·복구 절차는 [운영 적용 가이드](../guides/mes-rms16-deployment.md)에 있다. 기존 경보 또는 확정 AI 이력이 있으면 새 실행으로 지우지 않도록 MES 전환을 보류한다.

이 평가는 공통 정상 생성기·센서 범위를 공유하는 합성 시험이다. 실기 계산/전달/화면 기능은 검증했지만 실측 고장 일반화나 고장 원인 분류의 증거는 아니다. 실제 설비 자료 검증은 남아 있다.
