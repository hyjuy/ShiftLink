## 1. 프로젝트 개요
- **프로젝트명** : ShiftLink — 현장의 경험을 다음 교대와 다음 세대로 연결하는 온디바이스 지식 에이전트
    - 기술 정의: 베테랑의 암묵지 후보를 합성 데이터로 구조화하고, 근거·검증·승인 절차를 거쳐 회사가 보존하고 재사용할 수 있는 조직 지식으로 전환하는 온디바이스 현장 에이전트. 포터블 MES 보조 계층을 지향하되, 공식 MES/CMMS를 대체하거나 확정 상태를 변경하지 않는다.
    - "Link"는 두 가지 연결을 뜻한다. ① 세대 간 연결(베테랑 → 신입·저년차), ② 교대 간 연결(전 교대 → 다음 교대)
    - 공식 MES/CMMS에 쓰지 않는 읽기 전용 보조 계층이다. 공식 작업 상태를 바꾸지 않고, 근거를 붙인 제안까지만 한다.

## 2. 문제 정의
- 현장 장비 관리에서는 작업자마다 사용하는 용어와 기록 수준이 달라, 동일한 증상과 조치에 관한 경험을 일관되게 축적하고 활용하기 어렵다는 것을 문제 가설로 설정한다. 특히 숙련자의 판단 근거, 작업 요령, 적용 조건이 충분히 기록되지 않으면 신규 작업자는 기존 기록과 매뉴얼만으로 업무 맥락을 이해하기 어렵다. 또한 작업 과정에서 얻은 경험이 매뉴얼 개선으로 연결되지 않아, 유사한 상황에서도 개인의 기억과 구두 설명에 의존할 수 있다. 본 프로젝트는 이러한 기록의 불일치와 지식 전달의 단절을 줄이는 데 초점을 둔다.

이때 기록되지 않는 지식은 감각 기반 이상 징후 판단, 조건부 요령, 트러블슈팅 순서, 인수인계 맥락, 안전 금기의 다섯 유형(T1~T5)으로 나눌 수 있으며, 본 프로젝트는 이를 근거와 적용 조건이 붙은 지식 카드로 구조화해 신입·저년차·교대 근무자가 필요한 시점에 꺼내 볼 수 있게 하는 데 초점을 둔다. 다만 합성 결과를 실제 베테랑의 확정 지식으로 주장하지 않으며, 초기 데이터 부족 문제를 합성 시나리오로 완화하고 제한된 숙련자의 시간을 인터뷰가 아닌 고가치 검증에 집중시키는 것이 본 접근의 목적이다.

본 MVP에는 외부 숙련자 자문과 실제 전문가가 작성·검수한 평가셋이 없다. 숙련자 검증에 집중한다는 문장은 향후 운영 방향이며, 이번 검증은 팀 검수와 AI 평가를 통한 합성 지식의 구조화·검색·인계 품질에 한정한다. 실제 암묵지의 외재화, 신입 판단 능력 향상, 현장 생산성 개선은 측정·입증하지 않았다.

## 3. 구현 목표
### 3.1 공통 원칙·범위
- 가상 냉연 코일 처리 라인 L1의 공용 설비(유압 유닛 HPU, 구동 모터·감속기 GR, 롤러 테이블 RT, 컨베이어 CV)를 대상으로, 신입(S1)·저년차(S2)·교대(S3) 세 시나리오를 "라인 하나의 하루"로 이어 구현·시연한다. 설비 사전의 정상 범위·임계치 수치는 전부 가상 값이며 그 사실을 명기한다.
- 에이전트는 공식 MES/CMMS 상태를 변경하지 않는 읽기 전용 보조 계층으로 동작한다. 모든 응답은 지식 카드·설비 사전·인계 기록의 ID를 인용하고, 근거가 없으면 "해당 지식 없음"으로 응답한다. 안전 금기(T5) 카드는 검색 순위와 무관하게 항상 우선 노출하며, 안전 판단은 숙련자·관리자 확인으로 넘긴다. **[P1~P5 전문가1 원문 확인 필요]**
- 합성 결과를 실제 베테랑의 확정 지식으로 주장하지 않는다. L0·L1 지식은 실제 작업지시로 제공하지 않고, 안전·품질·설비 정지 관련 내용은 승인된 표준절차와 인간 책임자를 우선한다. MVP에서 에이전트가 인용하는 카드의 최고 등급은 L1(시뮬레이션 검증)이며, 응답에 등급을 함께 표시한다(4.10).
- 추론·검색·인계 저장·감사 로그는 Jetson 로컬에서 수행하고 외부 추론 API에 의존하지 않는다. 사용자 수정 지시에 따라 하루 1회 클라우드 DB에 업로드하는 요구를 반영하며, 프로젝트 저장소는 Aiven Cloud MySQL을 유지한다(입력 표기: `avien cloud mysql`). 기존 4.11의 PC만 접속·Jetson 외부 미접속 조건과 충돌하므로 전송 주체·허용 필드·원문 포함 여부는 #4에서 추가 결정한다. 클라우드 접속이 끊겨도 로컬 분석·저장·재시작은 가능해야 한다.
- **MVP 범위 제외**: PLC·안전장치·설비 직접 제어 / 검증되지 않은 자동 파라미터 변경 / 안전·품질·수리의 최종 판정 대행 / 실제 MES·CMMS의 확정 상태 자동 변경 / 예지보전, 음성·OCR·3D, 다중 단말 실시간 동기화 / 상용 현장 성능이나 다운타임 절감 효과의 단정.
장비 입력값과 확인 상태는 4.8의 ‘사용자 제공 장비 현황’을 따른다.

### 3.2 지식 데이터 파이프라인 목표
- 공개 기술자료를 시드로 삼아 설비 사전 → 베테랑 페르소나 → 사건·지식 원장(ground truth) → 산출물 생성 → 품질 검증 → 분할·버전 단계를 명령 한 번으로 재생성할 수 있는 합성 데이터 파이프라인을 구현한다.
- 암묵지 유형 T1(감각 기반 이상 징후 판단)·T2(조건부 요령)·T3(트러블슈팅 순서)·T4(인수인계 맥락)·T5(안전 금기)별로 지식 카드(K-01) 150건 이상, 인터뷰 Q&A·작업 메모·인계 로그·트러블슈팅 사례·조건부 판단 규칙 등 산출물 400건 이상을 생성하고, pydantic 스키마 검증·규칙 검사·교차 LLM-judge·사람 검수를 통과한 것만 채택한다. **[T1~T5 정의: 전문가1 원문 확인 필요]**
- 원천 근거(시드)와 합성 산출물을 물리적·논리적으로 분리하며, 생성 모델의 답변을 다시 근거 문서나 다음 생성의 시드로 사용하지 않는다. 모델이 만든 숫자·임계치·부품명은 근거가 없으면 삭제하거나 명시적 가상값으로 표시한다.
- 사건 단위로 지식베이스용과 평가용을 분리하고, 봉인 평가셋 60건(질의 36·인계 24, 안전 서브셋 12건 포함)은 3주차 채점 전까지 해시로 봉인한다. 개발 중 반복 채점용 개발셋 30건은 별도로 둔다. 생성 모델·평가(judge) 모델·온디바이스 추론 모델은 서로 다른 계열을 쓴다.
- 합성 결과가 실제 현장 성능을 뜻하지는 않는다. 파이프라인의 목표는 실제 노하우 데이터가 확보됐을 때 같은 스키마·검증 절차로 교체 투입할 수 있는 재현 가능한 틀을 만드는 것이다.

### 3.3 모델·에이전트 목표
- 베테랑 노하우를 지식 카드(K-01: T1~T5 유형·설비·적용 조건·근거·출처 ID 포함)로 구조화하고, 온디바이스 검색(RAG)으로 에이전트에 반영한다. 모델 가중치 재학습은 선택 항목으로 두며, 수행하더라도 응답 형식 고정에 한정한다. 계획서·발표에서 "모델이 노하우를 학습했다"는 표현은 쓰지 않으며, SFT를 실제로 수행한 경우에만 "응답 형식 미세조정(LoRA)"으로 한정해 표기한다.
- 에이전트는 공용 파이프라인 위에 질의 모드(설비·증상 질의 → 카드·매뉴얼 근거 제시)와 인계 모드(메모 → 인계 항목 후보 추출·대조)를 제공한다. 두 모드 모두 응답에 근거 카드 ID와 등급을 인용하며, 근거가 없으면 "해당 지식 없음"으로 응답한다.
- 소형 모델(플랜 B/C)에서도 출력 안정성을 확보하기 위해 라우터 + 고정 파이프라인 구조를 채택한다. 모델 호출은 요청 1건당 1회(구조화 검증 실패 시 재시도 1회 예외)를 기본으로 하고, 구조화 출력은 JSON 스키마 강제와 pydantic 검증·재시도로 보장한다.
- 출처 없음, 문서 만료, 문서 충돌, 자료 부족 상황에서는 생성형 답변을 보류하고 승인된 비상 절차 또는 담당자 호출을 우선한다.

### 3.4 인계 모드 목표 (기존 F-02~F-06 흡수)
- 작업자 메모의 후속 요청 추출(F-02) → 기존 작업·인계 목록 대조(F-03) → 근거 제시·사용자 검토(F-04)를 인계 모드로 구현한다. 인계 항목은 "등록 후보"로만 제안하고 사용자 수락 후 저장한다.
- 수락·수정한 인계 항목은 항목 ID를 유지한 채 다음 교대까지 보존하며(F-05), 원문이 정정·철회되면 자동 종료 대신 재검토 표시를 남긴다.
- 정상·예외(E-01~E-03)·자료 부족(D) 시나리오와 규칙 기반 Baseline 대비 인계 누락·오연결 개선을 검증한다(F-06).

### 3.5 평가·성능 목표
- 기준선 (0) 모델 단독 / (1) 매뉴얼만 검색 / (2) 지식 카드 포함 검색 / (3, 선택) 형식 SFT 적용 모델을 같은 봉인셋으로 비교한다. 인계 모드는 규칙 기반 Baseline과 추가 비교한다.
- 지표: 근거 적중(Recall@k), 근거 충실도, 조건 불일치 카드 오적용, 안전 금기 누락 0건, 지식 없음 처리율, 인계 누락·오연결(규칙 Baseline 대비), p95 지연, 발열 상태 처리량.
- 목표 지연은 플랜 B(Qwen2.5-3B) 기준으로 신규 요청 1건 p95 15초 이하, 카드 조회 2초 이하로 하며, 네트워크 차단 상태에서도 신규 분석·재시작이 가능함을 확인한다. 현재 제공된 전력 모드는 25W다. 25W 실측을 별도 기록하고, 기존 15W 계획과의 비교는 실제 모드 지원 여부를 확인한 뒤 같은 조건에서 수행한다(4.8).
- 현재 공개할 평가는 팀 검수·서브에이전트 평가를 거친 합성 평가셋의 점수다. 실제 전문가가 작성·검수한 평가셋은 없으며 그 점수는 ‘미보유·미측정’으로 표시한다. 향후 확보 시 합성셋 결과와 분리하여 보고한다. 현장 시간 절감, 다운타임 감소, 사업성은 이번 합성 실험만으로 주장하지 않는다.

### 4.3.1 방식별 캘리브레이션 부담

- **GGUF Q8_0**: 캘리브레이션 없이 바로 변환, FP16에 거의 근접한 품질 — 가장 손 안 대고 쓰기 좋음
- **bitsandbytes INT8**: 학습/추론 라이브러리 호환성 확인 필요 (weight-only)

    **4.7.4 지식 카드 K-01 스키마 (pydantic) [카드 공통 속성: 전문가1 원문 확인 필요]**
- 필수 필드: `card_id`(K-0001), `version`, `grade`(L0/L1/L2/L3), `tacit_type`(T1~T5), `equipment`(HPU/GR/RT/CV/COMMON), `component`, `scenario`(S1~S3), `title`, `symptom`(T1/T3 필수), `know_how`, `rationale`, `conditions[]`(signal·op·value), `exclusions[]`, `safety_flag`, `safety_basis`(안전 카드 필수), `conflict_group`, `confidence`, `provenance`(seed_ids·persona_id·event_ids·generator·generated_at), `split`(kb/dev/sealed), `status`(draft/accepted/rejected_rule/rejected_judge/rejected_human/rejected_safety)
- 검증 규칙: T5 → `safety_flag=True` 필수 / `safety_flag` → `safety_basis` 필수 / T1·T3 → `symptom` 필수 / T2 → `conditions` 1개 이상
- 사건(`Event`): `event_id, scenario, equipment, timeline[], true_cause, true_actions[], measurements{}, cards_expected[], split`. 분할은 Event에서 결정하고 카드·산출물이 상속
- 산출물 5종 공통 필드: `artifact_id, kind, event_id, card_ids[], persona_id, text, split, status` + 종류별 필드(인계 로그: `shift_from/shift_to/open_items[]`, 조건부 규칙: `if/then/unless`)
- **승인 반영:** `grade`는 독립 필드로 추가한다. `status`는 처리 상태, `grade`는 지식 검증 수준이며 서로 구별한다. MVP에서 `accepted` 카드는 검증 게이트를 통과한 `grade=L1`이어야 하며 L2·L3로 승격하지 않는다.
- **검토 대기(#16):** 중지 조건·예상 결과·유효기간·검증자·적용 범위와 전문가1의 D-27~D-29 구조 변경은 별도 결정한다. 아래 전문가1 페이지를 대조했으나, 그 페이지도 T1~T5 원 정의·P1~P5·공통 속성의 원전은 미확인이라고 명시한다.
- 전체 코드는 `고도화_전문가2_파이프라인.md` 4.7.4 참조

**4.7.5 품질 검증 지표·합격 기준**

| 검사 | 방법 | 합격 기준 |
| --- | --- | --- |
| 스키마 | pydantic 검증 | 채택 레코드 100% 통과 |
| 참조 무결성 | `event_id`·`card_ids`·`component`·`signal`이 원장/설비 사전에 존재 | 100% |
| 물리·설비 모순 | 설비 사전의 가상 정상 범위·상태 전이표(정지 상태에서 압력 상승 등 불가 조합)와 대조 | 위반 0건(위반 시 `rejected_rule`) |
| 안전 위반 | 금기 사전(예: 가압 상태 배관 분리, 운전 중 롤러 접근, 잠금 없이 정비)과 키워드+judge 이중 검사 | 채택 레코드 중 위반 0건, T5 카드 100% 사람 검수 |
| 교차 LLM-judge | 생성 모델과 다른 계열 모델이 `근거 타당성 / 조건 명시성 / 페르소나 일관성 / 안전` 4항목 1\~5점 | 4항목 평균 ≥ 4.0, 안전 항목 5점 아니면 보류 |
| 사람 검수 | 전혜민·최재영 이중 검수 | 봉인 평가셋 100%, T5 100%, 나머지 20% 층화 샘플(T×설비). 검수자 간 일치 ≥ 0.8(단순 일치율) |

| 다양성 | T1\~T5 × 설비 4종 커버리지 매트릭스, 산출물별 distinct-2 | 매트릭스 빈칸 0(CV는 선택이므로 제외 가능), distinct-2 ≥ 0.6 |
| 근거·가설 표시 | 행동 권고(`know_how`)에 `provenance`와 등급 표시가 있는지 | 100% |
| 불확실성 표현 | 정보 부족 사건(D)에서 원인을 단정하지 않는 비율 | 목표 95% 이상 |

- 채택 순서: 스키마 → 규칙 → 중복 → judge → 사람. 앞 단계 탈락은 뒤 단계로 보내지 않는다.
- 판정 결과는 레코드에 `status`로 남기고 폐기 레코드도 원장에서 지우지 않는다(재현성).
- 안전·설비 정지·품질 판정·임계치 변경 항목은 100% 검수한다.

**4.7.6 누수 방지·봉인**

- 분할은 사건 단위: `kb`(지식베이스·개발) / `dev`(개발 중 채점) / `sealed`(봉인 평가). 같은 사건에서 나온 카드·산출물은 같은 분할에만 속한다. 동일 원문·설비·사건 템플릿에서 파생된 데이터는 하나의 그룹으로 분할한다.
- `sealed` 사건의 카드는 K-01 베이스에 넣지 않는다. 대신 정답지(`cards_expected`)로만 쓴다. 단, 평가 문항이 참조해야 하는 "일반 지식"은 `kb` 카드에서 뽑아 `expected_card_ids`로 지정한다("근거 적중" 채점 근거).
- 봉인: 2주차 말 `sealed.jsonl`의 sha256을 `manifest.json`과 MySQL `dataset_version`에 기록하고 Git 태그(`data-v1.0-sealed`)를 찍는다. 3주차 채점 전까지 열람 금지, 채점 시 해시 재검증.
- 모델 분리: 생성 모델 ≠ judge 모델 ≠ 온디바이스 추론 모델(Qwen2.5-3B/7B, EXAONE-3.5). 온디바이스 후보 계열은 judge로 쓰지 않는다(자기 평가 편향).
- 형식 SFT(4.8 선택 항목)를 수행할 경우 학습 데이터는 `split=kb` 산출물에서만 추출하고 `dev`·`sealed`와 겹치지 않음을 해시로 확인한다.

**4.7.10 발표 전략**

- 재현성 시연: `python -m shiftlink.data all --seed 42 --version demo`는 계획된 실행 인터페이스다. 저장된 `raw/` 입력을 재생하는 결정적 후처리의 산출물 해시를 검증하고, 새 LLM 호출은 별도 실행으로 버전·품질·해시를 기록한다. seed 고정만으로 새 생성의 바이트 동일성을 보장하지 않는다. `generated_at`·`run_id` 등 가변 메타데이터와 비교용 정규화 본문의 해시 범위를 구분한다.

- 스토리 연결: "라인 하나의 하루"(S1→S2→S3) 데모에서 인용되는 카드 ID를 대시보드에서 역추적해 사건 원장까지 보여 준다. 데모 연출 골격은 다음 7단계를 따르되, 사용할 사건(EV-xxxx)은 2주차 원장 완성 후 정한다: ① 교대 중 이상 징후 발생 ② 이전 교대의 메모·임시 조치는 있으나 공식 인계 미등록 ③ ShiftLink가 카드·인계 기록을 검색하고 근거·등급 표시 ④ 원인을 단정하지 않고 확인 순서 제시 ⑤ 승인 없는 설정 변경 금지와 지속 시 반장 호출 조건 표시(T5 선두) ⑥ 점검 결과 입력 → 다음 교대 인계 후보 생성 ⑦ 카드 추가 → 답변 변화 시연.
- 발표 메시지: "우리는 없는 노하우를 진짜라고 주장하지 않는다. 공개 절차와 공정 규칙으로 현장 판단 가설을 생성하고, 출처·불확실성·검수 상태를 추적해 검증 가능한 조직 지식 후보로 전환한다." 차별점은 모델 자체가 아니라 데이터 계보, 안전 게이트, 실패 데이터, 인간 피드백, 버전 관리까지 포함한 지식 생산·운영 시스템이다.

| BAAI/bge-m3 (Ollama `bge-m3`) | 카드 미기재 | 1024 | 8192 토큰 | Ollama 파일 1.2GB, 플랜 B 한정 대안 |

- 벡터 저장소: sqlite-vec 1차(순수 C, 무의존성, pre-v1이므로 버전 고정), 대안 FAISS `IndexFlatIP`. Chroma는 규모 대비 과해 제외. 플랜 A처럼 임베딩 모델 상주 여유가 부족할 수 있는 조건에서는 SQLite FTS5 키워드 검색을 대안으로 검토한다(codex 9절).
- 검색: 메타데이터 필터(설비 ID·유형·`status=accepted`·`split=kb`·`grade=L1`) → 벡터 유사도 상위 k(3~5). 해당 설비·조건의 T5 카드는 일반 top-k와 별도로 확인해 응답 선두에 병합한다. 순위 재배열만으로 안전 카드 존재 확인을 대신하지 않는다. T5 외 모든 `safety_flag=True`로 이 기준을 확장하는 D-26은 승인 대기이며, 현재 기준의 누락 위험은 안전 담당자가 우선 검토한다.
- 구조화 출력: Ollama `format`에 pydantic JSON 스키마 전달 → 검증 실패 시 온도 0으로 1회 재시도 → 재실패 시 사용자 검토 큐. llama.cpp 전환 시 GBNF/`json_schema`로 동일 강제. 스키마는 출력만 제약하므로 프롬프트에도 스키마 설명을 넣는다
- 에이전트 구조: 라우터 + 고정 파이프라인 (소형 모델 멀티스텝 도구 호출 대신)
    1. 규칙 라우터: 입력 형식(메모 vs 질문)·키워드로 질의/인계 모드 판정(모델 호출 없음)
    2. 고정 도구 실행(코드): 설비 사전 조회 → 지식 카드 검색 → (인계 모드) 기존 인계 목록 조회 → 점검 체크리스트 조회
    3. 모델 1회 호출: 도구 결과를 컨텍스트로 근거 인용 답변 또는 인계 후보 JSON 생성
    4. 코드 검증: 인용 ID가 실제 검색 결과에 있는지 확인, 없으면 "지식 없음"으로 치환. 인용 카드의 등급(4.10)을 응답에 부착

- 발열·지연 대응
    - 질의당 모델 호출 1회 원칙(라우팅·검증은 코드), 컨텍스트 2048 토큰 상한, 검색 결과 k≤5·카드당 300자 이내로 절단
    - 카드 임베딩은 인덱싱 시 사전 계산. 질의 임베딩 후 Ollama로 구동하는 임베딩 모델은 `keep_alive: 0`으로 언로드하거나 플랜 B에서 상주를 비교한다. 다른 런타임은 해당 방식에 맞게 언로드·메모리 회수를 검증
    - LLM은 `keep_alive: -1`로 상주해 재로딩 발열 방지
    - 동일 질의·동일 검색 결과 조합은 응답 캐시(해시 키) 적용, 데모 반복 시 재추론 회피
    - `OLLAMA_NUM_PARALLEL` 기본 1 유지, 동시 요청 큐잉
    - jtop 온도 임계 접근 시 4.3 전환 기준에 따라 하위 플랜 전환. 전환 시 임베딩 모델은 유지(재인덱싱 불필요)
    - VLM·음성인식 등은 범위 밖이며, 도입하더라도 LLM과 동시 상주시키지 않고 순차 실행한다
- 추론 런타임은 원 계획서의 Ollama를 유지하고 llama.cpp 직접 구동은 전환 옵션으로 둔다. 설치 호환성·CUDA 가속·텍스트 처리 성능은 실제 JetPack과 모델 조합으로 확인한다. 기존 ‘NanoLLM 대비 약 절반 성능’은 동일 조건 측정 근거가 없어 성능 판단에 사용하지 않는다.
- 모델 가중치 재학습(선택, 3주차 RAG 안정 시): 목적은 지식 주입이 아니라 응답 형식 고정(카드 인용 형식, "지식 없음" 응답, 인계 항목 JSON)에 한정. 학습 장소: 사용자 제공 `4080 super 16기가 | 구글 colab t4` 환경을 우선 확인한다. GPU 가용 시간·메모리·실제 할당 상태는 실행 시 기록한다. Unsloth는 Colab/Kaggle 무료 노트북에서 3GB VRAM부터 QLoRA를 지원한다고 명시. 데이터 규모: 합성 질의응답 200~500쌍(추정), `split=kb`에서만 추출. 예상 소요: 데이터 정제 1일, 학습·GGUF 변환 0.5일, chat template·EOS 검증 및 Ollama 재테스트 1일(추정, 총 2.5일). 배포: Unsloth `save_pretrained_gguf(q4_k_m)` → Ollama `Modelfile` `FROM ./model.gguf` → 플랜 B(Qwen2.5-3B)에만 적용, A/C는 원본 유지. 가장 큰 위험은 "잘못된 chat template"이며 검증 실패 시 즉시 원본 GGUF로 복귀. 넣지 않는 게 나은 이유(현재 판단): P1/P2 보장에 기여하지 않고, 학습 성공과 최소 개선 기준이 아직 확인되지 않았으며, 3주차 평가 일정에 재배포 리스크를 얹는다. 3주차 시작 시점에 RAG 기준선이 안정되어 있을 때만 착수한다.

- 4.3 모델 비교 시 참고 요청된 저장소: karpathy/autoresearch. 참고 링크로 보존하며 도입·실행 완료를 뜻하지 않는다.

### 4.9 지식 반영·평가 기준선 (추가)
- 기준선: (0) 모델 단독 / (1) 매뉴얼만 검색 / (2) 지식 카드 포함 검색 / (3, 선택) 형식 SFT 적용 모델 / 인계 모드는 규칙 기반 Baseline 추가 비교
- 지표·목표 (목표치는 설계 목표(추정)이며 팀 확정 필요)

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| Recall@k | 정답 카드가 상위 k에 포함된 비율 | k=5에서 0.8 이상 |
| 근거 충실도 | 답변 문장이 인용 카드 내용과 일치하는 비율(정답지 대조) | 0.9 이상 |
| 조건 불일치 카드 오적용 | 적용 조건이 다른 카드를 인용한 건수 | 봉인셋 기준 5% 이하 |
| 안전 금기 누락 | T5 카드가 있는 사건에서 미노출 건수 | 0건 |
| 근거 없는 위험 조치·무권한 실행 | 근거 ID 없는 행동 권고 또는 읽기 전용 위반 | 0건 |
| 지식 없음 처리 | 카드 없는 질의에 "지식 없음" 응답 비율 | 0.95 이상 |
| 인계 누락·오연결 | 규칙 Baseline 대비 | 누락 감소, 오연결 비증가 |
| p95 지연 / 조회 지연 | 신규 요청 1건 / 카드 검색 (플랜 B 기준) | 15초 / 2초 |
| 발열 상태 처리량 | 사용자 제공 25W 모드에서 연속 20건 처리 시 건당 지연·온도 | 측정·보고(목표 미설정) |
| 오프라인·복구 | 네트워크 차단 상태 실행률, 재시작·재동기화 성공률, 감사 로그 완전성 | 측정·보고 |

- p95 15초·조회 2초 유지 근거: RAG 추가 시 검색(임베딩 1회 + sqlite 조회)은 2초 안에 들어오고, 모델 호출 1회 원칙이면 15초 안에 들어온다(추정). 단 플랜 A는 임베딩 모델 동시 상주가 어려워 목표 달성 보장이 없으므로, 목표 지연은 플랜 B 기준으로 명시한다.
- 현재 공개할 평가는 팀 검수·서브에이전트 평가를 거친 합성 평가셋의 점수다. 실제 전문가가 작성·검수한 평가셋은 없으며 그 점수는 ‘미보유·미측정’으로 표시한다. 향후 확보 시 합성셋 결과와 분리하여 보고한다.

| L0 합성 가설 | AI가 생성한 검증 전 노하우 후보 | 데이터 개발·검수 화면 | `draft`, `rejected_rule`/`rejected_judge`/`rejected_human`/`rejected_safety`(폐기, 원장 보존) | 예 |
| L1 시뮬레이션 검증 | 가상 공정 규칙에서 모순·위험 여부 확인 | 교육·시뮬레이션·데모 | `accepted`(스키마→규칙→중복→judge→사람 검수 전부 통과) | **예 (MVP 최고 등급)** |
| L2 전문가 승인 | 숙련자가 적용 범위와 조치를 승인 | 현장 작업 지원 | (신설 필요) `approved_expert` | 아니오(범위 밖) |
| L3 현장 검증 | 실제 운용 결과로 유효성을 확인 | 조직 표준 지식 | (신설 필요) `field_validated` | 아니오(범위 밖) |

- 필수 원칙: 합성 결과를 실제 베테랑의 확정 지식으로 주장하지 않는다. L0·L1 지식은 실제 작업지시로 제공하지 않고, 안전·품질·설비 정지 관련 내용은 승인된 표준절차와 인간 책임자를 우선한다.
- 에이전트 검색 대상 = `status=accepted AND split=kb AND grade=L1`. `sealed`·`dev` 사건의 카드는 등급과 무관하게 검색 대상이 아니다(4.7.6).
- 에이전트 응답은 인용 카드마다 "L1 합성·시뮬레이션 검증"을 표시하고, 데모 화면에 "실제 작업지시 아님" 문구를 상시 표시한다.
- 팀원의 사람 검수(전혜민·최재영), 허재원의 팀 내 안전 검토 및 서브에이전트 평가는 도메인 숙련자 승인이 아니므로 L2로 표기하지 않는다. L2·L3 전이에 필요한 속성(검증자, 적용 범위, 유효기간과 버전)은 향후 확장 항목으로 데이터 카드에 기록한다.
- 현장 피드백 반영 시 기존 합성 지식을 덮어쓰지 않고 상위 버전이 대체한 관계를 보존한다(범위 밖 설계 원칙).

### 4.11 저장 아키텍처 (신설, 구 4.7.9 흡수)

**반영 원칙:** Aiven Cloud MySQL은 이력·분석용으로 유지하고 로컬 JSONL/CSV를 원본으로 둔다. 하루 1회 업로드 요구는 반영하되, 기존 조건부 승인과 상충하는 전송 주체·허용 데이터는 #4의 미결 사항이다. 현 프로젝트는 가상 데이터만 사용하며 Aiven Cloud를 실제 사내망 DB와 동일한 것으로 간주하지 않는다. 아래 표의 제한은 종전 승인 범위이고, 직접 Jetson 전송·원문 업로드가 추가 승인됐다는 뜻은 아니다.

| 경로 | 위치 | 저장 내용 | 외부 접속 |
| --- | --- | --- | --- |
| **런타임(Jetson)** | 로컬 파일·SQLite | 채택 `kb` 카드, 설비 사전, 인계 항목, 검토 큐, 응답 캐시, 감사 로그(4.12) | 추론·검색에 외부 의존 없음. 하루 1회 업로드의 직접 전송 여부는 #4 미결 |
| **파이프라인 개발(PC)** | 로컬 JSONL/YAML + Git | `seeds/`(원천 근거), `ledger/`·`artifacts/`(합성 산출물, 물리 분리), `raw/`, `qc/`, `splits/`, `manifest.json` | 생성 단계 외부 API는 4.7.8 결정에 따름 |
| **이력·분석(Aiven MySQL)** | 클라우드 | 아래 7개 테이블 — ID·해시·지표·메타만. 원문·judge 코멘트 미적재 | 기존 승인안은 PC에서 접속. 일일 전송 주체는 #4에서 결정, 접속 정보는 환경 설정으로 분리 |

| 테이블 | 주요 컬럼 | 용도 |
| --- | --- | --- |
| `pipeline_run` | run_id, version, stage(P1\~P6), started_at, ended_at, git_commit, generator_model, judge_model, seed, status | 실행 이력 |
| `dataset_version` | version, split, record_count, manifest_sha256, sealed_at, sealed_by | 버전·봉인 증빙 |
| `record_index` | record_id, kind(card/event/artifact), version, split, tacit_type, equipment, persona_id, safety_flag, status, content_sha256 | 원문 없이 ID·해시·메타만 |
| `quality_metric` | run_id, metric_name, scope(all/T1..T5/equipment), value, threshold, passed | 4.7.5 지표 |
| `judge_log` | record_id, judge_model, criterion, score, run_id | 교차 검증 점수(코멘트 원문 미적재) |
| `human_review` | record_id, reviewer(코드값), decision, reason_code, reviewed_at | 검수 이력 |
| `eval_result` | run_id, item_id, mode(query/handover), metric(근거적중/조건불일치/안전누락/지식없음), value, model_plan(A/B/C) | 3주차 채점 결과 |

**기존 승인 조건과 일일 업로드 수정 요구의 경계**

1. MySQL 적재는 **가상 데이터(가상 라인 L1·가상 페르소나·가상 수치)에 한정**한다. `record_index.equipment`·`persona_id`는 가상 코드값이므로 실제 설비명·인적 정보가 아니다.
2. `human_review.reviewer`는 실명이 아닌 코드(R-01 등)로 적재한다.
3. 종전 승인안은 Jetson 외부 저장소 미접속이다. 사용자 수정 요구는 하루 1회 업로드이므로 PC 경유인지 Jetson 별도 배치 전송인지 추가 결정한다. 오프라인 시 전송 실패가 분석·저장을 중단시키지 않아야 한다. 미전송 기록 보존, 재시도·중복 적재 방지, 충돌 시 자동 덮어쓰기 금지는 일일 업로드 설계의 검토 기준으로 둔다.
4. **실제 현장 데이터로 시드를 교체하는 시점에는 MySQL 적재를 중단하거나 사내 DB로 교체한다.** 이 조건을 데이터 카드에 명시한다.
5. 상위 계획서 4.4·4.5에서 Aiven Cloud MySQL 명시를 확인했다. 로컬 SQLite 단일화는 현재 선택안이 아니다. 4.4·4.5의 처리 결과·로그 적재에는 이 절의 가상 ID·해시·지표·메타 제한을 함께 적용하며, 이를 넘어서는 일일 업로드 범위는 미결이다.

### 4.12 안전·권한·감사 (신설)
- 역할(데모 시나리오 S1~S3에 대응): 신입·저년차 — 조회, 체크리스트 수행, 기록 초안 / 숙련 작업자 — 지식 제안, 검토, 일부 조치 확인 / 반장·관리자 — 작업 승인, 인수인계 확정 / 정비·안전 담당 — 고위험 절차 승인 / 시스템 관리자 — 모델과 지식 버전 배포. MVP에서는 역할별 인증을 구현하지 않고 UI 라벨로만 구분한다.
- 감사 로그(로컬): 모든 도구 호출에 사용자, 시간, 장치, 입력, 검색 근거, 모델 버전, 도구 인자, 결과, 승인자를 기록한다.
- LLM은 PLC나 안전장치에 직접 명령하지 않으며, 위험 작업은 규칙 기반 차단과 인간 승인을 거친다.
- 출처 없음, 문서 만료, 문서 충돌, 자료 부족 상황에서는 생성형 답변을 보류하고 승인된 비상 절차 또는 담당자 호출을 우선한다.
- T5 카드의 `safety_basis`는 산업안전보건기준에 관한 규칙 제92조(정비 등의 작업 시의 운전정지), KOSHA GUIDE M-101-2012, OSHA 29 CFR 1910.147 중 하나 이상을 지침 번호·조문 번호로 명기한다. 안전 관련 상충은 보수적인 쪽만 채택한다.
- 안전 검수 책임자는 허재원이다. 전혜민·최재영의 데이터 검수와 다른 페르소나의 서브에이전트 평가를 결합한다. 외부 숙련자 자문은 불가능하므로 팀 내 수락은 교육·시뮬레이션 데이터 채택에 한정하며 실제 작업 승인이나 L2 전문가 승인으로 표기하지 않는다. 구체적인 검수 기록 양식·이견 해소 절차는 착수 전 정리한다.

### 6.2 전문가1 도메인·지식경영 검토
[ShiftLink — 전문가1 도메인·지식경영 검토 (원문취급)](https://app.notion.com/p/3d8b7d115dd18099bba4fb418854cdcc)는 요청한 위치에 이미 존재하므로 원문을 보존했다. 해당 검토문의 신규·반박·보강 의견을 전체 대조했고, 그 문서가 원전 미확인으로 남긴 부분까지 확인 완료로 바꾸지는 않았다.
전문가1 검토의 핵심은 지식 접근 실패와 적용 조건·인계 맥락 손실을 구분하고, 안전 카드 분류·노출·검수 기준을 일치시키며, 검색 품질과 사용자의 판단 향상 효과를 구별하자는 것이다. 이 해석은 검토 의견이며 실제 현장 효과의 증거가 아니다.
D-26~D-37은 모두 명시적 승인 근거가 없어 **승인 대기**다. 기존 승인 기준을 대체하지 않는다.

| ID | 제안 | 처리·확인 사항 |
| --- | --- | --- |
| D-26 | 안전 노출·채점 기준을 safety_flag=True로 확대 | 안전 누락 위험 우선 검토. 승인된 T5 규칙을 대체한 것으로 표시하지 않음 |
| D-27 | T4 전달축 분리 또는 content_type 필수화 | 스키마·커버리지·최소 건수·정답지 동시 개정 필요 |

- U-6: T1~T5의 원 정의문 및 포함·제외 기준은 미확인이다. 현재 하위 페이지의 경계 판정 규칙은 새 검토 의견이다.

### 6.3 이번 작성·검토 이력
2026-09-11에 승인 매핑, 전문가1 도메인·지식경영, 온디바이스 기술 정합성을 각각 서브에이전트로 병렬 검토했다. 작성자는 승인 메모와 원문을 대조하여 본문에 반영하고 미결 항목을 분리했다. 서브에이전트 검토는 문서 검토이며, 실제 도메인 숙련자 검증·장비 시험·L2 전문가 승인이 아니다.
주요 해소 사항은 부제/기술 정의 분리, 문제 정의·4.1~4.6 전체 수록, grade 추가, GPU 현황 갱신, 안전 담당 지정, 전문가 평가셋 부재 표시, T5 별도 조회, 재생과 새 생성의 검증 구분이다. #4 업로드 경로, #6 목표치 확정, #10 judge 조합, #16 원 정의, #20 임베딩 우선순위, 장비 RAM 확인은 미결로 남는다.
