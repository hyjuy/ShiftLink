2026-10-23. 기존 v14c 원본 core/settings, 과거 평가와 r1/r2/r3 릴리스를 보존하고 별도 정상 기준 후보를 만든다. 생성·적합·회귀·재생·부하 검사는 Raspberry Pi에서 실행한다. PC는 편집·Git·전송에만 사용한다. 운영 MES에 고장을 주입하거나 기존 경보를 확인·해제하지 않는다.

## 확인된 원인과 수정

기존 연구 정상 분포와 운영 합성 MES 정상 분포가 달랐다. 원인 분석용 2,902프레임에서 정상 상태인데 HPU와 두 CV에 통지가 반복됐다. 예를 들어 냉각기 오일 출구 41.513℃·냉각수 출구 27.123℃·빈 CV 대기율 0%는 구성상 정상 범위 안이지만, 연구 중심값 46.4395℃·29.9715℃·약 35%와 달랐다. 40개 선행 프레임도 good 품질·운전 중·normal 상태·해당 MES 경보 없음이었다. 생성기와 실제 물리 설비의 정상 여부를 동등하게 보지는 않는다.

## 자료 분리와 평가의 범위

[사전 계획](../research/mes-context-v1-prereg-20261023.md)의 통과 기준을 유지한다. 최종 정상 학습은 코일 부하 3군 × MesEngine/SignalDynamics 정상 경로 × 12실행 × 224프레임 = 16,128프레임이다. 초기 자료에 있던 slow/nominal/fast는 실행 구분용 배속 표식이며 물리 부하 축으로 해석하지 않는다. 모델은 모든 실행을 부하 3군으로 합쳐 적합하고 재생 배속을 입력에 사용하지 않는다.

고장은 별도 additive/hold/독립 코일 개입으로 만들며 탐지기의 PATTERNS/FaultSchedule을 사용하지 않는다. 오일/냉각수 냉각 이상, 누설, 마찰, 진동 고착, 보정 대상 출구 온도 고착, 대기율 불일치, 실제 코일 정체를 비교한다. 라벨·active_alarms를 정상 부하 선택에 사용하지 않는다. 정상 생성 일부와 구성은 공유하므로 현장 일반화의 증거로 설명하지 않는다.

개발 자료는 기존 fixture 24고장+6정상, replay fixture 24고장+6정상, 정상 전환 6실행이다. 후보와 평가 코드를 SHA256으로 고정한 뒤 코일 부하 3군 × 8개입 × 4개 독립 실행의 새 96고장, 3부하 × 2정상 경로 × 4실행의 24정상, 6정상 전환, 총 126실행·28,224프레임을 생성한다. train/개발/전환/replay개발/test의 run_id·seed·nonce 비중복을 검사한다.

정상 오통지는 별도 정상 실행의 통지 수다. 비매칭은 고장 실행에서 목표 설비·고장 시작~종료 구간에 매칭되지 않은 통지이며, 고장 전 정상 구간과 다른 설비의 통지도 포함한다. 이번 단독 개입 자료의 비매칭을 실제 파급 반응으로 단정하지 않는다. 두 수치를 합치지 않고 모두 보고한다. 지연은 합성 개입 시작 기준이며 통신·대기·PDA 렌더를 포함하지 않는다. 동일 검출 사건의 지연 차이와 전체 검출 사건의 p95는 구분한다.

## 실패 보존

첫 후보는 개발 24고장 중 5건·정상 통지 59건으로 실패했다. 조건별 통계가 추가된 v2는 21/24·정상 통지 21건이었다. 정상 자료 확장·정체값·온도 상승 보정 v3는 21/24·정상 통지 0건이었지만 CV 정상 정체값 예외가 실제 정체도 가렸고 기존 검출 사건의 지연 기준을 통과하지 못했다. v4에서 CV 독립 코일 근거와 정상 진동의 고착 창을 보완했다. 이후 1~2프레임 코일 불일치의 즉시 통지 RED를 재현하고 최종 후보에서 지속 여부를 확인하도록 고쳤다. 각 후보의 코드·profile·결과를 별도 경로에 보존한다. 미사용 평가를 만들기 전 수행한 개발 과정이다.

## 배포와 운영 경계

운영 기준은 r3-c6c8872다. PR #343이 병합된 것을 확인한 뒤 최신 main의 POSIX fsync 및 기존 동작을 통합했다. 새 후속 PR의 변경은 정상 기준 후보·profile·검증과 worker 연결이다. 기존 PDA 디자인·버튼·용어·active_alarms·확인·배지·진동은 변경하지 않는다. 같은 알람창의 무음 AI 참고 정보 계약과 정지 전 감지 이력 계약을 유지한다.

새 worker는 기존 출력 `/run/shiftlink-analytics/latest.json`과 별도 `/var/lib/shiftlink-analytics-normal-v1`을 사용한다. 기존 `/var/lib/shiftlink-analytics`와 STOP 스위치를 보존한다. 새 profile 해시가 맞아야 시작한다. 릴리스 manifest의 파일과 기존 worker unit 해시를 검사해 동시 수정 덮어쓰기를 차단한다. PDA 파일이 같으면 교체·재시작하지 않는다. 이전 unit과 state로 되돌릴 수 있도록 영구 백업을 남긴다.

실측 센서 정확도와 실제 물리 고장의 미탐 여부는 이 검증으로 확정할 수 없다. 정상 조절 상태와 같은 값으로 고착된 센서는 추가 기준 센서나 운전 변화 없이 구분하기 어렵다. 전체 경로 1초 완료와 고장→PDA 표시 p95도 별도 미검증이다.

## 자료 계약 추가 감사

학습 16,128프레임은 모두 운전 중·fault_level normal·active_alarms 0이었다. 측정 품질은 good 1,096,704건, unavailable 16,128건이며 unavailable은 `EQ-0007:rt_lift_delay`다. 이 신호를 정상값으로 채워 학습하거나 모든 69채널의 고장 검출을 검증했다고 설명하지 않는다.

의도적으로 구성한 움직이는 만재 CV fixture는 대기율 100%이며, 학습 중 `EQ-0009:cv_queue_len` 5,376개가 구성의 정상 상한 70%를 넘는다. 새 AI는 이 채널의 물리적 0~100%와 독립 코일의 이동·정체를 비교한다. 기존 MES/PDA의 70% 범위 경보 기준은 그대로이며, AI 참고 정보가 없다는 이유로 기존 경보를 지우지 않는다. 이 fixture 정의를 실제 현장의 정상 판정으로 일반화하지 않는다.

개입 평가의 대상 설비는 개입 후 104프레임 동안 모두 running 상태다. 이는 탐지기를 비교하기 위한 오프라인 조건이며 실제 MES의 자동 정지까지 포함한 폐루프 검증이 아니다. 정지 중 신규 분석을 보류하고 이미 확정한 감지만 유지하는 기존 계약은 별도 회귀로 확인한다. 순간 정지로 선행 관측이 없는 물리 고장을 AI가 반드시 포착한다는 보장은 없다.


## 배포 전 추가 실패와 의미 수정

v5의 첫 미사용 평가는 96/96 탐지·정상 통지 1·중복 0·비매칭 4·지연 p95 16프레임으로 정상 통지 0 기준에 실패했다. 이 평가와 후보는 보존하고 배포하지 않았다. 정상 압력 0.142가 일정해진 구간을 고착으로 판단했는데, 기존 정상 정체값 목록 0.143~0.156의 정확한 값만 예외 처리한 것이 원인이었다. 기존 replay 개발 자료에서도 같은 설비의 정상 압력 통지가 4번 재현됐다.

또한 `shiftlink/mes/server.py:839`의 speed 명령과 `:1042`의 `wait(1 / service.speed)`를 확인해 speed가 재생 배속임을 확정했다. 이를 물리 운전 부하로 해석했던 초기 계획을 수정했다. 최종 모델은 speed를 무시하고 독립 코일의 빈 상태·이동·대기 3군만 사용한다. v6는 이 의미를 수정한 개발 중간본이며 후보 고정 전에 다음 정체값 보완으로 대체했다.

최종 v7은 정상 학습에서 실제로 조절 정체가 관측된 채널에 한해, 같은 정상 학습 자료의 값 범위 안에서 일정하다는 이유만으로 센서 고착을 통지하지 않는다. 정상 범위 밖 고착·process 이상은 유지하고, CV는 이 예외에서 제외해 독립 코일 정체·불일치를 보존한다. 진동·출구 온도 고착도 별도 회귀로 확인한다. 학습에 사용한 정상 자료 외의 평가값으로 경계를 맞추지 않는다. 새 후보를 다시 고정한 뒤 별도 nonce의 96고장·30정상/전환 실행을 생성한다. 앞의 탐지·중복·지연 통과 기준과 표본 수는 유지한다.

## 새 실행 sequence 0의 제어 상태

검증 중 운영 MES가 외부에서 새 run `cc2477d1dbb042f6b9963d25b0046c2a`·sequence 0·stopped로 바뀌었다. 최초 독립 replay 요청은 서버가 연결을 끊어 실패했으며 로그를 보존했다. 이후 실제 조회에서 snapshots 0개·config_preserved true·is_synthetic true와 승인 config를 확인했다. sequence 0은 저장된 센서 tick이 없는 초기 제어 상태다.

이를 누락된 센서 프레임으로 처리하던 RED를 재현하고, provenance를 통과한 빈 초기 상태만 inactive/warming_up으로 보고하도록 고쳤다. 이전 run의 cursor·이력도 제거하며 센서 프레임은 만들어 넣지 않는다. 양수 sequence의 누락·역전·잘못된 trailer 거부는 유지한다. 최초 66개 회귀와 28,672프레임 일치 검사 이후 이 변경에 대해 관련 34개 회귀를 다시 통과했다. 추가 고유 테스트를 포함한 전체 고유 Python 검사는 67개다. 수정 worker의 보수적 실행 줄 커버리지는 277/343, 80.76%다.

실제 새 run 0의 독립 --once 실행은 inactive·처리된 센서 sequence -1·Torch/Timestral 미로딩으로 종료했다. 표시 sequence는 초기 제어 상태 0이고, 실제 센서를 처리했다는 의미로 0을 기록하지 않는다. 운영 MES 시작/정지 명령은 호출하지 않았다.
