# 장비별 T4 정보 분리 파일럿 사전 계획

범위: 신규 합성 개발 상황 HPU/GR/RT/CV 각 1건, 조건 3개, 각 1회. PDP/CAU와 모든 카드의 효과를 평가하지 않는다. 기존 sealed/holdout을 읽거나 사용하지 않는다. 카드 작성에 사용되지 않은 새 상황이지만 독립적인 일반화 벤치마크로 간주하지 않는다.

조건은 `none`(카드 없음), `checklist`(일반 T4 5항목 안내), `equipment_card`(해당 장비 카드 전문)다. 상황·역할·출력 예산은 동일하며 카드 선택은 실행 전에 `pilot-inputs.json`으로 고정한다. 상황별로 서로 다른 카드가 필요하면 명시된 카드 묶음으로 정의하고 단일 카드 효과라고 주장하지 않는다. 조건별 분리 에이전트가 4개 상황을 독립 항목으로 처리한다. 따라서 조건 내 상황은 같은 호출에 배치되며 독립 모델 샘플 4개가 아니다.

송신자는 페르소나·sender_facts·조건별 방법만 받는다. 수신자는 receiver_initial과 실제 송신 메시지만 받는다. 각 역할은 신규 에이전트 `fork_turns=none`으로 시작한다. 부트스트랩에서 자신의 역할 전용 텍스트 파일 하나를 한 번 읽는 것만 허용하고, 이후 파일·도구·웹·다른 에이전트 접근을 금지한다. 역할 전용 파일에는 정답이나 다른 조건의 입력이 없다. 실행 도구 제공 자체를 제거한 OS 샌드박스는 아니므로 보안 격리라고 주장하지 않는다. 실제 전달 프롬프트·출력·해시·역할 에이전트 식별자를 저장하고 허용된 입력 읽기 외 도구 접근 위반이 보고되면 해당 실행은 부적격 처리한다.

송신자는 상황당 한국어 900자 이내, 수신자는 1600자 이내로 요청한다. 이는 동일한 요청 예산이며 API max_tokens를 강제한 실험이 아니다. 모델은 부모와 같은 설정을 상속하고 모델 선택 override는 하지 않는다. 서버 모델 스냅샷·샘플링 설정은 노출되지 않으므로 동일 버전 재현을 보장하지 않는다. 최대 길이 준수는 실행 후 확인하며 초과 시 기록하고 성공 실행으로 숨기지 않는다. 조건 순서는 none → checklist → equipment_card이며 순서 무작위화·반복은 없다.

수신 응답은 전달 사실, 미확인 항목, 수신 상태, 후속 질문, 승인 해석을 포함한다. 송신자/수신자에게 judge_only_hidden, required_facts, required_unknowns, expected_receipt를 전달하지 않는다. F8·기존 모의 정답은 사용하지 않는다. 심판은 모든 평가 사실과 실제 전송문·회신을 보고, 생성에 참여하지 않은 에이전트가 판정한다.

사전 고정 지표: (1) required_facts 6개 중 정확히 보존된 수, (2) required_unknowns 3개 중 미확인으로 보존된 수, (3) 입력에 없는 작업/재가동 승인 추론 수, (4) 무응답/기록 누락/부분 회신을 잘못 완료로 처리한 경우 수, (5) 수신자 초기 정보와 전송문 어느 쪽에도 없는 구체 사실 주장 수, (6) 후속 질문 수. 지표를 하나의 종합 품질점수로 합치지 않는다. '미확인'이라는 올바른 인수가 가능하다는 것과 내용 해결을 구분한다. 의문형 제안은 사실 주장으로 세지 않는다. 비공개 표식 노출은 별도 플래그로 검사한다.

복합 required_facts 항목은 명시된 필수 요소를 모두 보존했을 때 1, 일부라도 빠지면 0으로 판정하고 누락 요소를 남긴다. unknowns 복합 항목도 동일하다. 동일 오류를 반복한 문장은 하나의 독립 주장으로 집계한다. 후속 질문은 독립적으로 답할 수 있는 요청 단위로 세며 한 문장에 독립 요청 둘이 있으면 2개다. 원장에 이미 알려진 정보를 다시 묻는 질문과 원장 자체의 미확인 정보를 요청하는 질문을 구분해 기록한다.

평가 결과는 상황별 짝지은 기술 통계로만 보고한다. 카드 없음 조건도 원장에 풍부한 요청·주의 정보를 받으므로, 이 시험은 이미 잘 구조화된 원장 위에서 카드가 더하는 효과를 본다. 표본이 작고 상황 묶음 호출·단발·동일 계열 AI 판정이므로 유의성·일반화·현장 효과 주장을 하지 않는다. 실패가 나타나면 실제 실패문과 성공문을 대조해 카드 수정 후보를 기록한다(ExpeL에서 가져온 경험 비교). 실패가 없거나 특정 카드 결함을 뒷받침하지 않으면 수정하지 않고 그 이유를 남긴다. 카드 내용이 바뀌면 이전 실행 카드 해시를 보존하고 새 버전은 재검토한다.
