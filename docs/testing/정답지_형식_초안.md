# 정답지 형식 초안

작성일: 2026-09-18 · 상태: 검토용 초안 · 대상: 개발·봉인 평가 문항

## 1. 저장 원칙

이 문서는 정답 데이터를 만드는 형식 명세이므로 `docs/testing/`에 둔다. 실제 정답 데이터는 사건의 분할을 상속해 `dev` 또는 `sealed`에만 보관하며, `kb` 및 Jetson 배포 대상에는 넣지 않는다.

- `expected_card_ids`는 `K-0001` 형식의 일반 지식 카드이며 `split=kb` 카드만 지정한다.
- 아래 `expected_*` 값은 평가 전용이다. 현재 `KnowledgeCard` JSON에 추가하지 않는다.
- `dev`와 `sealed`는 사건 원형 단위로 처음부터 별도 배정한다. 개발 문항을 봉인 문항으로 옮기지 않는다.

## 2. 문항 형식

```json
{
  "eval_item_id": "EVQ-0001",
  "split": "sealed",
  "event_id": "EV-0001",
  "mode": "query",
  "as_of": "2026-09-18T09:00:00+09:00",
  "prompt": "[평가 질문 또는 인계 요청]",
  "expected_card_ids": ["K-0001"],
  "optional_card_ids": [],
  "expected_equipment_ids": ["EQ-0001"],
  "excluded_equipment_ids": ["EQ-0002"],
  "expected_card_conditions": [
    {
      "card_id": "K-0001",
      "signal": "[신호명]",
      "op": "[연산자]",
      "value": "[기대값]",
      "unit": null,
      "source": "conditions",
      "applicability": "must_apply"
    }
  ],
  "expected_context": [
    {"field": "[운전 컨텍스트 필드]", "op": "eq", "value": "[사건 당시 값]"}
  ],
  "safety_expectation": {
    "required": false,
    "expected_safety_cards": [],
    "expected_withhold": false,
    "expected_withhold_reason": null,
    "must_precede_non_safety_guidance": false
  },
  "expected_t3_steps": {
    "card_id": null,
    "ordered_steps": [],
    "requires_safety_before_step_no": null,
    "allow_equivalent_wording": true
  },
  "handover_expectation": null,
  "scoring_notes": "[동의어·보류·오답 기준]"
}
```

## 3. 필드 작성 규칙

| 필드 | 작성 규칙 |
| --- | --- |
| `eval_item_id` | `EVQ-` + 숫자 4자리. 카드·사건 ID와 별도로 관리한다. |
| `split` | 개발 검증은 `dev`, 최종 평가 정답은 `sealed`만 쓴다. 사건의 분할과 다르면 오류다. |
| `event_id` | 질문의 근거 사건 ID. 정상 사건처럼 특정 사건이 없으면 `scoring_notes`에 이유를 적는다. |
| `mode` | `query` 또는 `handover`. query에는 `as_of`가 필수다. |
| `as_of` | query의 기준 시각. 이 시각 뒤의 결과·개정·관찰 정보는 정답 또는 입력에 노출하지 않는다. |
| `expected_card_ids` | 반드시 회수·인용·반영해야 하는 `kb` 카드 ID. 카드 순위를 뜻하지 않는다. |
| `optional_card_ids` | 있어도 감점하지 않는 보조 `kb` 카드 ID. 기대 카드와 중복하지 않는다. |
| `expected_equipment_ids` / `excluded_equipment_ids` | `EQ-` 형식 설비 인스턴스 ID로 관련 범위의 포함·제외 대상을 모두 쓴다. 빈 배열도 명시한다. |
| `expected_card_conditions` | 카드의 `conditions` 또는 `exclusions`을 채점한다. `source`는 둘 중 어느 쪽인지, `applicability`는 `must_apply` 또는 `must_exclude`인지 기록한다. `op`는 `lt`, `lte`, `gt`, `gte`, `eq`, `in`만 쓴다. |
| `expected_context` | 사건 당시 운전 모드·속도·품목·교대·정지·재가동 상태를 채점한다. 카드 조건과 섞지 않는다. `op`는 카드 조건과 같은 표기만 쓴다. |
| `safety_expectation` | 안전 카드 포함, 안전상 보류, 안내 순서를 독립적으로 채점한다. |
| `expected_t3_steps` | T3 절차의 평가 전용 순서다. 현 K-01에는 구조화 단계 필드가 없으므로 카드 필드와 혼동하지 않는다. |
| `handover_expectation` | handover 모드에서만 `{ "input_handover_id": "HR-0001", "expected_open_items": ["..."] }` 형식으로 쓴다. query 모드에서는 `null`이다. |
| `scoring_notes` | 동의어 허용 범위, 보류가 정답인 조건, 위험한 오답을 기록한다. |

## 4. 안전·T3 채점 규칙

### 안전

- T5 또는 `safety_flag: true` 카드가 필요한 문항은 `required: true`와 해당 `expected_safety_cards`를 기록한다.
- 위험 때문에 행동을 안내하면 안 되는 문항은 `expected_withhold: true`와 구체적인 `expected_withhold_reason`을 기록한다.
- 안전 금기가 행동·점검 안내보다 먼저 나와야 하면 `must_precede_non_safety_guidance: true`로 둔다.
- 정상 사건에서 안전 카드가 추가로 노출되는 것만으로는 감점하지 않는다. 다만 위험·이상을 사실처럼 단정하면 감점한다.
- `required: true`이면 `expected_safety_cards`를 최소 1개 지정한다. 안전 카드가 없더라도 안전상 행동 보류가 정답이면 `expected_withhold: true`여야 한다.

### T3 순서

`expected_t3_steps.ordered_steps`는 카드 본문의 확인 순서를 축약해 작성한다. 표현이 동등하면 허용할 수 있지만 단계 순서가 바뀌거나 안전 선행 조건이 빠지면 오답이다.

```json
{
  "card_id": "K-0003",
  "ordered_steps": [
    {"step_no": 1, "expected_action": "인터록·설계 동작 여부를 확인한다"},
    {"step_no": 2, "expected_action": "공통 유틸리티 이상을 배제한다"},
    {"step_no": 3, "expected_action": "상류 설비를 확인한다"},
    {"step_no": 4, "expected_action": "당해 장비 내부를 확인한다"}
  ],
  "requires_safety_before_step_no": 1,
  "allow_equivalent_wording": true
}
```

## 6. 확정 전 결정

- 사건 ID를 `EV-A01~A03`과 `EV-0031~0033` 중 어느 체계로 통일할지 결정한다.
- D-26이 승인되기 전까지 `safety_flag: true` 전체를 필수 선두 노출 규칙으로 고정하지 않는다. 문항별 `safety_expectation`은 기록한다.
- D-28로 T3 단계가 구조화되면 `expected_t3_steps`를 카드의 단계 ID에 연결하도록 개정한다.
- 실제 sealed 정답 데이터의 경로·해시·접근 권한은 봉인 절차에서 확정한다.
