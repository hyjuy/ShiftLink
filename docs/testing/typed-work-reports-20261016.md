# 유형별 근무일지와 재사용 근거 저장

2026-10-16. 브랜치 `feat/typed-work-report-20261016`, RED 체크포인트 `aab9abf`에서 Python 30개와 PDA 계약 검사의 실패를 확인한 뒤 구현했다. 기존 `/api/work-reports`, 일지 outbox, 사건·후보 테이블을 확장했다.

## 양식과 저장

| 근무 유형 | 입력 | 서버 처리 |
| --- | --- | --- |
| 정상 근무 | 설비·날짜·근무조·작성자, 추가 메모 선택 | 상세 기록 없이 저장 가능. 저장 시점 센서 근거 자동 첨부 |
| 정비 작업 | 정비·수리 내용, 부속품 대상 설비·이름·품번·수량·단위·사용 내용 | 양수 수량·설비 범위 검사. 부속품 사용 없음을 명시할 수도 있음 |
| 고장·이상 대응 | 문제 센서·문제 내용, 조치 전후 값·시각 선택, 수행 조치·작업자 결과·후속 인계 | 신호·단위·중복·유효 숫자 검사. 센서 미확인도 명시 가능. 해결 결과에는 조치와 확인 근거 필요 |

새 요청은 `work_report.form_version=2`와 `work_type`을 보낸다. 기존 요청은 종전 형식대로 처리하며, 전송 대기 요청은 수정 없이 다시 전송한다. 날짜·A/B/C 근무조·저장 확인창을 유지했다. B조 종료는 다음 날 00:00이며 날짜 달력은 교대 시간과 함께 반영한다.

센서 자료는 서버가 활성 설정과 현재 스냅샷에서 만든 `server_sensor_evidence`다. 별도 `work_report_sensor_evidence` 테이블에 원본 일지·사건·후보와 한 트랜잭션으로 저장한다. 재전송 시 다시 측정하지 않는다. `scope=save_snapshot`은 저장 시점 자료이며 근무시간 전체의 정상 판정이 아니다. 미수신 값은 `missing`, 수기 전후 값은 `source=manual`로 구분한다.

기존 업로더는 유형별 JSON과 서버 센서 근거를 함께 전송한다. 키 정렬로 재시도 시 동일한 내용 해시를 유지한다. 기존 해결 기록 업로드 보류 규칙은 유지한다. 실제 중앙 DB 연결은 이번 검증에서 사용하지 않았다.

## 지식카드 후보

고장·이상 기록에서 **최근 카드 없음 질문 연결**을 누르면 같은 설비의 실제 `query_id`를 연결한다. 후보 체크와 유효한 `no_applicable_card` 질문이 있어야 기존 서버 경로에서 `pending_review` 후보를 만든다. 질문이 없거나 상태가 다른 기록은 일지는 저장하되 후보 생성 조건을 만족하지 않는다.

후보에는 원문 상황·수행 조치·원인 확인 상태·작업자 결과·수기 센서 기록을 보존한다. 작업자가 해결을 선택해도 `mes_recovered=false`, `ready=false`이며 자동 승인하지 않는다. 기본 KB 검색 대상에 들어가는 정식 승격은 별도 검토 과정이 필요하다. 정식 검토·승격 화면/API는 이 단계에 포함하지 않는다.

[학술논문 조사](../../artifacts/ShiftLink%20재사용성%20향상을%20위한%20학술논문%20조사.md)의 P01(CBR: 회수·재사용·수정·보존)에 맞춰 질문과 사건, 해결 경험을 추적 가능하게 연결했다. P02의 경험과 검증된 교훈의 구분에 따라 원문 경험을 검토 대기 상태에 두며, 원인이나 성공을 자동 확정하지 않는다. 조건·단위·품질·설정 ID를 보존하되 LLM·임베딩 모델을 재학습하지 않는다.
