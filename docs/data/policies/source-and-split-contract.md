# 원문·출처 목록과 평가 분할 계약 v1

확정일: 2026-09-22 (Asia/Seoul). 사용자 요청에 따른 현재 데이터 작성 기준이다. 과거 전문가 제안 전체를 승인한 것으로 해석하지 않는다.

후속 구현: [생성 파이프라인](../../guides/card-generation.md)이 검토된 발췌문·명시된 그룹 배정·근거 연결을 검사하고 초안을 저장한다. 아래의 구현 전 상태 설명은 최초 확정 당시의 기록이다. 원문 자동 추출·신규 그룹 자동 배정·의미 기반 누출 판정·정식 평가 봉인은 여전히 별도 작업이다. `splits/inventory.json`은 최초 확정 시점의 해시 기준점이며 이후 개정을 소급 반영하지 않는다.

출처 식별·상태는 [source_registry.json](../../../seeds/source_registry.json), 기존 원형 배정과 신규 배정 규칙은 [prototype_split.json](../../../splits/prototype_split.json), 파일 확인 시점과 SHA-256은 [inventory.json](../../../splits/inventory.json)을 기준으로 한다. 작성 형식은 [v1.1 작성 가이드](../../../seeds/카드_작성_가이드_초안.md)를 따른다. 이전 설계의 분할 제안과 충돌하면 이 문서가 우선한다. 런타임 로더나 자동 누출 차단 기능을 구현한 것은 아니다.

확보 여부는 현재 작업 디렉터리 기준이다. 과거 공유 드라이브나 다른 PC에 보관했다는 기록을 현재 파일 확보로 간주하지 않는다. 등록부의 `reviewed_notes`는 기존 조사 기록을 뜻하며 이번에 원문 전체를 재검토했다는 뜻이 아니다. 공개 링크나 PDF 존재만으로 사용 권한·설비 적합성을 확정하지 않는다.

출처의 사용 상태는 `pending_review` → `approved_for_draft`로 관리한다. 승격에는 사용할 원문 판본/확인일, 절·페이지 또는 웹 heading, 사용 가능한 주장, 제외 범위, 검토자, 이용 범위 기록이 필요하다. 카드에는 `provenance.sources`의 `source_id`, `locator`, `document_version`으로 연결한다. 승인되지 않은 출처를 사실·절차의 확정 근거로 사용하는 생성은 보류한다. 원문을 확보하지 않은 문헌 식별자를 실제 검토한 근거처럼 넣지 않는다.

현재 등록은 모든 문서 전문의 일괄 생성 승인이 아니다. 우선 HPU·GR·RT·CV에 필요한 SD-001/002/003/005/006/007과 M-02/03의 관련 절을 검토한다. M-04와 M-05/06은 해당 기능을 생성할 때만 검토하며, M-07/08/09는 출처 식별 전 보류한다. 검토된 일부 절부터 초안 생성을 시작할 수 있고 전체 문서 검토를 기다릴 필요는 없다.

## 2. 프로젝트 자료는 원문과 구분한다

| 자료 | 역할 | 허용 범위 |
|---|---|---|
| `docs/data/reference/00_plant_and_relations.json` | 합성 공통 설정 + 원형 배정 혼합 | 기준정보의 허용 필드만 추출. 전체 파일을 생성 프롬프트에 넣지 않음 |
| `docs/data/knowledge_cards/01_kb_cards_shared.json` | 기존 합성 KB 사례·카드 | 검수된 `knowledge_cards`를 KB에 사용. 생성 원문으로 재투입하지 않음 |
| `docs/data/scenarios/EV-0031_upstream_cause.json` | 기존 kb 예제 | 기존 KB용 자료. 새 독립 평가 사례로 계산하지 않음 |
| `docs/data/scenarios/EV-0032_downstream_block.json` | dev 사례 | 개발·오류 분석 전용. 파생 카드도 dev 유지 |
| `docs/data/scenarios/EV-0033_common_utility.json` | sealed 사례 | 평가 관리자만 사용. KB·생성 입력·튜닝 제외 |
| `docs/testing/dev_sample_memos.jsonl` | 합성 개발 입력 | dev 전용. 현장 원문으로 표시하지 않음 |
| `eval/fixtures/dev`, `eval/fixtures/holdout` | 코드·평가 테스트 자료 | 생성 원문 아님. fixture 내부 kb 표기는 테스트 설정일 뿐 운영 KB 편입 승인 아님 |

공통 설정 추출 허용 키는 `production_lines`, `process_segments`, `equipment_groups`, `equipment_types`, `equipment`, `components`, `relations`, `manual_documents`, `manual_sections`, `personas`다. 모두 합성 설정이며 실제 운전 임계값·제조사 매뉴얼로 인용하지 않는다. `event_prototypes`와 사건·정답·배정 정보는 추출하지 않는다. 허용 키 안에도 평가 답·사건 원형이 포함되었는지 검토한 후 입력본을 확정한다. 시드 원문은 등록부에서 별도 선택한다.

평가 입력에는 평가 시점(`as_of`)까지 관측 가능한 사실만 넣는다. true_cause, true_actions, 정답 라벨, 사후 조치·결과·재발 확인은 정답지에 격리한다. 답변 후에 밝혀진 정보를 입력으로 되돌리지 않는다. 생성 모델의 출력이나 기존 정답을 다음 생성의 원문으로 사용하는 순환 증강은 허용하지 않는다.

## 3. 분할 단위와 비율

- 분할 이름은 `kb`, `dev`, `sealed`로 고정한다. `holdout/`은 최종 평가 fixture 디렉터리이며 사건 데이터의 별도 네 번째 분할이 아니다.
- 기존 PT-0003/0007/0011/0015/0016 배정은 유지한다. 신규 목표 비율은 기존 70:20:30 계획을 비율로 옮긴 **7:2:3**이다. 전체 건수 120 또는 후속 제안 72를 상한으로 두지 않는다.
- 행·카드가 아니라 **누출 연결 그룹**을 배정한다. 동일 사건, 재발·선행 사건, 같은 사건 원문을 번역·요약·재서술한 사례, 같은 원형에서 수치·설비명만 바꾼 사례를 한 그룹으로 묶는다. 여러 원형이 같은 사례 원문에서 파생되면 한 그룹이다.
- 원형 판정에는 `case_type`, `root_equipment_type`, 정렬된 `relation_path_types`, `primary_symptom_class`를 사용한다. 이 키만으로 완전한 중복 판정을 보장하지 않으므로 원문 계보와 사람이 검토한 유사 사례도 연결한다.
- 일반 제조사 매뉴얼을 함께 참고했다는 이유만으로 모든 사건을 한 그룹으로 합치지 않는다. 공통 배경 문헌은 공유 가능하나, 특정 고장 사례·해결 서사의 파생본은 동일 그룹이다. 이번 평가는 공통 KB를 이용하는 새로운 사건 처리 평가이며 미지 문헌에 대한 일반화 성능을 주장하지 않는다.
- 원형 ID는 외부 배정표로 관리한다. 이 작업으로 카드·이벤트 스키마에 필드를 추가하지 않는다. 카드와 관측·인계문·정답·변형본은 원천 그룹의 split을 상속한다.

신규 그룹의 안정적인 배정은 UTF-8 문자열 `shiftlink-split-v1:<group_id>`의 SHA-256을 big-endian 정수로 해석하고 12로 나눈 나머지로 결정한다. 0~6은 kb, 7~8은 dev, 9~11은 sealed다. group_id는 해시 결과를 보기 전에 원문 계보로 확정하고 변경하지 않는다. 기존 배정은 해시보다 우선한다. 그룹 크기가 달라 건수 비율은 정확히 일치하지 않을 수 있으며 그룹 수와 사건 수를 모두 보고한다. 이는 분할 방법이지 무작위 실험·통계적 독립성의 증명이 아니다.

KB 구축 전에 전체 신규 배치의 원문 계보·중복·유사 사례를 점검한다. 이미 다른 split에 들어간 그룹 간 연결이 뒤늦게 발견되면 신규 항목을 보류하고 해당 평가를 오염 검토 대상으로 표시한다. 숫자 비율을 맞추려고 기존 사례를 옮기거나 sealed 내용으로 튜닝하지 않는다. 필요한 새 평가는 새 버전의 독립 그룹으로 교체한다.

## 4. 평가 봉인과 재현성

1. 개발자는 dev로 프롬프트·검색·평가기·임계값을 조정한다. 평가 관리자는 sealed의 의미 내용과 정답을 분리해 관리한다. 폴더명만으로 접근 격리가 구현된 것으로 보지 않는다.
2. 봉인 전에 유형 T1~T6, 설비군, 정상/오류/경계/판단보류, 조건 불충족/미관측, 안전, 재가동 실패 등 평가 목적별 건수를 확인한다. 부족한 범주는 새로운 독립 그룹으로 보충한다. 해시가 원하는 split을 낼 때까지 ID를 바꾸지 않는다.
3. 생성 원문·검토 범위·계보, 그룹 배정, KB와 평가 입력/정답의 해시, 코드 커밋 및 dirty diff, 모델·프롬프트·인덱스·스키마 버전, k·임계값·평가 지표를 평가 manifest에 고정한다. 정답은 구현 출력 복사 없이 독립 작성·검토한다.
4. sealed는 고정된 최종 설정의 평가에 사용한다. 평가를 본 후 수정했다면 같은 자료의 결과는 재평가/회귀 검사로 표시하고 새 독립 최종 평가와 구분한다. 현재 inventory는 파일 무결성 기준점이며 과거 미열람이나 정식 봉인을 증명하지 않는다.
5. 누출 검사는 ID 교집합, 원문·원형·재발 계보, 정답/사후 필드, 정규화 중복, 유사 서사 검토, canary를 함께 사용한다. canary 부재만으로 누출 없음이라고 결론 내리지 않는다.
6. 검색 성능과 안전 누락을 따로 보고한다. 대용량 성능 측정은 KB 크기·동시 요청 수·환경·지연시간 분포와 함께 보고하며, 기존 합성 단일 요청 측정을 운영 성능으로 일반화하지 않는다.

## 5. 이번 확정의 완료 범위

출처 식별 목록, 사용 범위, 보완 항목, 기존 배정, 신규 분할 방식이 확정되었다. 기존 데이터·정답·holdout 파일은 수정하지 않는다. 등록부와 배정표를 자동으로 읽는 생성기, 원문 추출기, 누출 검사기, 접근 격리 및 정식 최종 평가 봉인은 별도 구현·운영 작업이다. 다음 카드 생성은 **관련 원문 절 검토 → 입력 투영본·계보 확정 → 그룹 배정 → kb 초안 생성 → 스키마·근거 검수** 순서로 시작한다.
