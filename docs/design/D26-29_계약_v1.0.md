## 2. 스키마 v1.0 (담당 A)

### 2.1 tacit_type 확장 — T6 정식 유형 `[팀 확정]`

- `tacit_type: Literal["T1","T2","T3","T4","T5","T6"]`
- `T6` = 재가동(setup restart) 지식 카드. **정식 유형**(9/21 회의 후 팀 확정). 코드 주석의 `proposal (not approved in 9/21 meeting)` 표기는 "team-confirmed after the 9/21 meeting; not part of the meeting's own decisions"로 갱신한다(담당 A).
- D-29 기본안(기존 T1~T5 안의 확장 필드)도 유지: `restart_type`/`tried_and_failed`는 모든 tacit_type에 허용, T6에서는 `restart_type` 필수.

#### 2.1.1 T3 / T4 / T6 경계 규칙 `[제안 — 팀 확인 필요]`

유형이 늘면 분류가 흔들리므로 경계를 먼저 고정한다. 아래는 제안이며 확정 시 표기를 바꾼다.

| 상황 | 유형 | 판단 근거 |
|---|---|---|
| 증상에서 원인을 좁혀가는 확인 순서 | T3 | 목적이 원인 규명 |
| 정지 상태에서 운전 상태로 되돌리는 절차·실패 경험 | T6 | 목적이 상태 복귀 |
| 재가동 미완료 상태를 다음 교대에 넘기는 방법 | T4 | 목적이 전달 |
| 재가동 중 금지 행위 | T5 | 안전 금기가 우선 |

한 카드가 두 목적을 담으면 분리한다. T5는 다른 유형과 겹칠 때 항상 우선한다(기존 안전 규칙 유지).

#### 2.1.2 T6 승격의 데이터·평가 파급 `[미결 — 통합본 개정 필요]`

T6는 스키마·도구·하니스(담당 A·B·C 범위)에 이미 반영됐다. 아래는 그 **범위 밖**이며 통합본 §3.2·§4.7.5·§4.7.7과 정답지 개정이 따로 필요하다. 이 항목이 미결인 동안 "T6 반영 완료"로 보고하지 않는다.

| 항목 | 기존(T1~T5 전제) | T6 승격 시 쟁점 | 본 문서 제안 |
|---|---|---|---|
| 카드 최소 수량 | T별 최소 20, T5 최소 25 → 최소 105 / 목표 150 | T6에도 20을 적용하면 최소 125가 되어 여유가 45→25로 줄고, 채택률 60% 가정상 T6만 약 33건을 추가 생성해야 한다 | **T6 최소치를 20으로 복사하지 않는다.** 1차 기간(10/2)에는 최소 기준을 유예하고 실제 생성·채택 가능량을 먼저 측정한다 |
| 커버리지 매트릭스 | T1~T5 × 설비 4종, 빈칸 0 | T6 × 설비 4종은 억지 카드를 유발한다. 재가동은 설비 단위보다 라인·구간 단위 행위다 | **T6의 축을 설비가 아니라 재가동 유형 3종**(`normal_stop_restart`/`abnormal_stop_restart`/`maintenance_restart`)으로 둔다. D-29의 요구("재가동 유형별 실패 구분")와 직접 대응한다 |
| 봉인 평가셋 | 60건(질의 36·인계 24, 안전 12) | T6 문항 추가 시 분할 계약 변경 | 봉인 전(2주차 말)에 결정한다. 봉인 후 변경 금지 |
| 기존 데이터 | 설계 예제 카드 12건(T5 3·T3 3·T2 3·T1 2·T4 1)에 T6 0건 | 소급 재분류 여부 | 기존 카드를 T6로 **소급 재분류하지 않는다**. 재분류는 카드 ID·정답지에 연쇄 영향을 준다 |

### 2.2 신규 모델 (전부 `ShiftLink/agent/schemas.py`)

```python
NonBlank = Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]

class HandoverMethod(BaseModel):          # D-27: T4 전달 방법
    required_context: list[NonBlank]      # min_length=1, 전달할 정보
    recipient_role: NonBlank              # 대상
    timing: NonBlank                      # 시점
    channel: NonBlank                     # 방법
    acknowledgement: NonBlank             # 확인 방법

class ResolutionStep(BaseModel):          # D-28: T3 단계
    step_id: str                          # pattern ^ST-\d{2,4}$
    order: int                            # ge=1
    action: NonBlank
    preconditions: list[str] = []
    expected_result: NonBlank
    stop_conditions: list[str] = []       # 길이 제한·요약으로 잘라내지 않음

RestartType = Literal["normal_stop_restart", "abnormal_stop_restart",
                      "maintenance_restart", "unknown"]
# 가상 설비 사전 기반 잠정 허용값. 현장 표준으로 단정하지 않음.

class FailedAttempt(BaseModel):           # D-29: 시도·실패
    attempt_id: str                       # pattern ^AT-\d{4}$
    restart_type: RestartType
    action: NonBlank
    observed_result: NonBlank
    failure_reason: str | None = None     # None = 이유 미상 보존. "미상" 문자열 자동 기입 금지
    evidence_ids: list[str] = []          # ^(K|EV|AR)-\d{4}$ 형식 검사만. 실존 검증은 하니스

class TypePayload(BaseModel):
    handover_method: HandoverMethod | None = None
    steps: list[ResolutionStep] | None = None
    restart_type: RestartType | None = None
    tried_and_failed: list[FailedAttempt] = []
```

`KnowledgeCard.type_payload: TypePayload | None = None` 추가.

### 2.3 검증 규칙 (model_validator, 위반은 ValidationError)

기존 규칙 유지 + 추가:

1. T4 → `type_payload.handover_method` 필수. (“인계했다” 사실만 있는 카드 차단은 구조 필수화로 달성)
2. T3 → `type_payload.steps` 필수(1개 이상). `step_id` 중복 금지, `order` 중복 금지, 리스트는 `order` 오름차순으로 저장되어야 함(정렬 자동 수정 금지 — 위반 시 오류).
3. T6 → `type_payload.restart_type` 필수. T6도 T5와 무관하게 `safety_flag` 규칙은 기존대로.
4. `tried_and_failed`의 각 attempt: 카드 `restart_type`이 known(≠unknown)이고 attempt.restart_type도 known인데 서로 다르면 오류(다른 유형으로의 실패 일반화 차단). 카드 restart_type이 unknown이면 attempt는 어떤 유형이든 허용.
5. `handover_method`가 T4 외 카드에 있으면 오류, `steps`가 T3 외 카드에 있으면 오류(책임 혼합 방지). `restart_type`/`tried_and_failed`는 전 유형 허용(2.1).

### 2.4 사건·카드 책임 분리

- `Event.restart_attempts: list[FailedAttempt] = []` 추가 — 사건별 시도 이력.
- 카드의 `tried_and_failed`는 재사용 가능한 일반화 지식, Event의 `restart_attempts`는 해당 사건 이력. Event는 `true_cause` 등 평가 정답을 포함하므로 런타임 KB·모델 입력에 절대 전달하지 않는다(하니스가 카나리로 검사).

## 4. 도구·파이프라인 계약 (담당 B)

### 4.1 도구 추가 — `search_safety_cards`

```python
def search_safety_cards(*, equipment_ids: list[str],
                        observations: dict[str, object] | None = None) -> list[dict]
```

- `safety_flag=True`인 적용 가능 카드 **전수** 반환. top-k와 무관(독립 조회).
- `ToolProvider` Protocol에 추가. 신규 `InMemoryToolProvider`(`ShiftLink/rag/retrieval.py`)가 도구 6종 구현: KB는 `accepted AND split=="kb" AND grade=="L1"` 카드만 적재(적재 시 검사, dev/sealed 혼입 시 예외).

### 4.2 조건 매칭 규칙 (결정적)

- `Condition.op` ∈ {==,!=,>,>=,<,<=}. observations에 signal이 있고 조건이 False로 확정 → 카드 제외. exclusions가 True로 확정 → 카드 제외.
- observations에 signal이 없으면 unknown → 제외하지 않되 결과에 `condition_status: "unverified"` 표기. 안전 카드도 동일(보수적 포함).

### 4.3 파이프라인·응답

- `FixedPipeline._run_tools`에 `safety_cards` 결과 추가(질의·인계 공통). 일반 `cards`와 병합 시 `card_id` 중복 제거, 안전 카드 선두.
- `ShiftLink/agent/response.py`:
  - `AgentResponse`: `safety_notices[]`(선두 고정: card_id, safety_basis, stop_conditions), `cards[]`(인용 card_id 포함), `steps[]`(T3 order 순서 보존), `handover_method`(T4), `restart_failures[]`(restart_type별 그룹, unknown 유지, failure_reason None 유지), `review_queue: bool`.
  - `build_response(...)`, `render_response(resp) -> str`: 결정적 텍스트 렌더(화면 계약). 실제 웹 UI 반영은 이번 범위 밖 — 미구현으로 표시.
- 운영 validator: 인용 ID가 tool_results에 실존, 안전 카드 누락 0, 단계 순서 보존, stop_conditions 유실 0. 스키마 실패에 한해 모델 1회 재시도, 재실패 시 `review_queue=True`로 반환(저장 차단).
- P5 규칙 검사(`check_card_rules(card) -> list[str]`)와 생성 프롬프트 템플릿(D-26~29 규칙 명시)을 retrieval.py 또는 별도 함수로 제공.
