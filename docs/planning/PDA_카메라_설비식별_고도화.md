## 1. 요구사항과 제약 충돌

### 1.1 신규 요구

작업자가 **PDA(산업용 핸드헬드)** 를 들고 현장을 다닌다. PDA 카메라로 설비를 식별하고, 식별된 설비가 에이전트 질의의 `eq_id` 컨텍스트로 자동 주입된다.

데모 환경에는 실제 설비가 없다. 따라서 **설비를 직접 찍지 않고, 설비를 대신하는 "상자"를 찍어서 어떤 설비인지 구분**한다. 상자 1개 = 설비 1대다.

### 1.2 충돌하는 기존 결정

| 제약 | 현재 문구(요지) | 충돌 내용 |
| --- | --- | --- |
| **C-056** | VLM·음성인식은 MVP 범위 밖. 도입해도 LLM과 동시 상주시키지 않고 순차 실행 | 카메라 인식에 신경망을 쓰면 정면 충돌 |
| **C-057** | 영상 장치 정보는 현황 기록일 뿐, 카메라 기능을 MVP에 추가하지 않음 | "반드시 카메라 사용"과 정면 충돌 |

여기에 물리 제약이 겹친다.

- Jetson Orin Nano 8GB(실측 7.6GB), **전력 15W 고정(N-6)**
- 신규 질의 p95 실측 21~34초 — **이미 목표 15초(C-119)를 초과** 중. 추가 연산 여유가 없다.

### 1.3 이 설계의 기본 입장

**카메라를 쓰되, Jetson에는 아무것도 더 얹지 않는다.**
인식 연산을 전부 PDA 단말에서 끝내고, Jetson에는 식별 결과(문자열 `eq_id` + 메타)만 전달한다. 그러면 C-056의 규범(LLM과 동시 상주 금지)은 **위반이 아니라 자동 충족**된다. Jetson에서 도는 모델은 여전히 LLM 하나뿐이다.

## 2. 설계 결정 요약

| # | 결정 | 근거 |
| --- | --- | --- |
| **A. 인식 위치** | **PDA 단말에서 전량 처리.** Jetson은 `eq_id` 문자열만 수신 | 15W·7.6GB에서 p95가 이미 초과. Jetson에 분류기를 상주시키면 C-056 위반 + p95 추가 악화 |
| **B. 인식 방식(1순위)** | **QR 코드 + 브라우저 내장 `BarcodeDetector` API** | 추가 의존성 0. Chrome/Android에서 네이티브 지원. 신경망 아님 |
| **C. 인식 방식(2순위)** | **ArUco 마커 + js-aruco2** (거리·각도 강건성이 필요할 때) | 원거리·비스듬한 각도에서 QR보다 강건. 단 JS 라이브러리 1개 추가 |
| **D. 폴백** | 색상 태그(육안) → **수동 선택 목록** | 인식 실패해도 데모가 멈추지 않아야 함 |
| **E. 상자 인쇄** | **QR과 ArUco를 한 면에 같이 인쇄** | B↔C 전환을 상자 재제작 없이 결정 가능 |
| **F. 구현 형태** | 기존 mock MES의 **정적 파일 서빙에 `pda.html` 추가** | `server.py:265-268`에 이미 web_root 서빙이 있음. 새 프레임워크·새 프로세스 불필요 |
| **G. HTTPS** | **자체 서명 TLS 또는 localhost 터널 필수** | `getUserMedia`는 보안 컨텍스트에서만 동작. LAN IP + http는 카메라가 열리지 않음 |
| **H. 안전 차단** | 신뢰도 임계 미달 시 **검색 자체를 막는다** | 잘못 식별된 설비의 안전 카드가 나가는 것이 이 시스템 최악의 실패 |

### 2.1 서브에이전트 제안 중 기각한 것

세 갈래로 설계를 병렬 검토했고, 다음은 검토 후 기각했다.

| 기각한 제안 | 기각 사유 |
| --- | --- |
| Jetson에 MobileNet 분류기 160MB 상주 | C-056의 취지를 정면으로 거스른다. p95가 이미 초과 상태라 "2% 메모리니까 괜찮다"는 논거가 성립하지 않는다. PDA 처리로 같은 목적을 달성할 수 있다 |
| FastAPI 도입 | mock MES는 표준 라이브러리 `BaseHTTPRequestHandler`로 이미 정적 파일을 서빙 중이다(`shiftlink/mes/server.py:265`). 새 의존성을 넣을 이유가 없다 |
| 경량 분류 신경망(MobileNetV3) 1순위 | 설비당 학습 데이터 수집이 필요한데 데모 일정에 맞지 않는다. 상자에 마커를 붙일 수 있는 상황에서 분류기를 쓸 이유가 없다 |
| 시연 대본을 "설비 명판 스캔"으로 작성 | 요구사항은 **상자**를 찍는 것이다. §12에서 상자 기준으로 다시 썼다 |

### 4.2 권고

**1순위 — QR + `BarcodeDetector`**

- 브라우저 내장 API라 **라이브러리를 하나도 추가하지 않는다**. 이 프로젝트가 표준 라이브러리만으로 mock MES를 만든 기조와 맞는다.
- 상자는 손에 들거나 1m 내외에서 찍는 데모 동선이라 QR의 거리 한계가 문제되지 않는다.
- 미지원 브라우저(주로 iOS Safari, Firefox)에서는 2순위로 자동 전환한다.

**2순위 — ArUco + js-aruco2 (MIT)**

- 원거리·비스듬한 각도·부분 가림에서 QR보다 확연히 강건하다. 발표장 동선이 상자에서 멀어질 수밖에 없다면 이쪽으로 전환한다.
- 전환 비용을 0으로 만들기 위해 **상자에는 QR과 ArUco를 처음부터 둘 다 인쇄한다**(§5).

**3순위 — 색상 태그 + 수동 선택**

- 색상은 자동 판정에 쓰지 않는다. **작업자가 육안으로 상자를 구분하는 용도**와, 수동 선택 목록의 항목을 상자와 대조하는 용도로만 쓴다. 조명에 따라 색이 무너지는 것을 자동 판정 경로에 넣으면 오인식 위험만 늘어난다.

### 4.3 기각: 온디바이스 VLM

"카메라를 쓰라"는 요구가 곧 "VLM을 쓰라"는 뜻은 아니다. 설비 4종을 구분하는 데 VLM은 과잉이고, C-056 정면 위반이며, 15W Jetson에서 LLM과 공존시킬 방법이 없다. 이 설계는 **카메라 요구는 충족하되 VLM은 쓰지 않는다.**

## 5. 상자 소품 스펙

### 5.1 물리 규격

| 항목 | 사양 | 비고 |
| --- | --- | --- |
| 크기 | 200 × 150 × 100 mm 내외 | 한 손으로 들 수 있고 바닥에 세워둘 수 있는 크기 |
| 재질 | 백색 골판지 또는 PP 박스 | 무광일 것 |
| 표면 처리 | **무광 코팅만.** 광택 필름·투명 테이프 덮기 금지 | 반사는 QR 실패의 1순위 원인 |
| 개수 | 설비 인스턴스 수만큼(최소 4개, 권장 6개) | 4종 구분 + 동종 2대 구분 시연용 |

### 5.2 인쇄 면 구성

```
┌──────────────────────────────────┐
│  ■ 색상 띠 (설비군 식별, 높이 20mm) │
├──────────────────────────────────┤
│                                  │
│   ┌────────┐      ┌────────┐     │
│   │ ██  ██ │      │ ▀▄▀▄▀▄ │     │
│   │  QR    │      │ ArUco  │     │
│   │ 80mm   │      │ 100mm  │     │
│   └────────┘      └────────┘     │
│                                  │
│        HPU-01                    │  ← 육안·수동 선택 대조용
│      유압 유닛                    │     48pt 이상 굵은 글씨
└──────────────────────────────────┘
```

| 요소 | 사양 |
| --- | --- |
| QR | 한 변 80 mm, 오류정정 레벨 **M**, 여백(quiet zone) 모듈 4개분 이상 |
| ArUco | `DICT_6X6_250`, 한 변 100 mm, 흰 여백 30 mm 이상 |
| 인쇄 | 300 DPI 이상, 순수 흑(0,0,0) / 순수 백(255,255,255) |
| 텍스트 | `equipment_id` + 한글 설비명, 48pt 이상 |
| 부착 면 | **최소 2면(정면·상면)** 에 동일 내용. 상자를 돌려놔도 인식되게 |

### 5.3 QR 인코딩 내용

```
SHIFTLINK:EQ:HPU-01
```

접두어 `SHIFTLINK:EQ:` 를 검사해 **현장의 무관한 QR(택배 송장 등)을 즉시 배제**한다. 이 접두어 검사가 오인식 1차 방어선이다.

### 5.4 설비 ↔ 마커 매핑 (초안)

| equipment_id | 설비군 | 한글명 | QR 내용 | ArUco ID | 색상 띠 |
| --- | --- | --- | --- | --- | --- |
| `HPU-01` | HPU | 유압 유닛 | `SHIFTLINK:EQ:HPU-01` | 30 | 빨강 |

## 6. 신뢰도·오인식 처리 정책

### 6.1 판정 단계

```
프레임 입력
   │
   ├─▶ QR 디코딩 성공?
   │      ├─ 접두어 `SHIFTLINK:EQ:` 불일치 → 무시(현장 잡 QR 배제)
   │      └─ 일치 → 후보 등록 (confidence = 1.0)
   │
   ├─▶ (QR 실패 시) ArUco 디코딩 성공?
   │      ├─ 매핑표에 없는 ID → 무시
   │      └─ 있음 → 후보 등록 (confidence = 0.95)
   │
   └─▶ 둘 다 실패 → 후보 없음
             │
   ┌─────────┴──────────┐
   │  연속 3프레임 투표  │
   └─────────┬──────────┘
             │
   ┌─────────┴───────────────────────────────┐
   │ 3/3 동일 → 확정 (햅틱 길게 1회)          │
   │ 2/3 동일 → 확정하되 확인 버튼 요구        │
   │ 불일치·후보 없음 → 재시도 (최대 3회)      │
   │ 3회 실패 → 수동 선택 화면으로 강제 전환   │
   └─────────────────────────────────────────┘
```

마커 디코딩은 성격상 "맞거나 틀리거나"라 연속값 신뢰도가 없다. 그래서 **신뢰도 대신 프레임 일치 횟수를 신뢰 근거로 쓴다.** 이것이 확률형 분류기보다 오히려 검증하기 쉽다.

### 6.2 안전 카드 오적용 차단

이 시스템에서 가장 위험한 실패는 **엉뚱한 설비의 안전 카드가 제시되는 것**이다. 3중으로 막는다.

1. **PDA 단**: 확정되지 않은 `eq_id`로는 검색 버튼이 활성화되지 않는다.
2. **전송 단**: 질의에 `eq_id_source`(`camera_scan` / `manual_selection`)를 함께 보낸다. 출처 없는 `eq_id`는 거부.
3. **서버 단**: `eq_id`가 MES 카탈로그에 실재하는지 검증하고, 실패 시 검색을 수행하지 않고 오류를 반환한다. **"애매하면 답하지 않는다"** — 출처 없는 응답을 "해당 지식 없음"으로 처리하는 기존 원칙과 같은 규범이다.

### 6.3 확정 후 변경

확정된 설비는 화면 상단에 **항상 고정 표시**되고, 옆에 `[수정]` 버튼이 붙는다. 작업자가 잘못 잡힌 것을 언제든 뒤집을 수 있어야 한다. 잘못된 컨텍스트로 조용히 진행되는 것이 오인식보다 나쁘다.

### 6.4 실제 설비로의 이행

데모의 상자가 나중에 진짜 설비로 바뀔 때 **교체되는 것은 "마커가 붙은 물리 대상"뿐**이다.

| 계층 | 데모 | 실제 설비 | 변경 |
| --- | --- | --- | --- |
| 물리 | 상자에 QR/ArUco 부착 | 설비 명판 옆에 QR/ArUco 부착 | 라벨 재부착 |
| 인식 | QR 디코딩 | QR 디코딩 | **없음** |
| 매핑 | `SHIFTLINK:EQ:HPU-01` → `HPU-01` | 동일 | **없음** |
| 컨텍스트 | `eq_id` 주입 | 동일 | **없음** |

즉 **인식 계층은 "상자"를 전혀 모른다.** 이 추상화 경계를 유지하는 것이 설계 목표 중 하나다. 코드나 스키마 어디에도 `box`라는 단어를 넣지 않는다.

## 8. 구현 방식

### 8.1 기존 구조에 얹는다

mock MES는 이미 `shiftlink/mes/web/`의 `index.html` · `app.js` · `operator.js` · `style.css`를 서빙한다(`shiftlink/mes/server.py:265-268`, 화이트리스트 방식).

따라서 PDA UI는 **같은 자리에 파일 2개를 추가하고 화이트리스트에 이름을 넣는 것**으로 끝난다.

```
shiftlink/mes/web/
  index.html      (기존)
  app.js          (기존)
  operator.js     (기존)
  style.css       (기존)
  pda.html        ← 신규
  pda.js          ← 신규
```

`server.py`의 do_GET에 경로 2줄을 추가한다(기존 화이트리스트 패턴 유지).

**새 프레임워크 없음. 새 프로세스 없음. 새 파이썬 의존성 없음.** 이 프로젝트가 표준 라이브러리로 MES를 만든 기조와 일관된다.

### 8.2 ⚠ 카메라와 보안 컨텍스트 — 가장 먼저 해결할 것

**`navigator.mediaDevices.getUserMedia`는 보안 컨텍스트(HTTPS 또는 localhost)에서만 동작한다.** PDA에서 `http://192.168.x.x:8000/pda.html` 로 접속하면 카메라 API 자체가 `undefined`이거나 즉시 거부된다. 데모 당일에 발견하면 복구 불가능한 종류의 문제다.

해결안 3가지(택1, 사전 검증 필수):

| 방안 | 방법 | 비용 | 비고 |
| --- | --- | --- | --- |
| **A. 자체 서명 TLS** | `ssl.SSLContext`로 `ThreadingHTTPServer` 감싸기. PDA에 인증서 1회 신뢰 등록 | 낮음 | 표준 라이브러리만으로 가능. **권장** |
| **B. Chrome origin 예외** | PDA Chrome의 `chrome://flags/#unsafely-treat-insecure-origin-as-secure` 에 Jetson 주소 등록 | 매우 낮음 | 단말 설정 의존. 데모용으로는 충분하나 재현성이 낮음 |
| **C. 터널** | PDA에서 `localhost` 로 보이게 포트 포워딩 | 중간 | 설정이 늘어남 |

A를 기본으로 하고 B를 당일 백업으로 준비한다. **이 검증이 다른 모든 작업보다 선행되어야 한다** — 여기서 막히면 카메라 요구 자체가 성립하지 않기 때문이다.

### 8.3 인식 코드 규모

```js
// pda.js — 개념 골격
const detector = 'BarcodeDetector' in window
  ? new BarcodeDetector({ formats: ['qr_code'] })
  : null;

async function scanFrame(video) {
  if (!detector) return arucoFallback(video);      // 2순위 경로
  const codes = await detector.detect(video);
  for (const c of codes) {
    const m = /^SHIFTLINK:EQ:(.+)$/.exec(c.rawValue);   // 접두어 검사 = 1차 방어
    if (m) return { eqId: m[1], method: 'qr' };
  }
  return null;
}
```

1순위 경로의 실질 분량은 수십 줄이다. 복잡도는 인식이 아니라 **UI 상태 관리와 폴백 흐름**에 있다.

## 9. 계약 설계

### 9.1 스캔 결과 구조

```python
@dataclass(frozen=True)
class EquipmentScan:
    scan_id: str            # "SC-0001" (접두어-4자리 규칙 준수)
    equipment_id: str       # 카탈로그에 실재해야 함
    method: Literal["qr", "aruco", "manual"]
    marker_value: str | None    # 디코딩된 원문 (감사용)
    frame_votes: int            # 일치한 연속 프레임 수 (1~3)
    scanned_at: datetime
    device_id: str | None       # PDA 식별(해시)
```

**신뢰도를 float로 두지 않는다.** 마커 디코딩은 성공/실패의 이산 사건이므로 `frame_votes`(몇 프레임이 같은 답을 냈는가)가 더 정직하고 검증 가능한 지표다. 분류기를 도입하게 되면 그때 `confidence` 필드를 추가한다.

### 9.2 질의 요청 확장

기존 `QueryRequest.eq_id`를 **재사용**한다. 새 필드를 만들면 라우터·파이프라인·도구 5종이 전부 영향을 받는다. 대신 **출처 필드만 추가**한다.

```python
class QueryRequest(BaseModel):
    question: NonBlank
    line_id: str
    eq_id: str                                   # 기존 그대로
    eq_id_source: Literal["camera_scan", "manual_selection", "unspecified"] = "unspecified"   # 신규
    scan_id: str | None = None                   # 신규, 감사 추적용
    observations: list[dict] = []
    k: int = 5
```

`HandoverRequest`도 동일하게 `eq_id_source` + `scan_ids: list[str]`만 추가한다.

이렇게 하면 **기존 44개 테스트가 그대로 통과**하고(새 필드는 기본값 보유), 감사 추적은 확보된다.

### 9.3 MES 엔드포인트

기존 양식(`/api/…`, 응답에 `is_synthetic: true`)을 따른다.

```http
POST /api/equipment/scan
{ "equipment_id": "HPU-01", "method": "qr",
  "marker_value": "SHIFTLINK:EQ:HPU-01", "frame_votes": 3 }

200 { "scan_id": "SC-0001", "equipment_id": "HPU-01",
      "name": "유압 유닛", "is_synthetic": true }
404 { "error": "unknown equipment_id: HPU-09", "is_synthetic": true }
```

```http
GET /api/equipment/scan/recent?limit=5
200 { "scans": [ … ], "is_synthetic": true }
```

**엔드포인트는 이 2개면 충분하다.** 별도 `confirm` 엔드포인트는 만들지 않는다 — 확정은 PDA에서 끝나는 UI 행위이고, 서버는 확정된 결과만 받는다. 서버 왕복을 늘리면 스캔 체감만 느려진다.

### 9.4 설비↔마커 매핑 저장 위치

`docs/data/reference/00_plant_and_relations.json`의 설비 항목에 **선택 필드 1개**를 추가한다.

```json
{
  "equipment_id": "HPU-01",
  "…기존 필드…",
  "markers": { "qr": "SHIFTLINK:EQ:HPU-01", "aruco_id": 30 }
}
```

별도 레지스트리 파일을 만들지 않는 이유: 설비 마스터가 이미 여기에 있고, 두 군데로 나뉘면 반드시 어긋난다. 정합성은 §13 T-3 테스트로 강제한다.

### 9.5 6번째 도구를 만들지 않는다

현재 도구 5종은 전부 **읽기 전용 조회**다. 이미지 인식 도구를 6번째로 추가하면:

- 에이전트가 카메라를 호출하는 구조가 되어 고정 파이프라인의 단순함이 깨진다
- 도구 계약에 쓰기(스캔 기록 저장)가 섞인다
- C-022(추가 MES API 채택은 별도 결정)에 걸린다

**식별은 에이전트의 일이 아니라 UI의 일이다.** 에이전트는 이미 확정된 `eq_id`를 받을 뿐이다. 도구는 5종을 유지한다.

## 10. 제약 등록부 개정안

### 10.1 C-056 개정

| | 내용 |
| --- | --- |
| 현행 | VLM·음성인식 등은 범위 밖이며, 도입하더라도 LLM과 동시 상주시키지 않고 순차 실행한다 |
| **개정안** | **VLM·음성인식은 계속 범위 밖이다. 설비 식별용 카메라는 도입하되, 인식 연산은 전량 PDA 단말에서 수행하고 Jetson에는 어떤 비전 모델도 적재하지 않는다. Jetson 상주 모델은 LLM 1개를 유지한다. 신경망 기반 인식(분류기·VLM)을 Jetson에 올리는 변경은 별도 결정 사항이다.** |
| 상태 | 개정 제안 |

개정의 취지는 제약을 **완화하는 것이 아니라 더 구체적으로 못 박는 것**이다. 현행 문구는 "동시 상주 금지"만 말해서 "순차 실행하면 되지 않나"라는 해석 여지가 있었다. 개정안은 **Jetson에 비전 모델을 아예 두지 않는다**로 강화한다.

| G-4 | 카탈로그의 모든 설비가 마커 매핑을 보유하고, 매핑이 1:1 | 불일치 0건 |

| G-7 | 카메라 이미지가 MES 상태·제어 경로로 전파되지 않음 | 경로 0건 |

### 13.2 카메라 없이 돌리는 전략

카메라와 실물 상자에 의존하면 CI에서 돌지 않는다. **생성한 이미지로 대체한다.**

- 테스트 픽스처는 `tests/fixtures/markers/` 에 **생성 스크립트로 만든 QR/ArUco 이미지**를 둔다. 상자 사진이 아니라 마커 이미지 자체면 충분하다 — 인식 계층은 상자를 모르기 때문이다(§6.4).
- 변형(회전, 저대비, 부분 가림, 블러)을 합성해 강건성 테스트를 만든다.
- QR 생성은 인쇄용 자산 생성 스크립트와 **같은 코드**를 쓴다. 그래야 인쇄물과 테스트가 어긋나지 않는다.
- 브라우저 JS 경로(`BarcodeDetector`)는 파이썬 테스트로 덮을 수 없다. **수동 체크리스트**로 분리하고 `[미측정]`으로 정직하게 표기한다.

### 13.3 수동 검증 체크리스트 (실물 필요)

| # | 항목 | 조건 |

| M-2 | 0.3 / 0.5 / 1.0 / 2.0 m 거리에서 인식되는가 | 거리별 |

## 14. 측정 지표와 목표치

| 지표 | 정의 | 목표 | 측정 |
| --- | --- | --- | --- |
| 식별 정확도 | 정상 조건에서 올바른 `equipment_id` 반환 비율 | **100%** | 픽스처 + 수동 M-2~M-4 |
| 오인식률 | 다른 설비로 확정되는 비율 | **0%** | 마커 방식상 0이 기본값. 1건이라도 나오면 설계 결함 |
| 스캔→확정 지연 | 상자를 비춘 시점부터 확정까지 | **< 1초** | PDA 내 계측 |
| 수동 폴백률 | 자동 인식 실패로 수동 선택에 이르는 비율 | **< 10%** | 스캔 로그 |
| 안전 카드 최초 표시 | 질의 시작~안전 카드 화면 노출 | **< 3초** | 부분 결과 선노출 경로 |
| p95 질의 지연 | 기존 지표 | 변화 없음 | **스캔 지연을 포함하지 않는다(D-40)** |

오인식률 목표를 **0%로 두는 것이 이 설계를 택한 이유**다. 확률형 분류기였다면 "5% 미만" 같은 목표를 세워야 했고, 그 5%가 안전 카드 오적용이 될 수 있었다. 마커 디코딩은 읽히거나 안 읽히거나이지, 다른 설비로 잘못 읽히는 일이 구조적으로 거의 없다.
