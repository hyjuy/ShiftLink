## 대조 결과 (감점 없음 — 확인한 것)

- `SYMPTOM_LABELS`(`pda.js:435-518`)의 카드 ID 57개는 모두 `kb_cards.json`에 있고, 전부 `status=accepted`, `split=kb`, `grade=L1`이다. 유형 주석(HPU/CV/RT/GR/CAU/PDP)도 각 카드의 `equipment`와 맞는다. dev·sealed 카드는 없다.
- 라벨에 적힌 수치(58℃, 62℃, 1.2 bar, 16 A, 80%)는 각 카드의 `symptom` 원문(K-1002, K-1025, K-1201/1202, K-1208, K-1011)과 같다.
- 질의 키: `queryApiPayload`가 `equipment_id`를 보낸다(`pda.js:709`). 화면 표시는 `code`(`pda.js:186`, `202`, `275`, `1431`)이고, `equipment_id`는 보조 줄에 따로 보인다(`pda.js:192`). 설비 유형은 `code` 접두어에서 나온다(`pda.js:79`). plant 파일의 10개 설비가 모두 이 규칙을 따른다(`00_plant_and_relations.json:234-597`).
- `cardFits`(`pda.js:46-47`)는 `mes_equipment_id`로 설치를 거른다. 그래서 GR-02(EQ-0005)에는 EQ-0004 전용 카드(K-1209/1210/1212/1216/1219)가 나가지 않는다.
- safety_flag=true 카드 가운데 `safety_basis=null`인 것은 없다. 따라서 `근거 미기재` 대체 문구(`pda.js:788`)가 실제 카드에서 뜨는 경로가 없다.

## 감점 내역

### D1 실값 사용 (-1 / 6)
- 근거: `pda.js:464` K-1203 라벨 `'출구 압력 정상 · 압력/유량 부족'`. 원문(`kb_cards.json:3188`)은 "펌프 출구 압력은 **읽히지만** … 압력 또는 유량이 부족"이고, "정상"은 원천에 없는 주장이다. 같은 줄 안에서 '압력 정상'과 '압력 부족'이 서로 모순된다.
- 근거: `pda.js:445` K-1012 라벨 `'벨트 교체 후 편주'`. 원문(`kb_cards.json:901`)은 "벨트 교체 후 **또는 사용 중**"이어서 라벨이 적용 범위를 좁힌다. `pda.js:448` K-1011과 `pda.js:456` K-1025는 원문의 "프로젝트 기준이며 원문 임계값이 아니다" 단서를 뺐다.
- 왜 문제인가: 작업자는 원문이 아니라 라벨을 보고 고른다. 원문은 선택한 뒤에야 보인다(`pda.js:633`). 실제 카드 내용과 다른 문장이 선택 기준이 된다.

### D2 ID 혼용 없음 (-1 / 5)
- 근거: `pda.js:1143-1146`. 인계 확인은 `equipment_id`가 아니라 `open_items[].text`에 `code` 문자열이 들어 있는지로 거른다. 일치하는 기록이 없으면 `S.handovers` 전체로 대체한다. 서빙되는 유일한 인계 HO-0101(`EV-0031_upstream_cause.json:1170-1209`)은 GR-01·RT-03 사건이다. 그래서 HPU-01·PDP-01 등 다른 설비를 확정한 상태에서도 이 GR-01 인계가 "미종료 3건"으로 나오고, 다른 설비라는 표시가 없다.
- 근거: `pda.js:1288`. 업로드 대기 카드의 `설비` 칸은 설비를 찾으면 `code`를, 못 찾으면 `equipment_id` 원문을 같은 자리에 넣는다. 같은 칸에 두 식별자가 섞인다.
- 왜 문제인가: 화면 상단 컨텍스트(`#ctx`)의 설비와 본문 인계의 설비가 갈라진다. 서버 키(`equipment_id`)를 쓰지 않고 자유 문장에서 code를 찾는 매칭이다.

### D3 지어내지 않음 (-3 / 4)
- 근거: `pda.js:967-977`. 「이 조치 시도」(`pda.js:907-908`)를 한 번 누르면 시도 기록이 결과 확인 없이 즉시 만들어진다. 고정 문자열 `failure_reason: '조치 후에도 증상이 유지됨'`이 들어가고, `pda.js:996`이 「효과 없음」을 표시한다. 작업자가 효과 여부를 입력하는 단계가 없다.
- 근거: `pda.js:970-972`. 시도의 `observed_result`에는 누르기 **전**의 관측값이 그대로 들어가는데, 화면에는 이것이 조치 결과 「관측」으로 보인다(`pda.js:998`, `1002`). 이 꾸며진 실패 기록은 인계 맥락 문구 「시도 N건 실패」(`pda.js:1211`)와 서버 저장 페이로드 `attempts:S.tries`(`pda.js:1360`)로 넘어간다. → -2
- 근거: `pda.html:503-505`. 인계 `required_context` 입력칸에 `야간조 정비 담당`, `교대 직후 최초 기동 전`, `구두 인계 + 인계서 기록`이 미리 채워져 있다. `docs/data`에 이 값의 원천이 없다. 데이터의 교대 체계는 A/B/C조다(`EV-0031_upstream_cause.json:1174-1175`). 작업자가 손대지 않으면 이 값이 그대로 저장된다(`pda.js:1358-1359`). → -1
- 왜 문제인가: 원천 없는 시도 결과와 수신자 정보가 실제 인계 기록으로 서버에 남는다. 다음 교대는 시도하지 않았거나 결과를 모르는 조치를 "실패함"으로 받는다.
