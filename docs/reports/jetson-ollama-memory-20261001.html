2. 원인 추적

2-1. 전원·과열이 아니라 메모리

처음에는 전원 부족을 의심했다 (종료 기록 없이 꺼짐, 부하 중에만 발생). tegrastats 기록은 달랐다.

2-2. 메모리를 먹는 것은 llama-server

실행 중 llama-server가 10초에 약 240MB씩 커졌다 (2.9GB → 3.1GB). 모델 크기는 1.7GB다. ollama stop으로 모델을 내리면 남은 메모리가 5.5GB로 돌아왔다.

2-3. 무엇이 늘리는가 — 4조건 테스트

같은 모델로 조건마다 30번 요청하고 llama-server 메모리 증가를 쟀다.

2-4. 확정 — 프롬프트 캐시

  • ollama 로그에 요청마다 prompt_save: saving prompt with length 176, total state size = 12.893 MiB가 찍혔다. 조건 D의 요청당 12.5MB와 같다.
  • llama-server --help: --cache-ram N … (default: 8192 …) (env: LLAMA_ARG_CACHE_RAM)
  • ollama가 llama-server를 띄우는 인자에 --cache-ram이 없어 기본값 8192MiB가 그대로 적용된다.
  • 실제 실험 프롬프트는 약 1000토큰이라 한 번에 약 70MB가 쌓인다. 분당 약 1GB 증가와 맞는다.
  • 9/29 벤치마크가 무사했던 것은 실행이 짧았기 때문으로 본다. ollama는 9/16 이후 바뀌지 않았다.

3. 해결

Jetson에서 실행 (sudo 필요):

sudo mkdir -p /etc/systemd/system/ollama.service.d && printf '[Service]\nEnvironment="LLAMA_ARG_CACHE_RAM=0"\n' | sudo tee /etc/systemd/system/ollama.service.d/cache-ram.conf && sudo systemctl daemon-reload && sudo systemctl restart ollama && systemctl show ollama -p Environment | grep -o 'LLAMA_ARG_CACHE_RAM=0'
  • 마지막에 LLAMA_ARG_CACHE_RAM=0이 나오면 적용된 것이다. ollama 로그에는 prompt cache is disabled가 찍힌다.
  • sudo systemctl edit ollama로 넣을 때 ### Lines below this comment will be discarded 아래에 쓰면 버려진다. 첫 시도는 이것 때문에 적용되지 않았다.
  • drop-in 파일이라 ollama를 재설치해도 유지된다.
  • 앞부분이 같은 요청(시스템 프롬프트)은 슬롯의 KV 캐시가 계속 재사용한다 (로그의 cached n_tokens = 516).
  • 나중에 캐시가 필요하면 0 대신 작은 값(예: 512)을 쓴다. 8192는 이 장비에서 쓰면 안 된다.

5. 함께 드러난 문제

  1. 연결 실패가 0점으로 기록됨. Jetson이 꺼진 뒤의 요청은 파이프라인이 ConnectionError를 잡아 검토 대기열로 넘겨, 채점에서 오류가 아니라 "인용 없음"으로 세졌다. v2~v4의 0/29가 이렇게 나와 무효 처리하고 다시 돌렸다. 실험 스크립트는 방식마다 앞뒤로 Jetson 연결을 확인하고 끊기면 결과를 .INVALID로 표시하게 고쳤다.
  2. 멈춘 실험이 계속 요청을 보냄. 백그라운드 실행을 멈춰도 Windows에서 자식 Python 프로세스가 남아 Jetson에 요청을 보냈다. 실험을 멈출 때 남은 프로세스도 확인한다.

6. 남은 일

  • Jetson은 한 대뿐이고 이미 적용했으므로 장비 쪽 추가 작업은 없다. 서비스 코드의 KEEP_ALIVE=-1도 그대로 쓴다.
  • ☐ eval/qa/score.py가 모델 오류(연결·시간 초과)를 따로 세게 할지 검토 (5-1)
