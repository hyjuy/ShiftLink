## 2. 현재 스키마 v1.1 (v1.0 규칙 유지)

`SCHEMA_VERSION = "1.1"` 모듈 상수. 기존 필드·검증을 기반으로 공백·연산자·유형별 필드 제한을 보완했고, §6의 선택 메타데이터를 추가했다. 카드 `version`은 전달받은 데이터 버전으로 보존하며 구현 버전과 동일하다고 가정하지 않는다.

공통 최소 조건: T1·T3는 공백 아닌 `symptom`, T2는 `conditions` 1개 이상, T5는 `safety_flag=true`가 필수다. 모든 유형에서 `safety_flag=true`이면 공백 아닌 `safety_basis`가 필수다. `symptom`·`safety_basis`는 선택인 경우 null/생략 가능하나, 문자열로 주어지면 공백만일 수 없다.

신규 생성은 `status="draft"`, `grade="L0"`로 시작한다. 이는 생성 정책이며 기존 accepted/L1 데이터의 스키마 허용을 없애지 않는다. 모델이 채택·승인을 결정하지 않는다. ID·출처·분할·시각·실행 버전은 입력/실행기가 공급하고, 근거 없는 confidence를 만들지 않는다. 필수 정보가 부족하면 별도 검수 기록에 원문과 부족 항목을 남긴다. 보완 큐의 자동 생성·저장 기능은 아직 구현되지 않았다.

#### 2.1.1 T1~T6 경계 규칙 `[현재 작성 기준]`

2026-09-22 사용자 요청으로 작성 가이드·프롬프트를 아래 기준에 맞춘다. 이는 현 작업의 작성 기준이며 전문가 원 정의나 과거 회의 승인을 새로 확정했다는 뜻이 아니다.

| 상황 | 유형 | 판단 근거 |
|---|---|---|
| 감각 기반 이상 징후의 의미 해석 | T1 | 증상의 의미가 핵심; 증상 유무나 단계 수로 T3와 구분하지 않음 |
| 조건에 따라 적용할 요령이 달라짐 | T2 | 조건별 요령 차이가 핵심; 단순 적용 범위는 다른 유형의 conditions로 기록 |
| 증상에서 원인을 좁혀가는 확인 순서 | T3 | 목적이 원인 규명 |
| 정지 상태에서 운전 상태로 되돌리는 절차·실패 경험 | T6 | 목적이 상태 복귀 |
| 재가동 미완료 상태를 다음 교대에 넘기는 방법 | T4 | 목적이 전달 |
| 재가동 중 독립적인 금지·중지·격리 지식 | T5 | 금기 자체가 핵심; 부수적인 주의사항은 원래 유형 + safety_flag |

한 카드가 독립적인 두 목적을 담으면 분리한다. 독립적인 안전 금기는 T5로 분리하고, 다른 유형에 부수적인 안전 내용은 safety_flag로 표시한다. T1~T6 전체의 기계적인 우선순위는 두지 않는다. 사건별 인계 현황은 원문/인계 기록이며, T4 카드는 재사용 가능한 인계 방법과 5개 필수 필드의 근거가 있어야 한다.

카드 하나에 주된 목적 하나를 지정한다. 분리는 각 지식이 따로 검색돼도 쓸모 있을 때만 하며, 같은 목적의 근거·조건·부연 설명은 분리하지 않는다. 독립 T5로 분리해도 원래 카드에 필요한 안전 표시·근거·중지 조건을 유지한다.

T6는 현 스키마를 유지하며 재가동 순서는 know_how에 기록한다. 원인 진단과 재가동이 독립적인 지식이면 T3와 T6로 분리하지만, 단계 저장만을 위해 재가동 지식을 T3로 바꾸지 않는다. T6의 단계별 표시·순서 검증이 실제 요구사항으로 확정되면 스키마 계약·검증·생성 지침·응답 표시·평가를 함께 확장한다. 이번 결정으로 새 필드나 카드 연결 기능을 추가하지 않는다. 분류 예시는 [현재 작성 가이드](../../seeds/카드_작성_가이드_초안.md#21-유형-경계-적용-기준-2026-09-22-사용자-요청-반영)를 따른다.

### 2.2 v1.0 기본 모델 요약 (v1.1 선택 필드는 §6)

```python
NonBlank = Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]

class HandoverMethod(BaseModel):          # D-27: T4 전달 방법
    required_context: list[NonBlank]      # min_length=1, 전달할 정보
    recipient_role: NonBlank              # 대상
    timing: NonBlank                      # 시점
    channel: NonBlank                     # 방법
    acknowledgement: NonBlank             # 확인 방법

class ResolutionStep(BaseModel):          # D-28: T3 단계
    step_id: str                          # pattern ^ST-\d{2,4}$
    order: int                            # ge=1
    action: NonBlank
    preconditions: list[str] = []
    expected_result: NonBlank
    stop_conditions: list[str] = []       # 길이 제한·요약으로 잘라내지 않음

RestartType = Literal["normal_stop_restart", "abnormal_stop_restart",
                      "maintenance_restart", "unknown"]
# 가상 설비 사전 기반 잠정 허용값. 현장 표준으로 단정하지 않음.

class FailedAttempt(BaseModel):           # D-29: 시도·실패
    attempt_id: str                       # pattern ^AT-\d{4}$
    restart_type: RestartType
    action: NonBlank
    observed_result: NonBlank
    failure_reason: str | None = None     # None = 이유 미상 보존. "미상" 문자열 자동 기입 금지
    evidence_ids: list[str] = []          # ^(K|EV|AR)-\d{4}$ 형식만 검사. 실존 검증은 별도 배치 검증 필요

class TypePayload(BaseModel):
    handover_method: HandoverMethod | None = None
    steps: list[ResolutionStep] | None = None
    restart_type: RestartType | None = None
    tried_and_failed: list[FailedAttempt] = []
```

### 2.3 검증 규칙 (model_validator, 위반은 ValidationError)

기존 규칙 유지 + 추가:

1. T4 → `type_payload.handover_method` 필수. (“인계했다” 사실만 있는 카드 차단은 구조 필수화로 달성)
2. T3 → `type_payload.steps` 필수(1개 이상). 각 `order`는 1 이상의 정수이며 1부터 시작하거나 연속일 필요는 없다. `step_id` 중복 금지, `order` 중복 금지, 리스트는 `order` 오름차순이어야 함(정렬 자동 수정 금지 — 위반 시 오류).
3. T6 → `type_payload.restart_type` 필수. T6도 T5와 무관하게 `safety_flag` 규칙은 기존대로.
4. `tried_and_failed`의 각 attempt: 카드·시도 restart_type이 모두 known인데 서로 다르면 오류. known 카드 + unknown 시도는 허용한다. 카드가 unknown 또는 null/생략(T1~T5만)이면 시도는 어떤 허용 유형이든 가능하다.
5. `handover_method`가 T4 외 카드에 있으면 오류, `steps`가 T3 외 카드에 있으면 빈 목록도 오류다. 다른 유형은 null/생략한다. `restart_type`/`tried_and_failed`는 전 유형 허용(2.1). T6의 재가동 설명은 know_how와 재가동 필드에 기록하며 구조화된 T6 단계는 별도 계약 변경 대상이다.

### 2.4 사건·카드 책임 분리

- `Event.restart_attempts: list[FailedAttempt] = []` 추가 — 사건별 시도 이력.
- 카드의 `tried_and_failed`는 재사용 가능한 일반화 지식, Event의 `restart_attempts`는 해당 사건 이력. Event는 `true_cause` 등 평가 정답을 포함하므로 런타임 KB·모델 입력에 절대 전달하지 않는다(하니스가 카나리로 검사).

### 4.2 조건 매칭 규칙 (결정적)

2026-09-22 보완: 일반 `search_cards(..., observations=None)`와 안전 검색은 동일한 조건 평가를 사용한다. 적용 조건 False 또는 제외 조건 True는 순위 계산 전에 제외한다. 남은 조건 중 하나라도 미확인이면 `unverified`, 모든 조건을 확인했거나 조건이 없으면 `verified`이다. 일반 검색의 관측값도 질의 입력에서 전달한다.

- `Condition.op` ∈ {==,!=,>,>=,<,<=}. observations에 signal이 있고 조건이 False로 확정 → 카드 제외. exclusions가 True로 확정 → 카드 제외.
- observations에 signal이 없으면 unknown → 제외하지 않되 결과에 `condition_status: "unverified"` 표기. 안전 카드도 동일(보수적 포함).

## 6. 실행·검증

### 2026-09-22 선택 메타데이터 확장 (스키마 구현 1.1)

사용자 요청에 따라 다음 선택 필드를 추가한다. 기존 카드의 `version`, 채택 상태, T4 필수 항목은 유지한다. `SCHEMA_VERSION`은 구현 계약 버전 `1.1`이며 과거 카드의 버전과 출처 기록을 소급 변경하지 않는다. 아래 확장은 9/21 회의 승인 사항으로 간주하지 않는다.

| 위치 | 선택 필드 | 용도 |
|---|---|---|
| `KnowledgeCard.generalization_evidence` | `supporting_event_ids`, `contradicting_event_ids`, `generalization_scope`, `confidence_basis` | 출처 자체와 구별되는 지지·반대 관계 및 일반화 근거 |
| `FailedAttempt` | `evidence_gap`, `next_observations`, `required_data`, `data_collection_role` | 근거 공백의 유형과 후속 수집 정보 |
| `ResolutionStep` | `verification_step`, `rollback_action`, `escalation_target`, `escalation_channel` | 결과 확인·복구·보고 경로 |
| `KnowledgeCard.safety_review` | `status`, `approved_by`, `approver_role`, `reviewed_at`, `valid_until`, `review_triggers`, `evidence_grade`, `safety_level` | 사람의 안전 검토 기록 |
| `Provenance` | `sources[]`, `extraction_method`, `model_version`, `prompt_version`, `index_version`, `schema_version` | 원문 위치와 생성·추출 실행의 추적 |
| `Provenance.sources[]` | `source_id`, `locator`, `document_version` | 원문 식별자, 페이지·절 등 위치, 문서 버전 |

- 모든 새 상위 필드는 미지정 가능하다. 미상 값은 null/빈 목록으로 보존하며 자동 생성하지 않는다. 값이 제공된 새 문자열은 공백을 허용하지 않는다.
- 지지·반대 사건 ID는 `EV-0001` 형식이고 각 목록은 중복 없이 서로 겹치지 않아야 한다. `provenance.event_ids`는 출처, 새 목록은 근거의 역할이므로 자동 복사하지 않는다. ID 실존·분할 검사는 별도 데이터 검증 책임이며 사건 본문을 자동 조회하지 않는다.
- `evidence_gap`은 `not_observed`, `not_recorded`, `insufficient_evidence`, `conflicting_evidence`. `failure_reason=None`을 대체하지 않으며 일부 이유와 추가 근거 공백은 공존할 수 있다.
- `safety_review.status`는 `draft`, `pending_review`, `approved`, `restricted`, `expired`, `withdrawn`. 기존 `KnowledgeCard.status`와 별개다. `approved` 기록에는 승인자·역할·검토일·유효기한·근거 등급이 필요하다. 날짜는 시간대가 필요하며 유효기한은 검토일 이후여야 한다.
- 안전 검토는 **메타데이터 저장만** 지원한다. 승인 권한 확인, 상태 전이, 자동 만료, 조회 차단 정책은 구현하지 않았다. 과거 `approved` 기록이 현재 유효한 승인을 보장하지 않는다. 기존 `accepted/L1/kb` 적재 정책은 유지한다.
- 응답의 `card_metadata[card_id]`에 출처·일반화 근거·검토 기록을 보존한다. 단계 및 실패 메타데이터는 구조화 응답과 텍스트에 전달한다. 모델·프롬프트·인덱스 버전은 구조화 메타데이터로 보존하고 화면에 일괄 출력하지 않는다.
- 신규 필드는 향후 필수 확장을 뜻하지 않는다. 원문 추적·실패 조사·현장 절차·검토 운영 등 실제 용도가 있는 것만 채운다. 필드 추가 자체로 검색 품질 향상을 주장하지 않는다.
- 검색 활용: 기존 `know_how` 외에 제목·증상·구성요소·일반화 적용 범위·단계 조치/예상 결과/확인 방법/사전 조건·인계 정보·실패 조치/관찰 결과/이유/추가 관찰/필요 자료를 토큰 일치 검색에 사용한다. 승인자·생성 모델·출처 ID는 순위 점수에 사용하지 않는다. 조건 평가 후 top-k를 선택하고 해당 카드만 직렬화한다. 이는 인메모리 어댑터 개선이며 벡터·하이브리드 인덱스나 대규모 운영 성능 검증을 대체하지 않는다.
