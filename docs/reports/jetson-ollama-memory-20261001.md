# Jetson 실험 중 다운 — 원인과 해결 (2026-10-01)

작성: 최재영·Claude · 장비: Jetson Orin Nano Super (jetson-06, 7.6GB RAM, 15W) · ollama 0.34.1 · 같은 내용 HTML: [jetson-ollama-memory-20261001.html](jetson-ollama-memory-20261001.html)

## 요약

- **증상**: 모델 실험을 돌리면 5~10분 뒤 Jetson이 응답을 멈추고 재부팅이 필요했다 (9/30 1회, 10/1 2회).
- **원인**: ollama가 띄우는 `llama-server`의 RAM 프롬프트 캐시(`--cache-ram`). 기본 상한이 8192MiB로 장비 메모리(7.6GB)보다 커서, 새 프롬프트마다 상태를 저장하다 RAM과 스왑을 다 채웠다.
- **해결**: ollama 서비스에 `LLAMA_ARG_CACHE_RAM=0`을 넣어 이 캐시를 껐다. 코드 변경 없음.
- **확인**: 요청당 메모리 증가 12.5MB → 0.1MB. 실제 실험 1회분에서 메모리가 일정했고, 정확도와 응답 시간은 그대로였다.

## 2. 원인 추적

### 2-1. 전원·과열이 아니라 메모리

처음에는 전원 부족을 의심했다 (종료 기록 없이 꺼짐, 부하 중에만 발생). `tegrastats` 기록은 달랐다.

| 항목 | 값 | 판단 |
|---|---|---|
| 입력 전력 최대 (`VDD_IN`) | 20.6W | 15W 모드의 순간 최대로 정상 |
| 온도 최대 (`tj`) | 65.7°C | 정상 |
| RAM | 09:45 1.8GB → 09:48 6.4GB → 09:51 **7.4/7.6GB** | 분당 약 1GB 증가 |
| 스왑 | 09:48 0 → 09:51 **3.8/3.8GB** | 가득 참 |

마지막에는 2초 간격 기록이 1분 간격으로 늘어졌다. 메모리와 스왑이 모두 차서 시스템이 멈춘 것이다. 그래서 전력 모드를 25W로 올리는 것은 해결책이 아니다.

### 2-2. 메모리를 먹는 것은 `llama-server`

실행 중 프로세스별 메모리를 보면 `llama-server`가 10초에 약 240MB씩 커졌다 (2.9GB → 3.1GB). 모델 크기는 1.7GB다. `ollama stop`으로 모델을 내리면 남은 메모리가 5.5GB로 돌아왔다.

### 2-3. 무엇이 늘리는가 — 4조건 테스트

같은 모델로 조건마다 30번 요청하고 `llama-server` 메모리를 쟀다. 조건마다 모델을 내렸다가 다시 올렸다.

| 조건 | 30회 증가 | 요청당 | 모양 |
|---|---|---|---|
| A 같은 입력, 출력 형식 없음 | 25MB | 0.8MB | 처음에만 늘고 멈춤 |
| B 같은 입력, 같은 출력 형식 | 44MB | 1.5MB | 처음에만 늘고 멈춤 |
| C 같은 입력, 출력 형식만 매번 다름 | 279MB | 9.3MB | 계속 증가 |
| D 입력이 매번 다름, 출력 형식 없음 | **375MB** | **12.5MB** | 계속 증가 |

출력 형식(JSON 스키마)만의 문제가 아니었다. 입력이 처음 보는 것이면 무엇이든 메모리가 늘었다 (D).

### 2-4. 확정 — 프롬프트 캐시

- ollama 로그에 요청마다 `prompt_save: saving prompt with length 176, total state size = 12.893 MiB`가 찍혔다. 조건 D의 요청당 12.5MB와 같다.
- `llama-server --help`: `--cache-ram N  set the maximum cache size in MiB (default: 8192, ...)  (env: LLAMA_ARG_CACHE_RAM)`
- ollama가 `llama-server`를 띄우는 인자에 `--cache-ram`이 없다. 그래서 기본값 8192MiB가 그대로 적용된다.
- 실제 실험 프롬프트는 약 1000토큰(카드 5장)이라 한 번에 약 70MB가 쌓인다. 분당 약 1GB 증가와 맞는다.
- 같은 입력은 저장된 상태를 다시 쓰므로 늘지 않는다 (A, B).

9/29 벤치마크가 무사했던 것은 실행이 짧아 상한 근처까지 가지 않았기 때문으로 본다. ollama는 9/16 이후 바뀌지 않았다.

## 3. 해결

Jetson에서 실행 (sudo 필요):

```
sudo mkdir -p /etc/systemd/system/ollama.service.d && printf '[Service]\nEnvironment="LLAMA_ARG_CACHE_RAM=0"\n' | sudo tee /etc/systemd/system/ollama.service.d/cache-ram.conf && sudo systemctl daemon-reload && sudo systemctl restart ollama && systemctl show ollama -p Environment | grep -o 'LLAMA_ARG_CACHE_RAM=0'
```

- 마지막 줄에 `LLAMA_ARG_CACHE_RAM=0`이 나오면 적용된 것이다. 재시작 후 ollama 로그에 `prompt cache is disabled`가 찍힌다.
- `sudo systemctl edit ollama`로 넣을 때 `### Lines below this comment will be discarded` 아래에 쓰면 버려진다. 처음 시도는 이것 때문에 적용되지 않았다.
- 설정은 drop-in 파일에 들어간다. ollama를 재설치해 `ollama.service`가 다시 써져도 유지된다.
- 0은 RAM 캐시를 끈다. 시스템 프롬프트처럼 앞부분이 같은 요청은 슬롯의 KV 캐시가 계속 재사용한다 (로그의 `cached n_tokens = 516`).
- 나중에 캐시가 필요하면 0 대신 장비에 맞는 작은 값(예: 512)을 쓴다. 8192는 이 장비에서 쓰면 안 된다.

## 4. 확인

| 항목 | 적용 전 | 적용 후 |
|---|---|---|
| 조건 C 요청당 증가 | 9.3MB | 0.7MB (처음에만) |
| 조건 D 요청당 증가 | 12.5MB | 0.1MB |
| 실제 실험 (v3, 31문항) 중 남은 메모리 | 분당 약 1GB 감소 | 2.8~2.9GB로 일정 |
| v3 모델 1순위 정답 | 23/29 (8문항마다 모델 재적재로 우회) | 22/29 (우회 없음) |
| v3 응답 시간 p50 | 2.81초 | 2.87초 |

정답 1개 차이는 GPU 연산의 비결정성 범위로 본다 (temperature 0에서도 생긴다). 우회용 "8문항마다 모델 다시 올리기"는 실험 스크립트에서 뺐다.

## 5. 함께 드러난 문제

1. **연결 실패가 0점으로 기록됨**: Jetson이 꺼진 뒤의 요청은 파이프라인이 `ConnectionError`를 잡아 검토 대기열로 넘겼다. 그래서 채점에서 오류가 아니라 "인용 없음"으로 세졌다. v2~v4의 0/29 결과가 이렇게 나왔고, 무효로 처리하고 다시 돌렸다.
   - 실험 스크립트는 방식마다 앞뒤로 Jetson 연결을 확인하고, 끊기면 결과를 `.INVALID`로 표시하고 멈추게 고쳤다.
   - 후속 과제: `eval/qa/score.py`가 모델 오류(연결·시간 초과)를 `error`로 따로 세게 할지 검토한다.
2. **멈춘 실험이 계속 요청을 보냄**: 백그라운드 실행을 멈춰도 Windows에서 자식 Python 프로세스가 남아 Jetson에 요청을 계속 보냈다. 실험을 멈출 때는 남은 프로세스도 확인한다.
