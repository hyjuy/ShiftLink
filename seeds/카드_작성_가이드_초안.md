# 카드 작성 가이드 — 스키마 v1.1

실행 방법: [근거 연결·검증·초안 저장 파이프라인](../docs/guides/card-generation.md). 검토된 발췌문을 입력하고, 생성 실패는 보완 대기 기록에서 확인한다.

> 생성 원문 선택과 데이터 분할은 [원문·출처·평가 분할 계약](../docs/data/policies/source-and-split-contract.md)을 따른다. 등록된 출처라도 검토된 사용 범위가 없는 경우 생성 근거로 확정하지 않는다.

> 최초 작성: 2026-09-17 / 정합성 개정: 2026-09-22
>
> 적용 대상: K-01 KnowledgeCard.tacit_type (T1~T6)
>
> 상태: 현재 구현에 맞춘 작성 기준. 전문가의 도메인 타당성 검토·현장 승인을 대체하지 않는다.

## 1. 기준과 책임

형식과 자동 검증은 [schemas.py](../shiftlink/agent/schemas.py), 교차 필드 규칙은 [구현 계약](../docs/design/D26-29_계약_v1.0.md), 생성 지시는 [GENERATION_PROMPT_TEMPLATE](../shiftlink/rag/retrieval.py)를 따른다. 과거 통합 설계의 미결 제안을 자동으로 필수화하지 않는다.

T6는 9/21 회의 이후 팀이 확정한 정식 유형이다. v1.1 선택 메타데이터는 후속 사용자 요청으로 추가했다. 둘 다 9/21 회의 자체의 승인 사항으로 보고하지 않는다. 유형 경계는 현재 작업의 작성 기준이며, 전문가 원 정의문이 확인되면 변경 영향과 적용 버전을 기록한다.

KnowledgeCard는 재사용 가능한 지식, Event는 사건 사실, Artifact는 원문 자료다. 사건별 인계 현황만으로 T4 카드를 만들지 않는다. 평가용 Event의 true_cause·true_actions 등을 런타임 KB·응답 모델에 전달하지 않는다.

## 2. 유형 판정과 필수 조건

| 유형 | 주된 효용 | 필수 조건 | 경계 |
|---|---|---|---|
| T1 | 감각 기반 이상 징후의 해석 | 공백 아닌 symptom | 진단 순서가 핵심이면 T3, 조건부 요령이면 T2 |
| T2 | 적용 조건에 따른 요령 | conditions 1개 이상 | 조건이 언급됐다는 이유만으로 T2가 되지 않음 |
| T3 | 증상에서 원인을 좁히는 확인 절차 | symptom, type_payload.steps 1개 이상 | 단계 수만으로 분류하지 않음. 상태 복귀가 목적이면 T6 |
| T4 | 재사용 가능한 인계 방법 | type_payload.handover_method의 5개 필드 | 사건 상태 전달문은 원문/인계 기록. 인계 방법이 있어야 카드화 |
| T5 | 독립적인 안전 금기·중지·격리 지식 | safety_flag=true, 공백 아닌 safety_basis | 다른 유형도 안전 내용이 있으면 safety_flag 사용 |
| T6 | 정지 후 재가동·상태 복귀의 지식과 실패 경험 | type_payload.restart_type | 원인 규명은 T3, 재가동 미완료를 전달하는 방법은 T4 |

독립적인 안전 금기는 T5로 분리한다. 다른 유형에 부수적인 안전 내용은 safety_flag와 근거로 표시한다. 독립적인 목적이 여럿이면 분리하며, T1~T6 전체의 기계적인 우선순위는 두지 않는다. 판정 불가 시 별도 검수 기록에 보류한다. ‘판정 보류’는 tacit_type이나 status의 허용값이 아니다.

### 2.1 유형 경계 적용 기준 (2026-09-22 사용자 요청 반영)

- 카드 하나에 주된 목적 하나를 지정한다. 각각 따로 검색해도 쓸모 있는 독립적인 목적이 둘이면 분리한다. 같은 목적의 근거·조건·부연 설명은 분리하지 않는다.
- T1은 “이 징후가 무엇을 뜻하는가”, T3는 “무엇을 확인해 원인을 구분하는가”에 답한다. 증상 유무나 단계 수만으로 구분하지 않는다.
- T2는 조건에 따라 적용할 요령이 달라지는 것이 핵심일 때 선택한다. 조건이 단순한 적용 범위라면 원래 유형을 유지한다.
- 금지·중지·격리 자체가 핵심이면 T5다. 다른 지식에 딸린 주의사항은 해당 유형의 safety_flag와 safety_basis로 기록한다. 독립 T5로 분리해도 원래 카드에 필요한 안전 표시·근거·중지 조건을 제거하지 않는다.
- T6는 현 스키마를 유지한다. 원인 진단과 재가동이 각각 독립적인 지식이면 T3와 T6로 분리하되, 재가동 순서를 저장하려는 이유만으로 T3로 바꾸지 않는다.

분류 검토 예시(실제 작업 지시나 원인 확정이 아님):

| 지식의 핵심 | 판정 |
|---|---|
| 평소와 다른 진동의 의미를 해석 | T1 |
| 확인 결과를 따라 진동의 원인 후보를 좁힘 | T3 |
| 운전 조건에 따라 기록 요령을 달리함 | T2 |
| 특정 운전 조건에서만 적용하는 원인 확인 절차 | T3 + conditions |
| 접근 금지 자체를 설명 | T5 |
| 원인 확인 절차에 중지 조건이 포함됨 | T3 + safety_flag + safety_basis |
| 정지 후 상태 복귀 순서를 설명 | T6; 현재는 know_how에 기록 |

## 3. 공통 작성 규칙

- 모든 카드에 ID·버전·유형·설비·구성요소·시나리오·제목·노하우·판단 근거·신뢰도·출처·분할이 필요하다. 정확한 키와 허용값은 KnowledgeCard.model_json_schema()로 확인한다. 필수값을 임의로 채우거나 null로 대체하지 않는다.
- 신규 초안은 status="draft", grade="L0"로 작성한다. 이는 생성 정책이며 스키마는 기존 검수 완료 데이터도 읽는다. 생성 모델이 accepted/L1로 승격하지 않는다. KB 적재 조건은 accepted AND grade=L1 AND split=kb이다.
- version은 전달받은 카드/데이터 버전, SCHEMA_VERSION="1.1"은 구현 계약 버전이다. 과거 버전을 소급 변경하지 않는다. 신규 provenance.schema_version은 실행기가 실제 값으로 기록한다.
- ID·시드/사건 ID·분할·생성 시각·모델/프롬프트 버전은 입력 또는 실행기가 제공한다. 출처나 confidence 수치를 근거 없이 창작하지 않는다.
- safety_flag=true이면 유형과 무관하게 공백 아닌 safety_basis가 필요하다. symptom·safety_basis는 선택인 경우 null/생략 가능하지만, 제공된 문자열은 공백만일 수 없다.
- conditions/exclusions의 연산자는 ==, !=, >, >=, <, <=만 허용한다. signal, op, value는 필수, unit은 선택이다.
- 적용 조건 False 또는 제외 조건 True이면 검색에서 제외한다. 조건 미확인은 unverified로 남기며 조치 제안을 보류한다. 안전 경고는 유지한다.
- 필수 증상·단계·인계 방법·안전 근거가 없으면 원문과 부족 항목을 별도 보완 대기에 남긴다. 값을 창작하지 않는다. 보완 큐의 자동 생성·저장 기능은 아직 구현되지 않았다.

## 4. 유형별 상세 규칙

### T3 단계

- steps는 1개 이상, 각 order는 1 이상의 정수다. **1부터 시작하거나 연속일 필요는 없다.** 원문 순번을 보존하고 오름차순으로 입력한다. 검증기가 자동 정렬하지 않는다.
- step_id는 ^ST-\d{2,4}$ 형식이다. ST-01, ST-001 모두 유효하다. 카드 내 step_id와 order는 각각 중복을 금지한다.
- action, expected_result는 공백이 아니어야 한다. preconditions, stop_conditions는 선택 목록이며 제공된 조건을 잘라내지 않는다.
- verification_step, rollback_action, escalation_target, escalation_channel은 확인된 정보만 기록한다. 분기 그래프·자동 실행 엔진은 현재 스키마에 없다.
- steps는 T3만 사용할 수 있다. 다른 유형은 null/생략하며 steps=[]도 금지다. T6는 know_how와 재가동 필드에 기록한다. 구조화된 T6 단계는 별도 계약 변경 대상이다.
- T6의 단계별 표시·순서 검증이 실제 요구사항으로 확정되면 단계 지원을 확장한다. 그때 스키마 계약·검증·생성 지침·응답 표시·평가를 함께 변경한다. 현재는 필드나 카드 연결 기능을 추가하지 않는다.

### T4 인계 방법

required_context(공백 아닌 문자열 1개 이상), recipient_role, timing, channel, acknowledgement가 모두 필요하다. 나머지 네 필드도 공백이 아니어야 한다. 알 수 없는 필드는 창작하지 않고 보완 대기로 둔다. handover_method는 T4만 허용한다.

### T6 및 전 유형의 재가동 경험

restart_type은 normal_stop_restart, abnormal_stop_restart, maintenance_restart, unknown 중 하나다. T6는 필수이며 미상이면 unknown을 쓴다. T1~T5에서는 선택이다. restart_type과 tried_and_failed는 모든 유형에 허용한다.

| 카드 restart_type | 시도 restart_type | 결과 |
|---|---|---|
| known | 같은 known | 허용 |
| known | 다른 known | 거부 |
| known | unknown | 허용 |
| unknown | 어떤 허용값이든 | 허용 |
| null/생략 (T1~T5만) | 어떤 허용값이든 | 허용; 카드 유형을 시도로부터 자동 추론하지 않음 |

각 시도는 attempt_id(^AT-\d{4}$), restart_type, 공백 아닌 action·observed_result가 필요하다. failure_reason 미상은 null로 유지한다. evidence_ids는 ^(K|EV|AR)-\d{4}$ 형식만 검사하며 실제 존재를 보장하지 않는다.

## 5. v1.1 선택 메타데이터

| 위치 | 용도·검증 |
|---|---|
| generalization_evidence | supporting_event_ids/contradicting_event_ids는 EV-숫자 4자리, 각 목록 중복 금지, 상호 겹침 금지. generalization_scope, confidence_basis는 근거가 있을 때 작성 |
| FailedAttempt.evidence_gap | not_observed, not_recorded, insufficient_evidence, conflicting_evidence 또는 null. 실패 이유를 대체하지 않음 |
| 실패 후속 정보 | next_observations, required_data, data_collection_role은 실제 추가 조사 필요사항만 작성 |
| Provenance.sources | source_id, 선택 locator·document_version. 출처 자체와 지지·반대 관계를 구분하며 자동 복사하지 않음 |
| 실행 출처 | extraction_method, model_version, prompt_version, index_version, schema_version은 실제 실행 정보만 기록 |
| safety_review | 카드 채택 상태와 별개인 사람의 검토 기록. draft/pending_review/approved/restricted/expired/withdrawn |

선택 객체는 null/생략, 선택 목록은 빈 목록/생략을 사용한다. 제공된 새 설명 문자열은 공백을 허용하지 않는다. safety_review.status=approved라면 approved_by, approver_role, reviewed_at, valid_until, evidence_grade가 필요하다. 날짜는 시간대를 포함하고 valid_until > reviewed_at이어야 한다. review_triggers·safety_level은 선택이다.

승인자를 추정하거나 자동 승인하지 않는다. 현재는 승인 권한·상태 전이·자동 만료를 실행하지 않는다. 과거 approved 기록이 현재 운영 승인이나 KB 채택을 보장하지 않는다.

## 6. 판정 예시

유형 판정 예시이며 완성된 유효 카드나 현장 작업 지시가 아니다.

| 후보 내용 | 처리 |
|---|---|
| 평소 대비 진동 감각의 차이와 확인 필요성 | T1 후보; 원문의 증상과 근거 확인 |
| 운전 조건별 적용·제외 요령 | T2 후보; 조건 구조화 |
| 원인 후보를 좁히는 확인 절차, 원문 단계 번호 2와 5 | T3 후보; 오름차순이면 번호 2·5 그대로 허용 |
| 현재 속도 하향 중, 원인 미확정, 다음 조에서 30분 간격 확인 | 사건별 인계 기록. 이것만으로 T4 카드화하지 않음 |
| 인계할 정보·대상·시점·채널·수신 확인 방법을 정한 원문 | T4 후보; 5개 필드의 근거 확인 |
| 독립적인 접근 금지·정지·격리 지식 | T5 후보; 안전 근거와 사람 검수 필요 |
| 정비 후 재가동 실패 경험, 실패 이유 미기록 | T6 후보; maintenance_restart, failure_reason=null. 미기록 사실이 확인될 때 evidence_gap=not_recorded |

## 7. 검수와 남은 작업

별도 검수 메모에는 주 유형, 목적, 경합 유형, 분리 여부, 원문 위치, 부족 정보, 전문가 확인 질문을 남긴다. 스키마 밖 메모를 카드 JSON의 임의 키로 넣지 않는다. 현재 모델은 알 수 없는 키를 무시할 수 있다.

스키마는 형식과 카드 내부 관계를 검증한다. 원문의 실존·주장 지지 여부, 참조 무결성, ID 중복, 사건별 분할·평가 누수는 별도 배치 검증이 필요하다. 생성·저장 파이프라인과 그 검증은 아직 완성되지 않았다.

T6의 도입 자체는 미결이 아니다. 전문가 검토는 유형 경계의 현장 타당성, 안전 검수 기준, T6 평가·분할 적용 범위를 대상으로 한다. 정의 변경 시 적용 버전과 기존 카드 재분류 필요 여부를 기록한다.
