## 1. 동작·계약 충돌

| 항목 | 시연 문서의 요구 | 현재 구현 | 영향과 필요한 정리 |
| --- | --- | --- | --- |
| LLM 실패·시간 초과 | 검색 결과와 안전 공지만 표시 | PDA `responseCards()`는 `review_queue=true`일 때 조치 카드를 모두 숨긴다. HTTP 오류·브라우저 시간 초과는 `runSearch()`에서 질문 화면으로 돌아간다. | 안전 공지는 정상 JSON 응답에서 표시할 수 있지만, 검색 결과를 모델 없이 보여주는 실패 경로는 문서대로 동작하지 않는다. 검증된 검색 카드와 모델 답변을 구분해 실패 화면 계약을 정해야 한다. |
| 클라우드 인계 ID | 로컬 인계를 Aiven으로 업로드하고 같은 ID는 한 번만 저장 | PDA는 `HO-` + UUID 또는 시간·난수 ID를 생성한다. SQLite는 ID를 최대 64자로 받지만 Aiven `handover_record.handover_id`는 `VARCHAR(16)`이고 주석 규칙은 `^HO-\d{4}$`다. | 긴 PDA ID를 현재 Aiven 열에 그대로 넣을 수 없다. ID 규격 또는 업로드 매핑을 정해야 한다. |
| 클라우드 인계 필수 필드·중복 기준 | 로컬 저장한 메모·인용 카드·설비·시각을 클라우드로 전달, ID 기준 중복 방지 | Aiven은 `version`, `shift_from`, `shift_to`, `shift_date`, `author_persona_id`, 사건·조치 ID 배열 및 해시 등을 필수로 요구한다. 현재 PDA 본문에는 이 필드가 없다. SQLite 기본키는 `handover_id`, Aiven 기본키는 `(handover_id, version)`이다. | 로컬 본문을 그대로 업로드할 수 없다. 필수 필드 생성·변환과 버전별 중복 정책을 합의해야 한다. |
| 클라우드 메모 원문 | 인계 메모를 올리고 다음 조 화면에서 인계 목록을 읽음 | `db/aiven_schema.sql`은 §4.11 원칙에 따라 `memo_text`, `open_items[].text` 원문 대신 해시만 저장한다고 명시한다. | 현재 스키마만으로 다음 조가 메모 본문을 읽는 시연은 성립하지 않는다. 원문 보관 정책과 실제 조회 경로를 먼저 정해야 한다. |
| 해당 지식 없음 화면 | 해당 지식 없음과 그 설비의 안전 공지를 먼저 보라는 안내 | `renderResult()`는 남은 조치 카드가 0개이면 실제 시도 여부와 무관하게 “적용 가능한 조치를 모두 시도했습니다”를 표시한다. | 지식 없음·검토 대기·시도 소진을 화면에서 구분해야 한다. |
| 노트북 비상 대체 | 노트북에서 `python -m shiftlink.mes --host 0.0.0.0` 실행 후 화면 주소만 변경 | 질의 모델의 기본 Ollama 주소는 실행 장비의 `localhost:11434`다. 새 MES 프로세스는 기존 Jetson의 인식 메모리와 SQLite를 자동으로 이어받지 않는다. | 노트북 자체 Ollama 또는 접근 가능한 Jetson Ollama 연결 설정이 필요하다. 기록 연속성이 필요하면 데이터 이전도 정해야 한다. 화면 주소 변경만으로 같은 상태를 유지하지 못한다. |

## 2. 아직 구현되지 않은 시연 범위

| 항목 | 문서의 시연 장면 | 현재 상태 |
| --- | --- | --- |
| 인계 자동 업로드 | 인터넷을 끊고 인계 2건 작성 → 복구 후 Aiven에 정확히 2건 | 로컬 SQLite outbox 저장·중복 방지까지 구현됐다. 자동 업로더·재시도·업로드 완료 상태 갱신은 없다. |
| 업로드 대기 건수 | 화면에 “업로드 대기 N건” | PDA 표시용 `S.outbox`는 SQLite backlog와 연결되지 않았다. 브라우저의 미확인 제출 1건 보존과 Jetson의 클라우드 업로드 대기는 서로 다른 상태다. |
| 다음 조 인계 목록 | 노트북에서 클라우드 인계 목록 조회 | PDA의 기존 인계 목록은 `/api/kb/cards`가 제공하는 예시 인계다. 클라우드 또는 새 outbox 인계를 읽는 화면·조회 API는 없다. |
| 질의·답변 기록 업로드 | 질문·설비·인용·응답 시간·모델/KB 버전을 클라우드에 기록 | 질의 API에서 해당 정보를 Aiven으로 저장하는 경로가 없다. 기존 `pipeline_run`은 P0~P6 데이터 파이프라인 메타데이터, `eval_result`는 평가 지표용이며 질의 본문·답변 로그 계약을 별도로 정해야 한다. |
| 현장 피드백·이벤트 요약 | 도움됨/틀림 기록 및 관리자용 정지·알람 요약 | 문서에 대응하는 클라우드 저장·조회 흐름은 확인되지 않았다. |

이 항목은 기존 H1·H2의 로컬 완료 기준을 넘어서는 후속 범위다. 시연 문서에는 계획으로 남아 있으므로 현재 완료된 기능으로 안내하면 안 된다.

## 3. 일치하는 부분

- 라즈베리파이는 화면·웹캠 분류를 담당하고, Jetson은 MES 엔진·검색·LLM·SQLite를 담당한다. 실제 장비별 배치 완료 여부와 별개로 구현 구조는 이 분리를 지원한다.
- MES 엔진은 HTTP 서비스와 같은 프로세스에서 실행되며 상태·이벤트를 HTTP로 제공한다.
- 인식 API는 클래스·신뢰도·장치 ID·시각을 받으며 원본 이미지를 보내지 않는다.
- `/api/query`는 최근 인식 설비와 현재 MES 관측값을 서버에서 붙인다. 명시적 수동 설비 선택과 변경된 `scan_id` 거절도 지원한다.
- `FixedPipeline`은 KB 검색과 안전 카드 검색 후 Ollama 모델을 호출한다. MES 질의의 기본 모델은 `exaone3.5:2.4b-instruct-q4_K_M`이다.
- PDA 정상 응답 화면은 안전 공지 → 답변 → 인용 조치 카드 순으로 표시한다.
- `/api/handover`는 SQLite에 원본 제출을 영속 저장한다. 동일 ID·동일 내용 재전송은 1건을 유지하고 다른 내용은409로 거절한다.
- 현재 검색 대상 `accepted/kb/L1` 카드 수는 문서와 같은 **86장**이다.
- 라즈베리파이의 기존 `shiftlink.pda` 프록시와 Jetson의 선택적 `--api-only` 모드는 문서의 역할 분리와 양립한다.

## 4. 검사에서 확인한 결과와 한계

- 현재 카드 JSON을 읽어 `accepted/kb/L1` 조건으로 세었을 때 **86장**이었다.
- Node에서 PDA의 `responseCards()`를 호출해 `review_queue=true`인 응답에 대해 조치 **0건**, 안전 공지 **1건**이 남는 것을 확인했다. 이는 화면 매핑 검사이며 실제 LLM 시간 초과를 재현한 결과는 아니다.
- 소스 검색에서 SQLite outbox의 저장·조회는 확인했으나 클라우드 업로드 경로는 확인되지 않았다.
- 문서의 **p95 약 5초**, 실제 랜선 분리·복구, 물리 웹캠·PDA 조작은 이번 비교 검사로 검증하지 않았다.
- 이전 별도 Jetson 검증에서는 실제 exaone 왕복·인용·안전 공지·인계 재시작 유지가 확인됐다. 당시 답변 본문은 `K-1001` 문자열에 그쳤으므로 설명형 답변 품질 통과를 의미하지 않는다. [기존 검증 기록](mes-query-handover-20261002.tdd.md) 참고.

먼저 정리할 부분은 클라우드 인계 ID·필수 필드·원문 정책이다. 이후 LLM 실패 화면 계약과 자동 업로더·대기 건수·다음 조 조회 경로를 맞춰야 문서의 전체 시연을 수행할 수 있다.
