## 2. 현재 스키마 v1.1 (v1.0 규칙 유지)

`SCHEMA_VERSION = "1.1"` 모듈 상수. 기존 필드·검증을 기반으로 공백·연산자·유형별 필드 제한을 보완했고, §6의 선택 메타데이터를 추가했다. 카드 `version`은 전달받은 데이터 버전으로 보존하며 구현 버전과 동일하다고 가정하지 않는다.

공통 최소 조건: T1·T3는 공백 아닌 `symptom`, T2는 `conditions` 1개 이상, T5는 `safety_flag=true`가 필수다. 모든 유형에서 `safety_flag=true`이면 공백 아닌 `safety_basis`가 필수다. `symptom`·`safety_basis`는 선택인 경우 null/생략 가능하나, 문자열로 주어지면 공백만일 수 없다.

신규 생성은 `status="draft"`, `grade="L0"`로 시작한다. 이는 생성 정책이며 기존 accepted/L1 데이터의 스키마 허용을 없애지 않는다. 모델이 채택·승인을 결정하지 않는다. ID·출처·분할·시각·실행 버전은 입력/실행기가 공급하고, 근거 없는 confidence를 만들지 않는다. 필수 정보가 부족하면 별도 검수 기록에 원문과 부족 항목을 남긴다. 보완 큐의 자동 생성·저장 기능은 아직 구현되지 않았다.

#### 2.1.1 T1~T6 경계 규칙 `[현재 작성 기준]`

2026-09-22 사용자 요청으로 작성 가이드·프롬프트를 아래 기준에 맞춘다. 이는 현 작업의 작성 기준이며 전문가 원 정의나 과거 회의 승인을 새로 확정했다는 뜻이 아니다.

| 상황 | 유형 | 판단 근거 |
|---|---|---|
| 감각 기반 이상 징후의 의미 해석 | T1 | 증상의 의미가 핵심; 증상 유무나 단계 수로 T3와 구분하지 않음 |
| 조건에 따라 적용할 요령이 달라짐 | T2 | 조건별 요령 차이가 핵심; 단순 적용 범위는 다른 유형의 conditions로 기록 |
| 증상에서 원인을 좁혀가는 확인 순서 | T3 | 목적이 원인 규명 |
| 정지 상태에서 운전 상태로 되돌리는 절차·실패 경험 | T6 | 목적이 상태 복귀 |
| 재가동 미완료 상태를 다음 교대에 넘기는 방법 | T4 | 목적이 전달 |
| 재가동 중 독립적인 금지·중지·격리 지식 | T5 | 금기 자체가 핵심; 부수적인 주의사항은 원래 유형 + safety_flag |

한 카드가 독립적인 두 목적을 담으면 분리한다. 독립적인 안전 금기는 T5로 분리하고, 다른 유형에 부수적인 안전 내용은 safety_flag로 표시한다. T1~T6 전체의 기계적인 우선순위는 두지 않는다. 사건별 인계 현황은 원문/인계 기록이며, T4 카드는 재사용 가능한 인계 방법과 5개 필수 필드의 근거가 있어야 한다.

카드 하나에 주된 목적 하나를 지정한다. 분리는 각 지식이 따로 검색돼도 쓸모 있을 때만 하며, 같은 목적의 근거·조건·부연 설명은 분리하지 않는다. 독립 T5로 분리해도 원래 카드에 필요한 안전 표시·근거·중지 조건을 유지한다.

T6는 현 스키마를 유지하며 재가동 순서는 know_how에 기록한다. 원인 진단과 재가동이 독립적인 지식이면 T3와 T6로 분리하지만, 단계 저장만을 위해 재가동 지식을 T3로 바꾸지 않는다. T6의 단계별 표시·순서 검증이 실제 요구사항으로 확정되면 스키마 계약·검증·생성 지침·응답 표시·평가를 함께 확장한다. 이번 결정으로 새 필드나 카드 연결 기능을 추가하지 않는다. 분류 예시는 [현재 작성 가이드](../../seeds/카드_작성_가이드_초안.md#21-유형-경계-적용-기준-2026-09-22-사용자-요청-반영)를 따른다.

#### 2.1.2 T6 승격의 데이터·평가 파급 `[미결 — 통합본 개정 필요]`

### 2.2 v1.0 기본 모델 요약 (v1.1 선택 필드는 §6)

```python
NonBlank = Annotated[str, StringConstraints(strip_whitespace=True, min_length=1)]

class HandoverMethod(BaseModel):          # D-27: T4 전달 방법
    required_context: list[NonBlank]      # min_length=1, 전달할 정보
    recipient_role: NonBlank              # 대상
    timing: NonBlank                      # 시점
    channel: NonBlank                     # 방법
    acknowledgement: NonBlank             # 확인 방법

class ResolutionStep(BaseModel):          # D-28: T3 단계
    step_id: str                          # pattern ^ST-\d{2,4}$
    order: int                            # ge=1
    action: NonBlank
    preconditions: list[str] = []
    expected_result: NonBlank
    stop_conditions: list[str] = []       # 길이 제한·요약으로 잘라내지 않음

RestartType = Literal["normal_stop_restart", "abnormal_stop_restart",
                      "maintenance_restart", "unknown"]
# 가상 설비 사전 기반 잠정 허용값. 현장 표준으로 단정하지 않음.

class FailedAttempt(BaseModel):           # D-29: 시도·실패
    attempt_id: str                       # pattern ^AT-\d{4}$
    restart_type: RestartType
    action: NonBlank
    observed_result: NonBlank
    failure_reason: str | None = None     # None = 이유 미상 보존. "미상" 문자열 자동 기입 금지
    evidence_ids: list[str] = []          # ^(K|EV|AR)-\d{4}$ 형식만 검사. 실존 검증은 별도 배치 검증 필요

class TypePayload(BaseModel):
    handover_method: HandoverMethod | None = None
    steps: list[ResolutionStep] | None = None
    restart_type: RestartType | None = None
    tried_and_failed: list[FailedAttempt] = []
```

### 2.3 검증 규칙 (model_validator, 위반은 ValidationError)

기존 규칙 유지 + 추가:

1. T4 → `type_payload.handover_method` 필수. (“인계했다” 사실만 있는 카드 차단은 구조 필수화로 달성)
2. T3 → `type_payload.steps` 필수(1개 이상). 각 `order`는 1 이상의 정수이며 1부터 시작하거나 연속일 필요는 없다. `step_id` 중복 금지, `order` 중복 금지, 리스트는 `order` 오름차순이어야 함(정렬 자동 수정 금지 — 위반 시 오류).
3. T6 → `type_payload.restart_type` 필수. T6도 T5와 무관하게 `safety_flag` 규칙은 기존대로.
4. `tried_and_failed`의 각 attempt: 카드·시도 restart_type이 모두 known인데 서로 다르면 오류. known 카드 + unknown 시도는 허용한다. 카드가 unknown 또는 null/생략(T1~T5만)이면 시도는 어떤 허용 유형이든 가능하다.
5. `handover_method`가 T4 외 카드에 있으면 오류, `steps`가 T3 외 카드에 있으면 빈 목록도 오류다. 다른 유형은 null/생략한다. `restart_type`/`tried_and_failed`는 전 유형 허용(2.1). T6의 재가동 설명은 know_how와 재가동 필드에 기록하며 구조화된 T6 단계는 별도 계약 변경 대상이다.

### 2.4 사건·카드 책임 분리

- `Event.restart_attempts: list[FailedAttempt] = []` 추가 — 사건별 시도 이력.
- 카드의 `tried_and_failed`는 재사용 가능한 일반화 지식, Event의 `restart_attempts`는 해당 사건 이력. Event는 `true_cause` 등 평가 정답을 포함하므로 런타임 KB·모델 입력에 절대 전달하지 않는다(하니스가 카나리로 검사).

### 3.1 고도화 (2026-09-22) — 실제 v0.9 데이터 대응

위 계약(세 가지 outcome, `deficiencies: list[str]`, 원본 보존, 자동 창작 금지)은 그대로 두고 아래를 추가했다. 기존 outcome 판정은 바뀌지 않는다(하니스 카테고리 E dev 8/8·holdout 4/4 유지).

- **결함 코드화**: `ConversionIssue{code, severity, field, message}` 목록을 `issues`에 담고 `deficiencies`(blocking)·`warnings`(non-blocking)는 여기서 파생한다. 검토 큐가 사유별로 묶을 수 있다. 코드 목록은 `compat.py` 모듈 docstring의 표.
- **1회 수집**: 구조 검사와 pydantic 검증을 모두 돌린 뒤 코드 단위로 중복 제거한다. 결함이 여러 개인 카드를 한 번에 보고한다(검토 왕복 감소).
- **최상위 재가동 필드 이전**: `docs/data/01_kb_cards_shared.json`처럼 `restart_type`·`tried_and_failed`가 최상위에 있으면 `type_payload`로 **이전**한다(내용 변경 없음, `field_relocated` 경고). 최상위 값과 `type_payload` 값이 다르면 병합하지 않고 `payload_conflict`로 검토 대기.
- **단계 단위 필드**: 최상위 `stop_conditions`·`expected_result`는 v1.0에서 `ResolutionStep` 소속이고 대상 단계를 추론할 수 없으므로, 값이 있으면 임의의 단계에 붙이지 않고 `step_scoped_field_unmappable`로 검토 대기(빈 값이면 통과).
- **`confidence` 문자열**: `"high"` 등은 환산 공식이 없으므로 자동 변환하지 않고 `confidence_not_numeric` 결함으로 남긴다(`docs/guides/카드_작성_가이드_초안.md` §8).
- **필드 유실 가시화**: v1.0 스키마에 없는 키는 확장 제안(`scope_level`·`manual_refs`·`is_synthetic` 등)과 미상 키를 구분해 경고로 남긴다. 값은 `original`에 보존된다.
- **등급·안전 표시**: `grade`는 값을 유지하되 v1.0 게이트 미재실행을 `grade_not_revalidated` 경고로 남기고, `safety_flag=True` 카드에는 D-26 전수 검토 경고를 붙인다. T5인데 `safety_flag`가 없으면 자동으로 세우지 않고 결함 처리한다.
- **T6**: 입력이 이미 T6면 그대로 두되 경고를 남긴다. 기존 카드를 T6로 **소급 재분류하지 않는다**(§2.1.2).
- **일괄 변환**: `convert_cards_v09()` → `V09ConversionBatch`(`counts`, `issue_counts`, `duplicate_card_ids`, `auto_accepted`). `auto_accepted`는 0이어야 하며 카테고리 E 증빙에 그대로 쓸 수 있다. 중복 `card_id`는 보고만 하고 병합하지 않는다.
- **원본 무손실**: `original`은 deep copy라 호출자가 입력을 나중에 바꿔도 보존값이 변하지 않는다. `result.model_dump()`이 곧 검토 대기 큐 레코드다.
- 범위 밖: Event·Artifact의 v0.9 변환(사건 JSON은 구조가 달라 별도 계약 필요), 변환 CLI.

### 4.2 조건 매칭 규칙 (결정적)

2026-09-22 보완: 일반 `search_cards(..., observations=None)`와 안전 검색은 동일한 조건 평가를 사용한다. 적용 조건 False 또는 제외 조건 True는 순위 계산 전에 제외한다. 남은 조건 중 하나라도 미확인이면 `unverified`, 모든 조건을 확인했거나 조건이 없으면 `verified`이다. 일반 검색의 관측값도 질의 입력에서 전달한다.

### 4.4 파이프라인 고도화 (2026-09-22, `shiftlink/agent/pipeline.py`)

라우터·도구 순서·1회 호출 원칙은 그대로 두고 통합본 §4.8·§4.9·§4.12 요구를 파이프라인에 구현했다. 하니스는 dev 6/6·holdout 6/6 유지.

- **조건 불일치 제외**: 통합본 4.8의 "중복 ID를 제거하고 조건 불일치 카드는 적용하지 않는다"를 병합 단계에서 적용한다. `search_cards`는 레지스트리상 `observations`를 받지 않으므로(시그니처 변경 미결) 관측값을 가진 파이프라인이 병합 목록에 §4.2를 적용한다. 확정 False → 제외, 미관측 → 유지 + `condition_status="unverified"`. 판정 로직 단일 출처는 `Condition.evaluate()`(schemas.py)이고 `retrieval.py`의 `_evaluate_condition`이 이를 위임한다.
- **"해당 지식 없음" 게이트**: 질의 모드에서 적용 가능한 카드가 0건이면 모델을 호출하지 않고 `AgentResponse.no_knowledge=True`로 보류한다(3.3, 4.9 지식 없음 처리, 4.12 자료 부족). 인계 모드는 메모에서 항목을 추출하므로 게이트 대상이 아니다.
- **모델 입력 격리**: 모델에는 `MODEL_CARD_FIELDS` 화이트리스트로 만든 컨텍스트만 전달한다. `true_cause`·`cards_expected`·`canary_token` 등 Event 정답은 구조적으로 도달할 수 없다(§2.4). 추가로 카나리 패턴(`zzk9-`/`qqz7-`)이 검출된 카드는 컨텍스트에서 제거하고 감사에 남긴다(§5). 검증기(`validate_response`)에는 전체 `tool_results`를 그대로 넘겨 인용 ID 실존 검사를 유지한다.
- **컨텍스트 절단**: 카드당 자유 텍스트 300자 상한(4.8 발열·지연 대응). **안전 카드는 절단 예외**이며 `safety_basis`·`stop_conditions`는 어떤 경우에도 줄이지 않는다(D-26, §2.2).
- **호출 횟수**: `PipelineResult.model_calls`로 1회 원칙을 감사 가능하게 만들고 재시도는 1회(`MAX_MODEL_CALLS=2`)로 상한을 둔다.
- **응답 캐시(옵션)**: `FixedPipeline(cache=ResponseCache())`. 키는 mode+요청+모델 컨텍스트의 sha256이며 검증을 통과한 출력만 저장한다(4.8 데모 반복 시 재추론 회피). 기본값은 비활성.
- **도구 실패 격리**: 설비·인계·체크리스트 실패는 빈 결과로 기록 후 진행하고, `search_cards`·`search_safety_cards` 실패는 근거·D-26 노출을 보장할 수 없으므로 "지식 없음"으로 보류한다(`tool_results["retrieval_error"]`).
- **감사 로그**: `PipelineResult.audit`에 도구 호출 순서·인자·결과 수·실패, 게이트 판정(조건 불일치·카나리 차단·지식 없음), 모델 호출/재시도/캐시 히트를 기록한다. `run(payload, actor=, device=)`로 주체·장치를 남긴다. 시각은 결정성 유지를 위해 기록하지 않는다(필요 시 호출자가 부여).
- **response.py 부수 변경**: `AgentResponse.no_knowledge` 필드와 렌더 1줄 추가. 등급(4.10 "L1 합성·시뮬레이션 검증") 표기는 아직 미구현으로 남는다.
- **dev 픽스처 수정**: `eval/fixtures/dev/category_f_e2e.json`의 F-e2e-002는 설명이 "condition-matching"인데 관측값 `pressure=8`이 카드 조건 `pressure>=10`과 모순이었다. 관측값을 12로 고쳐 설명과 일치시켰다(기대값은 그대로). holdout은 수정하지 않았다.

### 4.5 응답 고도화 (2026-09-22, `shiftlink/agent/response.py`)

§4.3의 필드 이름과 렌더 순서는 유지하고 통합본 §3.3·§3.4·§4.9·§4.10 요구를 채웠다. 하니스 dev 6/6·holdout 6/6 유지.

- **등급 표기(4.10)**: `cards: list[CardCitation]`에 `grade`와 `grade_label`("L1 합성·시뮬레이션 검증")을 담고 렌더의 인용 목록에 함께 출력한다. 등급 없는 인용은 `grade_label_missing`으로 검증 실패. 렌더 말미에 "실제 작업지시 아님" 고지를 **상시** 붙인다.
- **인용 검증(3.3, 4.8 코드 검증)**: 카드 파생 블록은 코드가 만들고, `answer`·`cited_card_ids`·`handover_candidates`만 `model_output`에서 받는다. 인용 ID는 검색 결과와 대조해 없는 것은 `dropped_citations`로 분리하고, **유효 인용이 하나도 없으면 답변을 버리고 `no_knowledge=True`로 치환**한다. 모델이 구조화 인용을 주지 않으면(결정적 스텁·구 호출자) 검색 결과를 인용으로 대체한다.
- **T4 보존(D-27)**: `handover_methods`를 카드별 목록으로 바꿔 두 번째 T4 카드가 첫 번째를 덮어쓰던 유실을 없앴다. `handover_method`는 첫 항목을 돌려주는 파생 필드로 남겨 §4.3 필드명을 유지한다. 검색된 T4가 응답에서 빠지면 `handover_method_lost`.
- **T3 카드별 순서(D-28)**: `StepRender.card_id` 추가. 렌더는 카드 단위로 묶어 출력하고 검증도 카드별로 오름차순·중복을 본다(이전에는 두 T3 카드의 단계가 섞여 항상 review로 빠졌다).
- **중단 조건(§2.2)**: 안전 공지의 `stop_conditions`를 `steps[0]`이 아니라 카드의 **모든 단계**에서 수집한다. 검증의 기대 집합도 v1.0에 없는 최상위 `stop_conditions` 대신 `type_payload.steps`에서 만든다(기존 검사는 사실상 동작하지 않았다).
- **안전 근거(D-26)**: `safety_basis`가 비면 빈 문자열로 통과시키지 않고 `safety_basis_missing`으로 보고하며 렌더에도 "근거 미기재 — 검토 필요"로 표시한다.
- **재가동 근거(D-29)**: `RestartFailure.evidence_ids`를 보존·렌더한다. `failure_reason=None`은 "미상" 표기만 하고 데이터는 그대로 둔다.
- **인계 후보(3.4 F-04)**: `handover_candidates`를 `status="proposed"`로만 제시하고 저장하지 않는다. 후보가 검색되지 않은 카드를 인용하면 `handover_candidate_unknown_card`.
- **검증 결과 보존·재시도 정책**: `validate_response`는 `[code] message` 형식으로 반환하고 `AgentResponse.validation_errors`에 남는다(사유 없는 review_queue 금지). 재시도는 모델 귀책 코드(`cited_card_unknown`, `handover_candidate_unknown_card`)에만 적용한다 — 카드 파생 블록은 결정적이므로 재추론해도 결과가 같다(§4.3 "스키마 실패에 한해 1회", Jetson 추론 낭비 방지). 판정은 `is_model_retryable()`.
- 미구현으로 남는 것: 실제 웹 UI 반영(§4.3 명시), 모델 출력 JSON 스키마 강제(Ollama `format`) 연결.

### 4.6 도구 계약 고도화 (2026-09-22, `shiftlink/agent/tools.py`)

도구 6종은 계약만 존재하고 전부 `NotImplementedError`라는 상태(개발계획 §2)를 유지한다. 실제 저장소 어댑터(설비 사전 JSON·sqlite-vec·인계 CSV·체크리스트)는 여전히 이 범위 밖이며, 대신 **계약을 검사 가능한 형태로** 만들었다. 하니스 dev 6/6·holdout 6/6 유지.

- **`TOOL_SPECS`**: 통합본 4.8 도구 표(입력·선택 입력·출력·저장소·읽기 전용·주석)를 데이터로 선언한다. `TOOL_STUBS`는 여기서 파생되므로 표와 코드가 어긋날 수 없다. `MAX_K = 5`(4.8 k 상한)도 여기에 둔다.
- **필드명 미확정 존중**: 출력 필드는 이미 코드로 고정된 카드 계열(`card_id`·`know_how`·`conditions`·`grade`, 안전 조회는 `safety_flag`·`safety_basis` 추가)에만 선언한다. 설비·인계·체크리스트의 "정식명·공정·관련 카드 ID" 등은 필드명이 정해지지 않았으므로 **추측해서 만들지 않고** `[필드명 미확정]`으로 남긴다. 4.8의 점수(score)도 현재 산출하지 않으므로 선언하지 않는다.

### 4.7 라우터 고도화 (2026-09-22, `shiftlink/agent/router.py`)

형식 기반 판정과 모드별 필드 격리(`extra="forbid"`)는 그대로 두고, 모델 입력의 신뢰 경계로서 부족했던 부분을 채웠다. 하니스 dev 6/6·holdout 6/6 유지.

- **관측값 스키마화**: `observations`가 `list[dict[str, object]]`라 무엇이든 통과했고, 파이프라인이 `{obs.get("signal"): obs.get("value")}`로 조용히 변환하면서 **`signal` 없는 기록은 버리고 같은 신호가 중복되면 뒤엣것이 이겼다**. §4.2 조건 판정이 이 값으로 안전 카드 적용 여부를 정하므로, 중복 신호 하나가 조건을 False→True로 뒤집을 수 있었다. `Observation`(`signal`·`value`·`unit`, `extra="forbid"`) 모델로 바꾸고 **중복 신호는 요청을 거부**한다. `value`는 필수다 — 값 없는 기록은 관측이 아니며, `None`으로 통과시키면 확정 조건이 미확인으로 약화된다.
- **공용 접근자**: 두 요청 모델이 `equipment_ids`·`search_text`·`k`·`shift`·`observation_map()`을 같은 이름으로 노출한다. 파이프라인의 `_run_tools`에서 모드별 분기(`request.eq_id` vs `request.eq_ids`, 하드코딩된 `k=5`)를 제거했다. 인계 모드의 `k`는 4.8 상한을 쓴다.
- **설비 ID 중복 제거**: `eq_ids`에 같은 설비가 두 번 들어와도 조회는 한 번만 한다. 입력값 자체는 보존하고 접근자에서만 정리한다.
- **k 상한 단일 출처**: `MAX_K`(tools.py, 4.8)를 라우터가 그대로 쓴다. 상한 값이 두 곳에서 갈라지지 않는다.
- **판정 근거 기록**: `RoutedRequest.route_reason`("format key 'question'")으로 규칙 라우터의 결정을 남긴다(4.12).
- **경계 오류 정리**: 비-매핑 입력과 형식 키 모호를 `[route_payload_invalid]`·`[route_format_ambiguous]` 코드 문자열로 구분해 던진다.
- **4.8 문구와의 차이 [확인 필요]**: 4.8은 "입력 형식(메모 vs 질문)·**키워드**로 판정"이라고 적혀 있으나, 구현은 **형식만** 사용한다. 같은 한국어 문장이 모드를 바꾸면 판정이 비결정적이 되고 기존 라우팅 테스트가 이를 금지한다. 키워드 라우팅 채택 여부는 팀 확인 항목으로 남긴다.
- **미결로 남는 것**: `eq_id`·`eq_ids`의 값 형식. 현재 테스트는 `HPU-01`, 하니스는 `HPU`(스키마 `Equipment` 리터럴), `docs/data`는 `EQ-0001`을 쓴다. 4.8이 `lookup_equipment`에 "설비 ID/별칭 → 정식명" 해소를 맡기고 있으므로 라우터에서 형식을 강제하지 않았다. 별칭 해소 규칙이 정해지면 그때 반영한다.

## 6. 실행·검증

### 2026-09-22 선택 메타데이터 확장 (스키마 구현 1.1)

사용자 요청에 따라 다음 선택 필드를 추가한다. 기존 카드의 `version`, 채택 상태, T4 필수 항목은 유지한다. `SCHEMA_VERSION`은 구현 계약 버전 `1.1`이며 과거 카드의 버전과 출처 기록을 소급 변경하지 않는다. 아래 확장은 9/21 회의 승인 사항으로 간주하지 않는다.

| 위치 | 선택 필드 | 용도 |
|---|---|---|
| `KnowledgeCard.generalization_evidence` | `supporting_event_ids`, `contradicting_event_ids`, `generalization_scope`, `confidence_basis` | 출처 자체와 구별되는 지지·반대 관계 및 일반화 근거 |
| `FailedAttempt` | `evidence_gap`, `next_observations`, `required_data`, `data_collection_role` | 근거 공백의 유형과 후속 수집 정보 |
| `ResolutionStep` | `verification_step`, `rollback_action`, `escalation_target`, `escalation_channel` | 결과 확인·복구·보고 경로 |
| `KnowledgeCard.safety_review` | `status`, `approved_by`, `approver_role`, `reviewed_at`, `valid_until`, `review_triggers`, `evidence_grade`, `safety_level` | 사람의 안전 검토 기록 |
| `Provenance` | `sources[]`, `extraction_method`, `model_version`, `prompt_version`, `index_version`, `schema_version` | 원문 위치와 생성·추출 실행의 추적 |
| `Provenance.sources[]` | `source_id`, `locator`, `document_version` | 원문 식별자, 페이지·절 등 위치, 문서 버전 |

- 모든 새 상위 필드는 미지정 가능하다. 미상 값은 null/빈 목록으로 보존하며 자동 생성하지 않는다. 값이 제공된 새 문자열은 공백을 허용하지 않는다.
- 지지·반대 사건 ID는 `EV-0001` 형식이고 각 목록은 중복 없이 서로 겹치지 않아야 한다. `provenance.event_ids`는 출처, 새 목록은 근거의 역할이므로 자동 복사하지 않는다. ID 실존·분할 검사는 별도 데이터 검증 책임이며 사건 본문을 자동 조회하지 않는다.
- `evidence_gap`은 `not_observed`, `not_recorded`, `insufficient_evidence`, `conflicting_evidence`. `failure_reason=None`을 대체하지 않으며 일부 이유와 추가 근거 공백은 공존할 수 있다.
- `safety_review.status`는 `draft`, `pending_review`, `approved`, `restricted`, `expired`, `withdrawn`. 기존 `KnowledgeCard.status`와 별개다. `approved` 기록에는 승인자·역할·검토일·유효기한·근거 등급이 필요하다. 날짜는 시간대가 필요하며 유효기한은 검토일 이후여야 한다.
- 안전 검토는 **메타데이터 저장만** 지원한다. 승인 권한 확인, 상태 전이, 자동 만료, 조회 차단 정책은 구현하지 않았다. 과거 `approved` 기록이 현재 유효한 승인을 보장하지 않는다. 기존 `accepted/L1/kb` 적재 정책은 유지한다.
- 응답의 `card_metadata[card_id]`에 출처·일반화 근거·검토 기록을 보존한다. 단계 및 실패 메타데이터는 구조화 응답과 텍스트에 전달한다. 모델·프롬프트·인덱스 버전은 구조화 메타데이터로 보존하고 화면에 일괄 출력하지 않는다.
- 신규 필드는 향후 필수 확장을 뜻하지 않는다. 원문 추적·실패 조사·현장 절차·검토 운영 등 실제 용도가 있는 것만 채운다. 필드 추가 자체로 검색 품질 향상을 주장하지 않는다.
- 검색 활용: 기존 `know_how` 외에 제목·증상·구성요소·일반화 적용 범위·단계 조치/예상 결과/확인 방법/사전 조건·인계 정보·실패 조치/관찰 결과/이유/추가 관찰/필요 자료를 토큰 일치 검색에 사용한다. 승인자·생성 모델·출처 ID는 순위 점수에 사용하지 않는다. 조건 평가 후 top-k를 선택하고 해당 카드만 직렬화한다. 이는 인메모리 어댑터 개선이며 벡터·하이브리드 인덱스나 대규모 운영 성능 검증을 대체하지 않는다.
