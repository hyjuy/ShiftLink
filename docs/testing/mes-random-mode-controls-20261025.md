# MES 랜덤 모드 버튼·PDA 모의 복구 연결 (2026-10-25)

## 상태

버튼/복구 수정 후보다. 앞선 RMS16/r7 운영 배포와 구분하며 이번 수정은 아직 운영에 적용하지 않았다. 운영 MES와 Pi를 읽기 전용으로 확인한 시점에 기존 AI 이상징후 EQ-0004 1건이 동일 실행에서 유지 중이었다. MES 재시작은 실행·주입 고장을 새로 만들므로 이 고장을 임의로 수리/초기화하거나 서비스를 재시작하지 않았다. Pi 분석 PID30896·NRestarts0, Jetson MES PID45593·NRestarts0를 확인했다.

원본 기준은 `351aeff0733344b46e73658de4a76a5cacaa6080`이다. 기존 모델/프로파일/평가 데이터/운영 DB/PDA 파일은 변경하지 않았다. 관계 지식/게시/검수 경로도 변경하지 않는다.

## 원인과 수정

- 기존 progressive 서비스는 시작만 눌러도 생성기가 가동됐다. 서비스 엔진은 기본을 기존 MesEngine 운전으로 두고, 제어 바의 **랜덤 모드** 버튼으로만 새 모드를 켜고 운전을 시작한다. 시작/일시정지/재개는 운전 상태만 바꾼다. 활성 고장/회복 확인 중의 모드 해제와 시나리오 변경은 거절하며 같은 run/sequence와 이력을 유지한다. 초기화/프로세스 재시작 뒤 랜덤 모드는 꺼진다. 예전 `--random-faults`는 바꾸지 않았다.
- 점진 고장은 센서만 바꾸고 `recovery`를 만들지 않았다. PDA는 서버의 `mes_recovery`/`mes_restart` 항목이 없으면 비활성 자리표시자를 그린다. MES 화면은 scenario_id=normal도 복구 금지로 취급했다. 관측된 이상에 공통 수리 절차를 붙이고, 시나리오가 normal이어도 유효한 복구 계획이 있으면 기존 단계 잠금을 따른다.
- AI 조기 징후는 정상 범위를 벗어나기 전에 나타날 수 있다. 조치 시작에서 사용자가 선택한 설비에 동일한 공통 항목을 제공한다. 생성기의 종류/예정 시각/강도/센서 목표를 공개하지 않는다. 실제 수리 명령은 선택 설비에 진행 중인 주입 고장이 있을 때만 연결하고, 다른 설비/이전 실행의 세션은 거절한다.
- **모의 수리 완료 기록**은 정지와 주입 고장 해제를 기록하며 곧바로 정상 복귀로 세지 않는다. **재가동 (라인 복구 시작)** 이후 현재 프레임의 품질·단위·시각·정상 범위를 충족하는 센서를 3회 연속 확인해야 `recovered`다. 불량/누락/비가동·다시 이상이면 확인 횟수를 채우지 못한다. 같은 설비의 다음 고장은 새 조치 단계로 시작한다.
- 지식카드 유무와 무관하게 기존 resolution API와 PDA `actionChips`를 재사용한다. PDA의 sensor/AI 알람 병합/중복 억제/진동/화면 파일은 바꾸지 않는다. 버튼은 기존 control-bar 및 attention 스타일과 정렬을 사용한다.

## Pi 검증 및 보존

모든 실행 검증은 Raspberry Pi의 별도 소스와 임시 SQLite/Chromium 프로필에서 했다. 운영 제어 API에는 쓰기 명령을 보내지 않았다.

- RED: 기존 소스에서 기본 시작만으로 fault가 생기는 assertion 실패, `random_mode` 미지원 오류. 실패 테스트 체크포인트 `5fae5bb`와 red2.log를 보존했다. 최초 RED는 KB 파일 패키징 누락으로 실패한 환경 로그이며 기능 RED로 세지 않는다.
- 추가 RED: 초기 후보에서 조기 이상징후 세션과 다른 설비 선택의 복구 항목 0건을 재현했다(early-red.log, 8테스트 중 2실패). 공통 항목 제공과 명령의 설비 검증을 나누어 해결했다.
- 핵심/기존 회귀: 기본 시작 원본 센서 동일성, 430tick 자동 고장 없음, 명시적 boolean 제어/동일 run, 고장 유지, 카드 있음/없음 전체 복구, 조기 세션, 다른 설비 보호, 반복 고장, 이전 run 세션, 불량 센서 회복 금지와 기존 progressive/legacy recovery/field draft 회귀를 실행했다.
- 광범위한 표준 라이브러리 trace는 계측 비용 때문에 중단하고 green4.log를 보존했다. 변경 모듈만 계측한 별도 검증은 85테스트 중 Python/API 회귀84개 통과, 브라우저 하니스의 SVG `.click()` 선택자 1실패였다. 소스 변경 없이 실제 설비 버튼 선택자로 하니스를 바로잡았다. 해당 실행의 progressive_factory 실행 행 관측은 208/217(95.85%)이며 분기 커버리지가 아니다.
- Pi에는 Node/agent-browser가 없어 기존 설치 Chromium과 격리 venv의 CDP 클라이언트를 사용했다. 초기 브라우저 하니스의 로딩 완료 대기/프로필 정리/설비 선택 오류는 별도 로그에 보존했다. 운영 브라우저 설정이나 패키지는 변경하지 않았다.

최종 Pi Chromium 브라우저 회귀는 browser-final.log에서 1/1 통과했다(10.041초). 앞선 browser5.log의 기능 검증 통과 후 제어 바를 화면 안에 보이게 캡처하고 버튼의 화면 내 경계까지 확인했다. 실제 시작/랜덤 켜기/설비 선택/모의 수리/재가동/정상 회복/랜덤 끄기와 지식카드 있음·없음 두 경로의 PDA actionChips 잠금 해제를 확인했다. 1440×900과 390×844에서 기존 제어 버튼 겹침이 없음을 확인하고 합성 화면을 저장했다. 앞선 Python/API84개와 합쳐 서로 다른85개 검증이 통과했으며, 새 브라우저 하니스를 고친 후 전체85개를 재실행한 것으로 표현하지 않는다. 지연/탐지율 재평가는 이 UI/제어 수정의 검증이 아니며 앞선 고정 평가의 수치를 새 결과로 재사용하지 않는다.

공개 집계는 [summary JSON](mes-random-mode-controls-20261025-summary.json)이다. 9개 파일 SHA256는 실제 Pi 검증 묶음의 바이트 해시이며 Git의 LF 정규화와 구분한다. 정적 스타일 감사는 `/static/style.css` 라우트 별칭을 파일 경로로 해석하지 못해 기본 글꼴 경고를 냈으며, 기존 CSS를 변경하지 않고 실제 Chromium에서 두 화면 폭을 확인했다.

비공개 전체 실행 자료: `/home/pi/shiftlink/analytics/validation/random-mode-control-20261025` (red/green 로그, 별도 소스, 계측 결과, 격리 화면). 과거 자료를 덮어쓰지 않는다.

## 적용 전 조건

기존 AI 사건·기존 경보가 유지 중이면 재시작으로 해제하지 않는다. 사용자가 현재 모의 사건을 수리/복구한 뒤 신규 경보 없음과 준비 상태를 다시 확인하고, 변경 소스 및 unit/drop-in·일관된 DB 백업을 보존한 후 MES에만 적용한다. 새 엔진은 기본 운전으로 시작하며 화면에서 랜덤 모드를 명시적으로 켠다. Pi 분석 모델·PDA 프로세스·기존 경보는 건드리지 않는다. 문제가 생기면 변경 파일만 이전 버전으로 복원하며 운영 DB를 과거 백업으로 덮어쓰지 않는다.
