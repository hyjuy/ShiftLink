## 감점 내역

### D1 실값 사용 (-2 / 6) → 4
- 근거: `pda.js:706-707`. 안전 공지 객체를 `{title: '안전 공지', know_how: stop_conditions.join}`로 덮어쓴다. 그래서 `safetyEl`(`pda.js:749-751`)은 실제 카드 ID 옆에 그 카드의 실제 `title`·`know_how`가 아니라 고정 문자열과 재조합 문장을 보여 준다. 또 `byId(notice.card_id)`가 로컬 카드에서 실패하면 `c.tacit_type`·`c.grade`가 없어 `K-xxxx · undefined · undefined`가 그대로 나간다.
- 왜 문제인가: 카드 ID와 표시 내용이 정본과 어긋난다. 작업자는 ID를 보고 카드 원문을 찾는데, 화면 제목이 원문에 없다.
- 근거: `pda.js:918`과 `pda.js:169`. `attempt_id`가 `'AT-' + S.attemptSeq`이고, 설비를 바꾸거나 검색할 때마다(`pda.js:1030`) 0으로 돌아간다. 이 ID가 인계 저장 페이로드 `attempts:S.tries`(`pda.js:1272`)로 서버에 들어간다.
- 왜 문제인가: 서로 다른 시도가 같은 `AT-0001`로 저장된다. 서버 쪽 시도 기록 키가 유일하지 않다.

### D2 ID 혼용 없음 (-4 / 5) → 1
- 근거: `pda.js:233`의 `findByCode(scan.code) || S.equipment.find((e) => e.type === scan.class)`. 인식한 `code`가 구성에 없으면(비활성 설비는 `pda.js:72`에서 빠짐) **같은 유형의 첫 설비로 바꿔 끼우고** `camera_scan`으로 확정한다(`pda.js:242-243`). 그런데 질의는 `camera_scan`일 때 `scan_id`만 보낸다(`pda.js:695-696`). 그 결과 화면에 확정된 `code`(예: RT-01)와 서버가 `scan_id`로 풀어 쓰는 설비(예: RT-03)가 갈라진다. (-2)
- 왜 문제인가: 라벨(`code`)과 서버 키가 서로 다른 설비를 가리키는 경로가 코드에 존재한다. 데이터 정합 렌즈에서 가장 큰 결함이다.
- 근거: `pda.js:77`, `type: String(e.code).split('-')[0]`. 설비 유형을 라벨인 `code` 접두어에서 잘라 낸다. 정본에는 `equipment_type_id`(`00_plant_and_relations.json:236`)가 따로 있다. 이 `type`이 카드 적용 판정 `cardFits`(`pda.js:44`)와 스캔 대체(`pda.js:233`)의 키가 된다. (-1)
- 왜 문제인가: 라벨 표기 규칙이 바뀌면 카드 매칭이 조용히 틀어진다. 라벨을 서버 쪽 의미 키로 쓰는 혼용이다.
- 근거: `pda.js:1055-1058`. 인계 기록을 `equipment_id`가 아니라 `open_items[].text`에 `code` 문자열이 들어 있는지로 거른다. 하나도 안 맞으면 `S.handovers` 전체를 그대로 보인다. (-1)
- 왜 문제인가: 자유 텍스트에 라벨이 들어 있는지를 키로 쓴다. 맞는 기록이 없을 때는 다른 설비의 인계가 이 설비 화면에 표시 없이 섞여 나온다.

### D3 지어내지 않음 (-4 / 4) → 0
- 근거: `pda.js:924`(`failure_reason: '조치 후에도 증상이 유지됨'`), `pda.js:945`(`효과 없음` 고정 pill), `pda.js:919-921`(조치 **전** 관측값을 `observed_result`로 저장). 「이 조치 시도」 탭 한 번으로 결과 입력 없이 실패 기록이 만들어지고 인계 페이로드(`pda.js:1272`)로 나간다. (-1)
- 왜 문제인가: 작업자가 관측하지 않은 결과와 사유를 시스템이 만들어 서버 기록으로 남긴다.
- 근거: `pda.html:481-483`. `RECIPIENT_ROLE`·`TIMING`·`CHANNEL`에 원천 없는 기본값(「야간조 정비 담당」, 「교대 직후 최초 기동 전」, 「구두 인계 + 인계서 기록」)이 미리 채워져 있다. 검증(`pda.js:1150`)은 빈칸만 막으므로 손대지 않아도 그대로 저장된다(`pda.js:1270-1271`). (-1)
- 왜 문제인가: `required_context`가 작업자 입력이 아니라 지어낸 값으로 채워진 채 인계 기록이 된다.
- 근거: `pda.js:703`과 `pda.js:705`. `unverified_card_ids`, 즉 조건을 확인하지 못한 카드가 `excluded`로 들어간다. 그런데 `actionEl`은 excluded면 `item.why`를 무시하고 「조건 불일치 — 이 카드는 지금 쓰면 안 된다」를 출력한다(`pda.js:780`). 조건 pill도 비어 있다(`conds: []`, `pda.js:702`). (-1)
- 왜 문제인가: 서버 응답은 "미확인"인데 화면은 "불일치"로 단정한다. 원천에 없는 판정이다.
- 근거: `pda.js:451`, `'K-1203': ['출구 압력 정상 · 압력/유량 부족']`. 카드 원문(kb_cards.json 3188행)은 「펌프 출구 압력은 **읽히지만** 작업에 필요한 압력 또는 유량이 부족하다」이다. "읽힌다"를 "정상"으로 바꿔 원문과 반대 방향의 상태 주장을 만들었다. (-1)
- 왜 문제인가: 압력이 부족한 상황인데 화면 라벨은 압력 정상이라고 말한다. 증상 선택 근거가 왜곡된다.

## 감점하지 않은 것 중 위험 신호

- `pda.html:15-16`은 "값을 복사해 두지 않으므로 어긋날 수 없다"고 적었지만, `SYMPTOM_LABELS`(`pda.js:422-507`)는 카드 ID별 문구와 수치(58℃·62℃·1.2 bar·16 A)를 복사해 둔 표다. 지금은 정본과 맞지만, 카드가 개정되면 조용히 어긋난다.
- `pda.js:880`의 「조치 — 관련도 순」은 실제로는 Jetson `cited_card_ids` 순서이고(`pda.js:704`) 이유 문구도 일괄 「Jetson 답변 인용」(`pda.js:703`)이다. "관련도 순"이라는 근거가 화면에 없다(C1 렌즈와 겹침).
- `pda.js:1200`은 구성에 없는 설비의 인계를 `설비 EQ-xxxx`로 표기한다. 다른 화면은 모두 `code`인데 여기만 `equipment_id`가 라벨 자리에 나온다.
- `pda.js:1032`에서 `waitCards`를 비운 뒤 아무 데서도 채우지 않는다. 안전 카드 선노출이 실제로 없다(E1). `pda.js:1033`·`pda.js:1042`는 세 단계를 동시에 run·done으로 바꾼다(E2). 렌즈 밖이라 감점하지 않았다.
- `pda.js:711-738`의 `rankCards`는 export만 되고 화면 경로에서는 호출되지 않는다. 테스트가 이 함수로 통과해도 실제 화면 동작을 보증하지 못한다.
- `pda.js:752`는 `safety_basis`가 없으면 「근거 미기재」를 표시한다. 안전 공지가 로컬 카드와 매칭되지 않을 때(`pda.js:706`) 조문이 빠질 수 있다(B2 렌즈).
